# تقرير حالة مشروع PWA وFlutter

**تاريخ التقرير:** 2026-09-26
**نقطة الكود المرجعية:** `7954f2b`
**الهدف:** تطوير PWA لتحسين الاستخدام الحالي، مع تجهيز Laravel بوصفه Backend آمنًا ومشتركًا للويب وFlutter، دون استبدال قاعدة البيانات الحقيقية أو نسخ منطق المخزون والمال داخل العميل.

---

## 1. الملخص التنفيذي

وصل المشروع إلى مرحلة متقدمة في تأسيس PWA وAPI مشتركة:

- PWA قابلة للتثبيت عبر HTTPS، بواجهة عربية RTL وأصول SVG نصية.
- API v1 موحدة باستجابات وأخطاء وإصدار ومعرف طلب ثابت.
- جلسات أجهزة مستقلة باستخدام Access Token وRefresh Token قابلين للإبطال.
- إدارة أجهزة وPush وربط OneSignal بجلسة الجهاز.
- عقد Idempotency دائم لبعض طلبات API التعديلية منخفضة المخاطر.
- Queue لإرسال OneSignal، وتنظيف مجدول للإشعارات والتوكنات ومفاتيح Idempotency.
- IndexedDB لمسودات الجرد، مع عزل الحساب والمتجر وحدود الحجم والعدد.
- APIs قراءة للمنتجات والمخزون والشفت والمبيعات وطلبيات التوريد والنقل المخزني.
- ما زالت عمليات البيع والاعتماد والنقل والجرد والشفت المالية أو المخزنية Online-only وغير مفتوحة للكتابة عبر تطبيق الهاتف.
- لم يبدأ إنشاء مشروع Flutter نفسه بعد.

**التقدم التقريبي نحو الهدف الكامل:** بين 45% و50%. البنية الأساسية متقدمة، لكن Flutter وعمليات الكتابة الحساسة واختبارات الحمل والإطلاق التدريجي ما تزال أمامنا.

## 4. الأنظمة المنجزة كأساس قراءة

### 4.1 المصادقة والمستخدمون والأجهزة

**المنجز:**

- Bearer Token للأجهزة.
- Refresh Token مع تدوير وإبطال.
- ربط الجلسة بمعرف الجهاز واسمه ومنصته وإصدار التطبيق.
- تسجيل الخروج من جهاز أو جميع الأجهزة.
- حد أقصى للأجهزة.
- فحص حالة الحساب والاشتراك والمتجر في كل جلسة.
- Rate Limiting وAbilities مستقلة.

**المتبقي:**

- اختبارات Feature فعلية لجميع حالات التعطيل والإبطال.
- اعتماد سياسة تغيير كلمة المرور وإبطال الجلسات.
- واجهات Flutter لتسجيل الدخول وإدارة الأجهزة.

### 4.2 الإشعارات ومركز النشاط

**المنجز:**

- إشعار داخلي مع عزل المستلم حسب نوع الحساب ومعرفه.
- قراءة وإخفاء آمنان.
- API للإشعارات.
- OneSignal عبر Queue مع Retry وTimeout وBackoff.
- ربط Push بجلسة الجهاز.
- صفحة إدارة للملخص والتنظيف.
- تنظيف تلقائي بعد مدة الاحتفاظ.
- Payload بإصدار وروابط داخلية آمنة.

**المتبقي:**

- اختبار Push وDeep Link على Staging وجهاز حقيقي.
- مراقبة `failed_jobs` وQueue lag.
- قياس الإرسال العام على عدد كبير من الأجهزة.
- استكمال مركز نشاط تشغيلي موحد.

## 6. حالة PWA

**المنجز:**

- Manifest عربي RTL.
- وضع `standalone` واختصارات للمالك والمحاسب.
- أيقونة SVG نصية فقط.
- Offline shell عامة.
- Service Worker بإصدار بناء.
- Network First للتنقل وCache للأصول العامة فقط.
- منع Cache لمسارات الإدارة والمالك والمحاسب وAPI.
- دورة تحديث تنتظر حفظ المسودات.
- تنظيف Cache القديم وفحص إصدار العامل.
- بوابات عقد ونشر ومتصفح.

**المتبقي:**

- اعتماد اختبار أجهزة أندرويد ضعيفة ومتوسطة.
- اختبار أكثر من متصفح وحالات انتهاء الجلسة Offline.
- تحسين الصفحات على الهاتف نظامًا بعد نظام.

## 7. سياسة Offline الحالية

### مسموح

- Offline shell.
- عرض أصول عامة مخزنة.
- مسودة جرد غير معتمدة.
- إعدادات عرض وبيانات مرجعية محدودة عند اعتمادها لاحقًا.

### ممنوع حاليًا

- البيع النهائي.
- التحصيل والمصروف.
- إغلاق الشفت.
- قبول أو رفض النقل.
- اعتماد الجرد.
- تعديل المخزون.
- اعتماد أو حذف طلب توريد.

لا يوجد Background Sync للعمليات الحساسة، ولا تستخدم سياسة Last Write Wins في المال أو المخزون.

## 8. Idempotency والصيانة

**المنجز:**

- تخزين دائم لمفاتيح Idempotency.
- عزل المفتاح حسب الحساب.
- بصمة للطريقة والمسار والجسم.
- إعادة الاستجابة الأصلية للطلب المكرر.
- رفض إعادة استخدام المفتاح مع طلب مختلف.
- تنظيف السجلات المنتهية كل ساعة.
- تنظيف الإشعارات يوميًا الساعة 02:30.
- تنظيف توكنات الأجهزة يوميًا الساعة 03:00.

**المتبقي:**

توسيع العقد بعد التدقيق إلى:

- البيع والتحصيل.
- إغلاق الشفت.
- النقل المخزني.
- اعتماد الجرد.
- اعتماد طلبيات التوريد.

ولا يكفي Idempotency وحده؛ يلزم Transaction وLock وإعادة التحقق من الرصيد ويوم العمل ومعالجة التعارض.

## 10. حالة Flutter

لم يبدأ إنشاء مشروع Flutter بعد، لكن Backend أصبح جاهزًا بدرجة جيدة لنسخة قراءة تجريبية تشمل:

- تسجيل الدخول وتجديد الجلسة.
- الحساب والمتاجر والأجهزة.
- الإشعارات وPush.
- المنتجات والبحث والمزامنة.
- المخزون والشفت والمبيعات.
- طلبيات التوريد والنقل المخزني للقراءة.

قبل فتح العمليات الحساسة في Flutter يلزم إكمال عقود الكتابة والـIdempotency والتعارض والاختبارات الفعلية.

## 12. الملاحظات والمخاطر المفتوحة

- يلزم اختبار Staging حقيقي قبل اعتبار الإشعارات والأجهزة مكتملة إنتاجيًا.
- يجب عدم توسيع Offline إلى المال أو المخزون قبل عقد تعارض واضح.
- يجب إبقاء قاعدة Laravel المصدر الوحيد للحقيقة.
- يلزم تحديث الملخص التاريخي في نهاية خارطة الطريق؛ بعض عباراته أقدم من تنفيذ Token وPush الحالي.
- لا تعد اختبارات العقود النصية بديلًا عن Feature Tests وقبول الأجهزة الحقيقية.
- لا تستخدم أوامر `migrate:fresh` أو `db:wipe` أو أي إعادة بناء مدمرة على قاعدة البيانات الحقيقية.
