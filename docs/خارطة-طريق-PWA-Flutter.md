# خارطة طريق تحويل النظام إلى PWA ثم Flutter

## 1. القرار المعماري

الهدف المعتمد هو:

> نبني PWA لتحسين الاستخدام الحالي واختبار تجربة الهاتف، وفي الوقت نفسه نعيد تنظيم Laravel ليصبح Backend آمنًا ومشتركًا للويب وFlutter.

لا تعني هذه الخطة إعادة كتابة المشروع دفعة واحدة، ولا تسمح بإنشاء منطق مخزون أو محاسبة مستقل داخل المتصفح أو Flutter. يبقى Laravel المصدر الوحيد للحقيقة، وتستخدم واجهات Blade وPWA وFlutter خدمات العمل نفسها.

## 2. مبادئ لا تتغير أثناء التنفيذ

1. **Laravel هو صاحب القرار:** الصلاحيات، يوم العمل، المخزون، البيع، الجرد، النقل، الشفتات والحسابات تعتمد من الخادم فقط.
2. **لا نجاح وهمي:** لا تظهر رسالة نجاح لعملية حساسة قبل تأكيد الخادم لها.
3. **Offline للمسودات لا للاعتماد:** يسمح بكتابة مسودة محلية، ولا يسمح باعتماد بيع أو نقل أو جرد أو شفت دون اتصال.
4. **API بإصدار واضح:** تبدأ الواجهات الجديدة من `/api/v1` ولا ترتبط بتفاصيل Blade.
5. **خدمات مشتركة:** Web Controller وAPI Controller يستدعيان Application Service نفسها.
6. **التدرج:** لا تبدأ مرحلة قبل اجتياز بوابة قبول المرحلة السابقة.
7. **الأمان والعزل:** كل استجابة وكل Cache وكل إشعار مرتبط بالمستخدم والدور والمتجر المصرح به.
8. **قابلية القياس:** لا نعالج ضغط الخادم بالتخمين؛ نضع قياسات ثم نحسن أبطأ المسارات المثبتة.
9. **هوية موحدة:** الويب وPWA وFlutter يستهلكون رموز تصميم موحدة، مع منع الألوان العشوائية داخل الصفحات.
10. **الرجوع الآمن:** كل إطلاق كبير يملك Feature Flag وخطة تعطيل لا تمس البيانات.


## 2.1 تعهد حماية النظام وقاعدة البيانات الحقيقية

المشروع الحالي **نظام عامل يحتوي بيانات حقيقية**، ولذلك تنطلق الخارطة من التحسين المحافظ، لا من الهدم أو إعادة البناء الشامل.

القواعد الملزمة:

1. لا تستخدم قاعدة الإنتاج في التطوير أو الاختبارات أو تجارب PWA وFlutter.
2. لا تنفذ `migrate:fresh` أو `migrate:refresh` أو `migrate:reset` أو `migrate:rollback` على قاعدة حقيقية.
3. لا تحذف جدولًا أو عمودًا مستخدمًا، ولا تغيّر معنى حقل موجود مباشرة.
4. أي تغيير Schema يكون **إضافيًا ومتوافقًا للخلف** أولًا، مثل إضافة جدول أو عمود nullable أو فهرس مدروس.
5. تؤخذ نسخة احتياطية مشفرة، ثم يجرب الاسترجاع منها، قبل أي Migration إنتاجية.
6. تختبر التغييرات على نسخة بيانات منزوعة الهوية أو بيانات مصطنعة داخل Staging منفصلة.
7. لا تنسخ بيانات العملاء الحقيقية إلى أجهزة المطورين أو CI.
8. يسبق كل نشر تقرير أثر: الجداول المتأثرة، مدة القفل المتوقعة، المساحة، وخطة الرجوع.
9. تستخدم Feature Flags لتشغيل المسار الجديد تدريجيًا مع بقاء المسار الحالي صالحًا.
10. لا يستبدل النظام العامل دفعة واحدة؛ يفعّل البديل لنظام واحد ومجموعة مستخدمين محددة ثم يقارن الناتج.
11. لا تعدّل البيانات القديمة لتناسب واجهة جديدة إلا بخطة ترحيل مدققة وقابلة للاستئناف.
12. كل Script بيانات يكون idempotent، يسجل التقدم، ويملك Dry Run وتقريرًا قبل التنفيذ الفعلي.

مرجع الاختبارات الملزم هو `docs/testing-database-safety.md`، ويجب أن تبقى اختبارات PHPUnit على SQLite داخل الذاكرة وفق إعدادات المشروع. أما اختبارات التكامل مع MySQL فتستخدم قاعدة اختبار منفصلة لا تحمل بيانات حقيقية.

## 2.2 استراتيجية التغيير الآمن

لكل تحسين يؤثر في البيانات نستخدم نمط **Expand → Migrate → Verify → Switch → Contract**:

1. **Expand:** إضافة البنية الجديدة دون إزالة القديمة.
2. **Migrate:** نقل تدريجي قابل للاستئناف عند الحاجة.
3. **Verify:** مقارنة النتائج القديمة والجديدة آليًا.
4. **Switch:** تحويل القراءة أو الكتابة خلف Feature Flag.
5. **Contract:** حذف القديم لاحقًا فقط بعد فترة استقرار ونسخة احتياطية وموافقة صريحة.

إذا كان الإصلاح لا يحتاج تعديل قاعدة البيانات فلا ننشئ Migration لمجرد إعادة التنظيم.

## 3. النطاق المستهدف

### 3.1 PWA

- واجهة الويب الحالية بعد تحسينها للهاتف.
- تثبيت على الشاشة الرئيسية.
- Shell يعمل عند ضعف الاتصال.
- إشعارات وروابط عميقة.
- مسودات محلية محددة.
- مراقبة حالة الاتصال والمزامنة.

### 3.2 Flutter

- تطبيق مستقل للعمليات اليومية.
- يبدأ بالمحاسب والمهام التشغيلية.
- يتصل بـLaravel API فقط.
- يستخدم قاعدة محلية للمسودات والقراءة المؤقتة، لا كسجل مالي مستقل.

### 3.3 ما يبقى على الويب أولًا

- الإدارة العامة.
- إعدادات الاشتراكات والصلاحيات.
- التقارير الثقيلة.
- الاستيراد والتصدير.
- إعدادات النظام الحساسة.
- عمليات الصيانة والتدقيق.

## 4. مسارات العمل المتوازية

تقسم الخطة إلى ثمانية مسارات، ويملك كل مسار قائمة مهام وبوابة قبول:

1. تدقيق النظام وتجربة الهاتف.
2. إعادة تنظيم Laravel وAPI.
3. PWA والتخزين المؤقت.
4. Offline والمزامنة.
5. الإشعارات والروابط العميقة.
6. البحث والأداء وقاعدة البيانات.
7. نظام التصميم ومركز التحكم.
8. Flutter والإطلاق التشغيلي.

هذه المسارات أدوات مشتركة، لكنها **لا تنفذ كإعادة بناء شاملة لكل المشروع**. وحدة التنفيذ الأساسية هي «نظام واحد مكتمل» كما في القسم التالي.

# نموذج التنفيذ المعتمد: نظام بعد نظام

## لماذا هذا النموذج؟

بدل فتح الإشعارات والبحث والمنتجات والبيع والجرد معًا، نغلق دورة نظام واحد من التدقيق حتى الإطلاق. هذا يحافظ على استقرار المشروع، ويجعل أثر كل تغيير معروفًا، ويمنع تراكم أنصاف الأنظمة.

## دورة العمل الموحدة لكل نظام

يمر كل نظام بالخطوات التالية دون تخطي:

1. **فهم الموجود:** المسارات، الشاشات، الجداول، الخدمات، الصلاحيات والتكاملات.
2. **توثيق السلوك الصحيح الحالي:** ما يعمل جيدًا يبقى كما هو ويحاط باختبارات.
3. **حصر الأخطاء والديون:** نفصل الخطأ المؤكد عن التحسين الاختياري.
4. **حماية البيانات:** تحديد هل يحتاج الإصلاح Schema أو بيانات، وخطة Backup/Rollback إن احتاج.
5. **اختبارات تثبيت السلوك:** Feature وPermissions وConcurrency قبل إعادة التنظيم.
6. **إصلاح محدود:** أصغر تعديل يحقق الهدف دون تغيير جانبي.
7. **استخراج خدمة مشتركة:** فقط عندما يحتاج الويب وAPI نفس منطق العمل.
8. **إضافة API للنظام:** Resources وأخطاء وصلاحيات وPagination وإصدار واضح.
9. **تهيئة PWA والهاتف:** استجابة، لمس، حالات اتصال، مسودة إذا كانت مسموحة.
10. **قياس الأداء:** استعلامات، فهارس، حجم الاستجابة، Cache وQueue عند الحاجة المثبتة.
11. **Pilot:** تفعيل محدود ومقارنة النتائج مع المسار الحالي.
12. **إغلاق النظام:** توثيق، مراقبة، خطة رجوع، وقائمة قبول موقعة قبل الانتقال للنظام التالي.

## ترتيب الأنظمة المقترح

الترتيب قابل للتعديل بعد مرحلة القياس، لكن نقطة البداية المقترحة هي:

### النظام 1: المصادقة والمستخدمون والصلاحيات

- دخول المالك والمحاسب والإدارة.
- الجلسات والأجهزة والتوكنات.
- عزل المتاجر.
- استعادة كلمة المرور.
- إبطال الأجهزة والجلسات.
- أساس `/api/v1/auth` و`/api/v1/me`.

**سبب البداية:** لا يمكن إطلاق PWA أو Flutter بأمان قبل تثبيت الهوية والصلاحيات.

### النظام 2: الإشعارات ومركز النشاط

**حالة الأساس المنجز:** اكتملت جلسات الأجهزة القابلة للإبطال، تدوير Refresh Token، وربط OneSignal بجلسة الجهاز. يبقى اختبار Push الحقيقي ضمن بوابة Staging.

- الإشعار الداخلي.
- Push والأجهزة.
- القراءة والعدادات.
- منع التكرار.
- Deep Links.
- Queue وسجل التسليم والفشل.

**المخرج:** مركز إشعارات موثوق يخدم الويب وPWA وFlutter.

### النظام 3: المنتجات والأقسام والبحث

**حالة الأساس المنجز:** اكتمل API قراءة معزول حسب المتجر للأقسام والمنتجات والبحث والباركود والمزامنة التزايدية، دون كشف التكلفة أو إضافة مسارات تعديل.

- إنشاء وتعديل وأرشفة المنتجات.
- الأنواع: وحدة، طقم، رول ومتر.
- المخزون المتاح والحد الأدنى.
- الاسم والباركود.
- بحث موحد سريع ومفهرس.
- API منتجات محدود الأعمدة ومقسم صفحات.

**المخرج:** أساس مشترك تعتمد عليه المبيعات والجرد والنقل والطلبيات.

### النظام 4: المخزون وحركاته

**حالة أساس القراءة المنجز:** اكتملت ملخصات المخزون وسجل الحركات وفحص سلامة الأرصدة عبر API معزول للقراءة فقط وفهارس مخصصة. تبقى mutations ضمن أنظمة البيع والجرد والنقل ولا تنفذ كمسار عام.

- مصدر كل حركة.
- اللقطات التاريخية للتكلفة والوحدة.
- منع الرصيد غير الصحيح.
- التزامن والقفل.
- سجل تدقيق قابل للتتبع.
- مطابقة المجاميع مع المنتجات.

**سبب تقديمه:** الأنظمة اللاحقة تعتمد على سلامة حركة المخزون.

### النظام 5: الشفت ويوم العمل

**حالة أساس القراءة المنجز:** اكتملت حالة الشفت الحالية، سجل الإقفالات، وأيام العمل الناقصة عبر API معزول للقراءة فقط. تبقى عمليات الفتح والإغلاق كتطوير حساس مستقل.

- فتح وإغلاق الشفت.
- يوم العمل.
- الشفتات الناقصة.
- الكاش المتوقع والموازنة.
- صلاحيات وتزامن الإغلاق.

### النظام 6: البيع والفواتير والبيع السريع

**حالة أساس القراءة المنجز:** اكتملت قائمة المبيعات والتفاصيل والبنود وملخص يوم العمل عبر API معزول لا يكشف التكلفة أو الربح. تبقى عملية البيع والتحصيل كتطوير Idempotent مستقل.

- سلة البيع.
- التسعير والتكلفة والخصومات.
- الدفع والتحصيل.
- الفاتورة وPDF.
- منع الإرسال المكرر.
- الباركود وتجربة الهاتف.

### النظام 7: طلبيات التوريد

**حالة أساس قراءة طلبيات التوريد:** أضيفت القائمة والملخص والتفاصيل عبر API معزول، بينما تبقى عمليات الكتابة مغلقة لحين مراجعة المعاملات والصلاحيات.

- الإنشاء والمراجعة والاستلام.
- حالات الطلب.
- المنتجات والتكلفة.
- إضافة المخزون.
- الرفض والإرجاع والملاحظات.
- المستندات وPDF.

### النظام 8: النقل المخزني

**حالة أساس قراءة النقل المخزني:** أضيفت القائمة والملخص والتفاصيل عبر API معزول حسب المتجر المشارك وأيام العمل، بينما تبقى عمليات الكتابة مغلقة لحين مراجعة الأثر المخزني وIdempotency.

- الإرسال والاستلام والرفض والإلغاء.
- يوم العمل للمرسل والمستلم.
- مطابقة المنتجات.
- حركة المخزون والتكلفة.
- الإشعارات والتقرير.
- Idempotency عند القبول أو الرفض.

### النظام 9: الجرد

**حالة الحفظ المرحلي المنجز:** أضيفت قراءة جلسات الجرد وتفاصيلها وحفظ مسودة المحاسب عبر API مع عزل الحساب والمتجر، وIdempotency، وقفل السجلات، ونسخة لاكتشاف التعارض. لم يفتح إرسال النتيجة أو اعتماد الفروقات أو تعديل المخزون من تطبيق الهاتف.

- إنشاء الجلسة واختيار المنتجات.
- مسودة المحاسب.
- الحفظ المرحلي.
- المراجعة وإعادة العد.
- الاعتماد وحركة المخزون.
- أول تجربة Offline مسموحة لمسودة غير معتمدة.

### النظام 10: الموظفون والمحاسبون

**حالة دليل الأفراد المنجز:** أضيفت قراءة دليل الموظفين والمحاسبين وملخص الحالات عبر API معزول حسب الحساب والمتجر، مع تقليل البيانات حسب دور القارئ. بقيت الرواتب والسلف والمديونيات والتحصيلات والنقل وتعديل الحسابات والصلاحيات خارج Mobile API.

- الحسابات والأدوار والمتاجر.
- الرواتب والسلف والمديونيات والتحصيلات حسب الموجود.
- نقل الموظف أو المحاسب.
- سجل العمليات والصلاحيات.
- حماية الخصوصية في API والجهاز المحلي.

### النظام 11: المصروفات والاستهلاك الداخلي والعمليات المالية المساندة

**حالة أساس القراءة والتدقيق المنجز:** أضيفت قراءة المصروفات والاستهلاك الداخلي ومشتريات المالك وملخصاتها ضمن فترة محاسبية محدودة، مع عزل المتجر وتقليل البيانات حسب الدور. بقي الإدخال والتعديل والحذف والاعتماد المالي والعمل Offline مغلقًا.

- الإدخال والمراجعة.
- الربط بالشفت والمتجر ويوم العمل.
- المرفقات والملاحظات.
- التقارير والتدقيق.
- منع Offline للاعتماد المالي.

### النظام 12: التقارير وPDF

**حالة الأساس المنجز:** أضيف سجل تقارير Mobile API، وملخص التقرير الشهري من الخدمة المرجعية نفسها، وروابط تنزيل PDF موقعة قصيرة العمر للمالك، مع عزل المتجر ومنع Cache وOffline. التقارير الثقيلة المؤجلة عبر Queue تبقى مرحلة تشغيل مستقلة.

- تعريف مصدر كل رقم.
- التاريخ المعتمد.
- الفلاتر والتقسيم.
- تشغيل التقارير الثقيلة عبر Queue عند الحاجة.
- روابط تنزيل آمنة ومؤقتة للتطبيق.
- مقارنة التقرير مع البيانات المصدرية.

### النظام 13: الاشتراكات والإدارة والأمن

**حالة أساس القراءة والتدقيق المنجز:** أضيفت نظرة حوكمة للمالك تشمل حالة الحساب والاشتراك والحدود والاستخدام، وسجل الاشتراكات، وجلسات الأجهزة، وسجل تدقيق منقح. بقي التجديد وتغيير الخطة والتعليق والصلاحيات وإعدادات الأمن خارج Mobile API.

- الخطط والحدود.
- حالة الحساب والمتجر.
- مركز القيادة الأمنية.
- السجلات والتنبيهات.
- إعدادات النظام عالية الحساسية.

### النظام 14: الهوية ومركز التحكم

**حالة العقد المشترك المنجز:** أضيف عقد Design Tokens ذي نسخة وبصمة تحقق للوضعين المظلم والفاتح، والخط والاتجاه والشعار وألوان الحالات، ويستهلكه Flutter دون تغيير واجهات Blade. بقي Publish وRollback معطلين حتى بناء سجل إصدارات ومعاينة بصرية واعتماد مستقل.

- Design Tokens.
- الوضعان المظلم والفاتح.
- الشعار والألوان المسموحة.
- Preview وPublish وRollback.
- عقد مشترك يستهلكه الويب وFlutter.

## قاعدة الانتقال بين الأنظمة

لا ننتقل من نظام إلى التالي حتى يحقق النظام الحالي:

- اختبارات السلوك القديم والجديد.
- عدم وجود Migration مدمرة.
- نجاح المقارنة على Staging.
- نجاح Pilot محدود.
- عدم ظهور فروقات بيانات.
- وجود مراقبة وخطة رجوع.
- توثيق ما تم وما أجل ولماذا.

- اختبارات ترحيل قاعدة البيانات والرجوع.

# المرحلة 3: بناء PWA الأساسية

**الحالة: منفذة في الأساس البرمجي.** اكتمل Manifest العربي والاختصارات، Worker بإصدار بناء، Offline shell آمن، دورة تحديث تنتظر حفظ المسودة، ومنع Cache للبيانات الخاصة. تبقى بوابة القبول الفعلية على أجهزة أندرويد.

## 3.1 قابلية التثبيت

- Web App Manifest عربي وRTL.
- اسم قصير واسم كامل.
- أيقونات معتمدة بكل الأحجام.
- `display: standalone`.
- `start_url` آمن.
- Theme وBackground من الهوية المعتمدة.
- اختصارات للعمليات الأكثر استخدامًا.

## 3.2 Service Worker

تعتمد استراتيجية Cache حسب نوع المورد:

| المورد | الاستراتيجية |
| --- | --- |
| CSS/JS والخطوط والأيقونات المرقمة | Cache First مع إصدار البناء |
| التنقل العام | Network First مع Offline fallback |
| بيانات غير حساسة قصيرة العمر | Stale While Revalidate عند الحاجة |
| العمليات المالية والمخزنية | Network Only |
| صفحات التقارير والبيانات الحساسة | عدم التخزين إلا بقرار صريح |

## 3.3 دورة التحديث

- اكتشاف نسخة Service Worker الجديدة.
- إظهار تنبيه «يتوفر تحديث» بدل استبدال الصفحة أثناء الإدخال.
- تطبيق التحديث بعد حفظ المسودة أو موافقة المستخدم.
- تنظيف Cache القديم.
- تسجيل إصدار الواجهة في تقارير الأخطاء.

## 3.4 تجربة الهاتف

- مراجعة كل صفحة ذات أولوية على أحجام الهاتف.
- منع الاعتماد على Hover.
- جعل الحقول والأزرار مناسبة للمس.
- تحويل الجداول غير العملية إلى بطاقات أو عرض مختصر.
- منع اختفاء الحقول خلف لوحة المفاتيح.
- حفظ موضع المستخدم والمسودة عند الرجوع.
- Skeleton loading وحالات فارغة وأخطاء واضحة.

## بوابة القبول

- التطبيق قابل للتثبيت ويعمل في وضع مستقل.
- Offline shell يعمل دون كشف بيانات مستخدم سابق.
- التحديث لا يفقد نموذجًا مفتوحًا.
- اختبارات Lighthouse ليست المعيار الوحيد؛ تنجح الرحلات الفعلية على أجهزة أندرويد ضعيفة ومتوسطة.

# المرحلة 4: التخزين المحلي وOffline

**الحالة: منفذة لمسودة الجرد المسموحة فقط.** أضيف Outbox في IndexedDB مفصول بالحساب والمتجر، مع Idempotency وحالات queued/sending/failed/conflict، وحدود حجم وعدد ومحاولات، ومزامنة عند عودة الاتصال وتنظيف كامل عند الخروج. بقيت جميع العمليات المالية والمخزنية المعتمدة محظورة Offline.

## 4.1 هل نستخدم قاعدة داخلية؟

نعم، لكن حسب المنصة:

- **PWA:** تستخدم IndexedDB للبيانات المنظمة والمسودات. لا يستخدم `localStorage` للبيانات الكبيرة أو طوابير المزامنة.
- **Flutter:** تستخدم SQLite عبر طبقة Repository، أو محرك محلي موثوق مبني عليها، مع تشفير القيم الحساسة عند الحاجة.

القاعدة المحلية ليست نسخة مستقلة من قاعدة Laravel، بل Cache ومسودات وطابور عمليات محدود.

## 4.2 تصنيف البيانات

### يسمح محليًا

- إعدادات العرض.
- آخر بيانات مرجعية يحتاجها المستخدم.
- مسودات الجرد غير المعتمدة.
- مسودة نقل لم ترسل.
- فلاتر البحث.
- آخر مزامنة.
- Outbox metadata دون أسرار.

### يمنع اعتماده Offline

- بيع نهائي.
- تحصيل أو مصروف مالي.
- إغلاق شفت.
- قبول أو رفض نقل.
- اعتماد جرد.
- تعديل مباشر للمخزون.
- حذف أو اعتماد طلب توريد.

## 4.3 نموذج المزامنة

كل مسودة أو أمر قابل للإرسال يحمل:

- `local_id`.
- `idempotency_key`.
- نوع العملية.
- وقت الإنشاء المحلي.
- إصدار البيانات المصدرية.
- الحالة: draft، queued، sending، synced، conflict، failed.
- عدد المحاولات.
- آخر خطأ مفهوم للمستخدم.

## 4.4 التعارض

لا نطبق Last Write Wins على المخزون أو المال. عند التعارض:

1. يوقف الاعتماد.
2. يجلب الخادم أحدث نسخة.
3. يوضح للمستخدم ما تغير.
4. يطلب مراجعة وإرسالًا جديدًا.

## 4.5 تنظيف البيانات

- حذف Cache المستخدم عند تسجيل الخروج.
- فصل قاعدة كل حساب/متجر منطقيًا.
- مدة صلاحية لكل نوع بيانات.
- حد أعلى للحجم.
- عدم نسخ التقارير المالية كاملة دون ضرورة.

## بوابة القبول

- انقطاع الشبكة لا يفقد مسودة مسموحة.
- عودة الشبكة لا تكرر العملية.
- تبديل المستخدم لا يعرض بيانات المستخدم السابق.
- التعارض يظهر للمستخدم ولا يعدّل المخزون بصمت.

# المرحلة 5: الأداء والضغط وقاعدة البيانات

## 5.1 الرصد قبل التحسين

تقاس المؤشرات التالية:

- p50 وp95 وp99 لزمن الاستجابة.
- معدل أخطاء 4xx و5xx.
- الاستعلامات البطيئة.
- عدد الاستعلامات لكل Endpoint.
- Queue lag.
- CPU والذاكرة والقرص.
- الاتصالات بقاعدة البيانات.
- Cache hit rate.
- حجم الاستجابات.
- زمن البحث.

## 5.2 تحسين Laravel

- إزالة N+1 باستخدام eager loading محدد الأعمدة.
- Pagination لكل قائمة كبيرة.
- نقل PDF والإشعارات والتقارير الثقيلة إلى Queue.
- Cache للبيانات المرجعية الآمنة فقط.
- عدم Cache الأرصدة الحساسة دون سياسة invalidation واضحة.
- ضغط الاستجابات والأصول.
- Timeouts وحدود واضحة للخدمات الخارجية.
- Health checks للويب والـQueue وقاعدة البيانات والتخزين.

## 5.3 تحسين قاعدة البيانات

- فهارس مركبة حسب `store_id` والحالة والتاريخ المستخدمة فعليًا.
- مراجعة `EXPLAIN` للاستعلامات البطيئة.
- منع `SELECT *` في API.
- أرشفة أو Partitioning فقط بعد إثبات الحاجة.
- Connection pooling إذا أثبت الحمل الحاجة.
- نسخ احتياطي مجرب بالاسترجاع، لا مجرد ملف Backup.

## 5.4 اختبارات الحمل

سيناريوهات واقعية:

- دخول عدد كبير من المحاسبين بداية اليوم.
- بحث منتجات متزامن.
- مبيعات متزامنة على المنتج نفسه.
- وصول إشعارات جماعية.
- إنشاء تقارير شهرية.
- نقل وجرد متزامنان.

## بوابة القبول

توضع SLOs رقمية بعد قياس Staging، ثم لا يطلق الإصدار إذا تجاوز p95 أو معدل الخطأ الحدود المتفق عليها.

# لوحة متابعة الخارطة

لكل مهمة تسجل الحقول التالية:

| الحقل | الوصف |
| --- | --- |
| المعرف | مثل `PWA-03` أو `API-12` |
| المسار | PWA، API، Flutter، Security، Performance، Design |
| الهدف | النتيجة التشغيلية، لا اسم الملف فقط |
| المالك | المسؤول عن القرار والتنفيذ |
| الحالة | Backlog، Ready، In Progress، Review، Done، Blocked |
| الاعتماديات | المهام التي يجب أن تسبقها |
| المخاطر | بيانات، صلاحيات، تزامن، أداء |
| الاختبارات | Unit، Feature، Contract، E2E، Load |
| Feature Flag | اسم العلم أو غير مطلوب |
| خطة الرجوع | كيفية تعطيلها دون فقد البيانات |
| معيار القبول | شرط قابل للقياس |

## قواعد إدارة العمل

- لا توجد أكثر من مرحلة بنيوية كبيرة قيد التنفيذ بلا مالك واضح.
- لا تنتقل المهمة إلى Done لمجرد اكتمال الكود؛ يجب اكتمال الاختبار والتوثيق والمراقبة.
- كل Sprint يحتوي أعمال منتج وأعمال دين تقني وأعمال مراقبة.
- تسجل القرارات الكبيرة في ADR ولا تعاد مناقشتها دون معلومة جديدة.
- تراجع الخارطة كل أسبوعين، والمخاطر شهريًا.

# أول حزمة عمل مقترحة

لا تبدأ الحزمة الأولى بكتابة Service Worker مباشرة. تبدأ بالترتيب التالي:

1. جرد الصفحات والرحلات والأدوار.
2. تصنيف العمليات Offline/Online.
3. تدقيق الإشعارات والأجهزة.
4. قياس البحث والاستعلامات الأكثر استخدامًا.
5. إضافة مراقبة أساسية وRequest IDs.
6. تصميم عقد `/api/v1/me` و`/api/v1/app-config` دون ربط Flutter بعد.
7. إعداد Manifest والأيقونات وOffline shell تجريبي.
8. اختبار PWA على أجهزة حقيقية.
9. اختيار رحلة واحدة للمسودة المحلية، ويفضل الجرد غير المعتمد.
10. مراجعة النتائج قبل توسيع النطاق.

# قرار التخزين المحلي النهائي

- نعم لقاعدة داخلية في PWA وFlutter.
- لا لنسخة محلية مستقلة من النظام المالي أو المخزون.
- PWA تستخدم IndexedDB.
- Flutter تستخدم SQLite.
- الاعتماد النهائي للعمليات الحساسة يبقى Online ومن Laravel.
- كل إرسال قابل للتكرار يستخدم Idempotency Key.
- كل تعارض حساس يتطلب مراجعة، ولا يحل تلقائيًا.

# تعريف النجاح النهائي

تنجح الخارطة عندما يصبح لدينا:

- ويب وPWA وFlutter يستخدمون Backend واحدًا.
- منطق العمل غير مكرر.
- تجربة هاتف سريعة وقابلة للتثبيت.
- مسودات آمنة عند انقطاع الشبكة.
- إشعارات موثوقة بروابط عميقة.
- بحث سريع قابل للقياس.
- قاعدة بيانات مراقبة ومفهرسة وفق الاستخدام.
- مركز هوية موحد بإصدارات ورجوع آمن.
- إطلاق تدريجي يمكن إيقافه دون خسارة بيانات.

# تحديث التنفيذ — 2026-09-25

أُنجز أساس PWA النصي الآمن: Manifest عربي RTL، وأيقونة SVG واحدة بدل ملفات PNG
الثنائية، وOffline shell عامة، وService Worker يستبعد المسارات الخاصة والعمليات
التعديلية من التخزين، وApp Context محمي بالجلسة مع Request ID. تستخدم مسودة جرد
المحاسب الآن IndexedDB مع ترحيل مسودة `localStorage` القديمة والتحقق من إصدار
الخادم، بينما تبقى المزامنة التلقائية وPush subscription وToken الخاص بـFlutter
خارج هذه الدفعة.

بدأت المرحلة 4A بحوكمة التخزين المحلي: عزلت مسودات الجرد حسب الحساب والمتجر،
وأضيفت حدود للحجم والعدد، وترقية لسجلات IndexedDB القديمة، وتنظيف لمسودات الحساب
الحالي عند تسجيل الخروج. لا تتضمن هذه الخطوة Outbox أو Background Sync ولا تغير
اعتماد الجرد أو المخزون؛ الانتقال إلى الإرسال المؤجل يبقى مشروطًا بعقد Idempotency
ومعالجة تعارض معتمدة في الخادم.

بدأت كذلك مرحلة Backend المشتركة بعقد Idempotency دائم ومخزن في قاعدة البيانات
لطلبات API التعديلية. فُعّل العقد أولًا على القراءة والإخفاء في مركز الإشعارات
كمرحلة منخفضة المخاطر، مع إعادة الاستجابة المكتملة وعزل المفتاح حسب الحساب وتنظيف
السجلات المنتهية. لم يُفعّل بعد على أي عملية مالية أو مخزنية.

اكتمل أساس عقد API v1 للجلسة الحالية: غلاف موحد للنجاح والخطأ، وإصدار صريح، ورقم
تتبع، وHeaders تمنع التخزين، وأكواد مستقرة لأخطاء التحقق والجلسة والصلاحيات والحد
المؤقت. أضيف عميل PWA مركزي لا يعيد Mutation تلقائيًا ولا يخزنها Offline. كان
هذا العقد أساس جلسة الويب، ثم بني فوقه نطاق Bearer للأجهزة في الخطوة التالية.

بدأ نطاق الأجهزة للمرحلة المشتركة: أضيفت Bearer Tokens مجزأة وقابلة للإبطال،
وجلسات أجهزة محدودة، وAbilities، وفحص موحد لحالة المالك والمحاسب والمتجر والاشتراك،
ومسارات `/me` وApp Config والمتاجر والأجهزة والإشعارات. بقي النطاق Read-focused
دون مبيعات أو شفتات أو تحصيلات أو نقل أو اعتماد جرد، تمهيدًا لاختبار عميل Flutter
تجريبي قبل فتح العمليات الحساسة.

مرجع التشغيل والاختبار: [`تشغيل-PWA-الأساسية.md`](تشغيل-PWA-الأساسية.md).
