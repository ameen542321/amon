# النظام 01: تدقيق المصادقة والمستخدمين والصلاحيات

## حالة الوثيقة

- النوع: تدقيق أولي قبل أي إصلاح.
- النطاق: الدخول والخروج، الحراس، الصلاحيات، استعادة كلمة المرور، المسارات العامة، والملفات الخاملة المرشحة.
- قاعدة البيانات: لم تعدل، ولم تنفذ Migration أو أمر بيانات.
- القرار: لا يحذف ملف أو دالة ولا يصلح منطق حساس قبل اعتماد النتائج وإضافة اختبارات حماية.

## قواعد العمل المعتمدة

1. مراجعة الدوال الموجودة قبل إنشاء أي دالة جديدة.
2. تفضيل إعادة الاستخدام أو التوحيد على إضافة طبقة مكررة.
3. حذف التعليقات والكود الميت بعد إثبات عدم الاستخدام بالبحث والمسارات والاختبارات.
4. حذف الملف الخامل فقط في Commit مستقل قابل للرجوع.
5. عدم حذف Middleware قديمة لمجرد عدم ظهورها في Routes قبل فحص الاستدعاء الديناميكي والاختبارات والوثائق.
6. إبلاغ صاحب المشروع بأي ثغرة أو خطر قبل الإصلاح.
7. عدم تعديل قاعدة البيانات الحقيقية.
8. أي واجهة تمس النظام تراجع وفق `docs/الهوية-البصرية-للمشروع.md` ودون CSS داخل Blade.

## ما يعمل جيدًا ويجب الحفاظ عليه

- تسجيل الدخول يجرب حارس المحاسب ثم حارس الويب.
- يوجد Rate Limiting مركب من البريد وIP مع تسجيل أحداث الفشل والتقييد.
- يعاد توليد Session ID بعد نجاح الدخول.
- يمنع تداخل حارسي الويب والمحاسب في الجلسة نفسها.
- تسجيل الخروج يبطل الجلسة ويعيد CSRF token.
- Reset Password يخزن الرمز مشفرًا، يفحص انتهاءه، يقفل السجل داخل Transaction، ويحذفه بعد الاستخدام الناجح.
- مسارات المالك والمحاسب الأساسية تستخدم الحارسين الموحدين.
- `UnifiedStoreGuard` يتحقق من ملكية المتجر وحالته في المسارات التي تستخدم `store.check`.
- توجد حماية عامة من المصادر المحظورة وحماية من تكرار الطلبات التعديلية.

## نتائج أمنية تحتاج قرارًا قبل الإصلاح

### SEC-01 — حرج: مسارات إرسال Push الإدارية خارج مجموعة حماية الأدمن

في `routes/admin.php` يوجد مسارا GET وPOST للإشعارات العامة قبل مجموعة `web + auth + is.admin`. حسب تعريف المسار الظاهر لا تحميهما مجموعة الأدمن المحيطة، وقد يسمح ذلك بالوصول غير المصرح إلى صفحة الإرسال أو تنفيذ الإرسال بحسب حماية Controller الداخلية.

**الإجراء المقترح:**

- فحص Controller وأي Authorization داخلي.
- إضافة اختبار يثبت أن الضيف والمالك والمحاسب يحصلون على منع.
- نقل المسارين داخل مجموعة الأدمن أو إضافة Middleware صريحة.
- لا ينفذ الإصلاح قبل اعتماد صاحب المشروع لأنه يغير صلاحيات وصول فعلية.

### SEC-02 — عالٍ: رابط تقارير عام يعتمد على اسم الملف فقط

المسار `/view-report/{filename}` غير محمي، ويتحقق من سلامة المسار والامتداد لكنه لا يتحقق من هوية المستخدم أو ملكيته للتقرير. منع Path Traversal جيد، لكن من يعرف اسم ملف صالح قد يستطيع قراءته.

**الإجراء المقترح:**

- حصر مولدات هذه الملفات وطريقة تسمية الملفات ومدة بقائها.
- استبداله برابط موقّع قصير العمر أو مسار محمي يتحقق من مالك التقرير.
- إضافة اختبار يمنع مستخدم متجر آخر والضيف.

### SEC-03 — متوسط/عالٍ: فحص بريد الموظف مسار عام وقابل لتعداد الحسابات

المسار `/employees/check-email` خارج مجموعة المالك ويعيد `exists: true/false` عن بريد المحاسب، ما يمكن أن يكشف وجود الحسابات ويستعمل للتعداد.

**الإجراء المقترح:**

- نقله داخل حارس المالك.
- إضافة Rate Limit.
- التحقق من أن الغرض التشغيلي لا يحتاج كشفًا عامًا.
- توحيد الرد إذا استعمل في سياق تسجيل عام مستقبلًا.

### SEC-04 — متوسط: رسالة «نسيت كلمة المرور» تكشف وجود البريد

`ForgotPasswordController` يعيد خطأ صريحًا عند عدم وجود المستخدم. هذا يسمح بتعداد عناوين الملاك.

**الإجراء المقترح:** إرجاع رسالة عامة موحدة سواء وجد البريد أم لا، مع إبقاء الإرسال الفعلي للمستخدم الموجود فقط.

### SEC-05 — متوسط: جلسة الدعم تتجاوز فحوص الحالة والمتجر عمدًا

الحراس الموحدة تسمح لجلسة الدعم بتجاوز بعض حالات الإيقاف والاشتراك والمتجر. هذا قد يكون مطلوبًا للدعم، لكنه امتياز مرتفع ويحتاج:

- مدة قصيرة.
- سجل بدء/انتهاء.
- سبب وتذكرة مرتبطة.
- إعادة تحقق للأفعال الحساسة.
- مؤشر واضح في كل صفحة.
- منع أو تأكيد مضاعف للعمليات المالية والمخزنية أثناء الدعم.

## مشكلات وظيفية أو اتساق محتملة

### AUTH-01 — خطأ محتمل في `UnifiedStoreGuard` مع حارس المحاسب

بعد التأكد من `accountant` guard، يستخدم الفرع `auth()->user()->store_id` من الحارس الافتراضي بدل `auth('accountant')->user()`. إذا لم توجد جلسة web موازية فقد تكون النتيجة null ويحدث خطأ عند الوصول إلى `store_id`.

**قبل الإصلاح:** نضيف اختبار محاسب يدخل مسارًا يحمل `{store}` دون جلسة web.

### AUTH-02 — حساب محاسب بلا مالك قد يتجاوز فحص المالك

`UnifiedAccountantGuard` ينفذ فحص حالة واشتراك المالك فقط داخل `if ($owner)`. الحساب اليتيم يستمر بعدها إذا كان المتجر صالحًا. يجب تقرير السياسة: الرفض الآمن غالبًا هو الأنسب.

### AUTH-03 — اختلاف جدول Password Broker عن التنفيذ الفعلي

`config/auth.php` يشير إلى `password_reset_tokens` بينما Controllers والمخطط الموجود يستخدمون `password_resets`. التدفق اليدوي قد يعمل لأنه لا يستخدم Broker، لكن الإعداد مضلل وأي كود جديد يعتمد Broker قد يفشل.

**القرار المطلوب:** إما توحيد التنفيذ على Broker الرسمي بترحيل آمن، أو تصحيح الإعداد ليعكس الجدول الحالي دون لمس البيانات بعد اختبار كامل.

### AUTH-04 — استعادة كلمة المرور تغطي User فقط

يوجد Broker باسم `accountants`، لكن `ForgotPasswordController` و`ResetPasswordController` يبحثان في `User` فقط. يجب تحديد هل المحاسب يستعيد بنفسه أم عبر المالك. لا ننشئ مسارًا جديدًا قبل اعتماد السياسة.

### AUTH-05 — بريد مكرر بين User وAccountant

الدخول يبحث عن User أو Accountant لفحص التعليق، ثم يحاول تسجيل المحاسب أولًا. إذا سمحت قاعدة البيانات بالبريد نفسه في الجدولين فقد يصبح السلوك ملتبسًا. يلزم تدقيق القيود والبيانات على نسخة آمنة، دون تعديل الإنتاج.

### AUTH-06 — Middleware تغير بيانات الاشتراك أثناء طلب قراءة

`UnifiedOwnerGuard` و`CheckSubscriptionActive` يستطيعان منح ثلاثة أيام وتحديث الحالة إذا كان تاريخ الاشتراك فارغًا. تغيير البيانات داخل Middleware أثناء GET يجعل السلوك خفيًا ومكررًا.

**المقترح:** بعد تثبيت السلوك بالاختبارات، ينقل منح الفترة التجريبية إلى إنشاء الحساب أو خدمة اشتراك صريحة، دون تغيير بيانات الموجودين تلقائيًا.

### AUTH-07 — حالات `active` و`suspended` غير موحدة

بعض الحراس تفحص `status !== active` وبعضها يفحص `status === suspended`. إذا وجدت حالات أخرى ستكون النتيجة مختلفة. يلزم جرد القيم الفعلية ثم اعتماد سياسة واحدة.

### AUTH-08 — مسارات Logout مكررة وبأسماء مختلفة

يوجد Logout عام وLogout للمالك وLogout للمحاسب، وكلها تستدعي الدالة الشاملة نفسها. قد يكون ذلك مطلوبًا للتوافق مع الواجهات، لكنه مرشح للتوحيد بعد حصر كل الروابط والاختبارات، لا بإنشاء دالة Logout إضافية.

## دوال وملفات خاملة مرشحة — لا تحذف بعد

### كود ميت واضح داخل ملف مستخدم

- نسخة كاملة معلقة من دالة `login()` داخل `Auth/LoginController.php`.
- Imports وتعليقات قديمة تحتاج Pint وتنظيفًا بعد تثبيت الاختبارات.

يمكن حذف الكود المعلق دون أثر تشغيلي بعد اجتياز الاختبارات، لأنه ليس مسار رجوع صالحًا داخل المصدر.

### Middleware aliases لا يظهر لها استخدام في Routes الحالية

المرشحون الأوليون:

- `subscription.active` → `CheckSubscriptionActive`.
- `store.active` → `CheckStoreStatus`.
- `store.access` → `CheckStoreAccess`.
- `check.suspended` → `CheckUserSuspended`.
- `store.master` → `UnifiedStoreGuard` باسم Alias إضافي.
- `redirect.dashboard` → `RedirectIfAuthenticatedToDashboard`.
- `plan.limit` → `CheckPlanLimit`.
- `SubscriptionWarning` كملف مستقل؛ التحذير منفذ أيضًا داخل `UnifiedOwnerGuard`.
- `RedirectActiveUser` غير مسجل حاليًا وAlias الخاص به معلق.

### شروط الحذف

لا يحذف أي مرشح حتى تنفذ الخطوات التالية:

1. `route:list` في بيئة مكتملة dependencies.
2. بحث PHP وBlade وconfig والاختبارات عن الاسم واسم الـAlias.
3. مراجعة الاستدعاءات الديناميكية والحزم.
4. اختبارات Feature للحارس الموحد البديل.
5. Commit حذف مستقل.
6. مراقبة Staging ثم الإنتاج.

## ملاحظة عن Admin guard

`config/auth.php` يعرّف `admin` provider باستخدام `App\Models\Admin`، بينما لا يظهر Model بهذا الاسم في الفحص الأولي، والنظام الفعلي يبدو أنه يستخدم `User` بدور `admin` عبر web guard. كما تستدعي دالة Logout حارس `admin`.

هذا إعداد خامل أو غير مكتمل مرشح للتنظيف، لكن يجب أولًا فحص إعدادات الإنتاج والـseeders وجميع مسارات الدعم. لا ننشئ Model جديدًا لمجرد إرضاء config إذا لم يكن النظام يحتاجه.

## مراجعة الاستايل والهوية البصرية لنظام المصادقة

قبل تعديل صفحات الدخول والاستعادة:

- قراءة المرجع `docs/الهوية-البصرية-للمشروع.md`.
- إبقاء Cairo والـRTL.
- منع `<style>` و`style=""` داخل Blade.
- استعمال `ui-*` والمكونات المركزية.
- اختبار الوضعين المظلم والفاتح.
- اختبار الهاتف ولوحة المفاتيح ورسائل Validation.
- عدم تغيير نصوص أمنية أو إخفاء حالة مهمة بهدف التجميل.
- أخذ Screenshot عند تنفيذ تغيير مرئي قابل للتشغيل.

## الرأي في Livewire

### القرار المقترح: استخدام انتقائي، وليس تحويل المشروع كله

Livewire مفيد في صفحات ويب داخلية تحتاج تفاعلًا خادميًا سريعًا، مثل:

- فلاتر وقوائم الإدارة.
- Pagination وبحث بسيط متصل بالخادم.
- مودالات CRUD غير حساسة.
- مركز الإشعارات وحالة القراءة.
- شاشات إعدادات لا تحتاج Offline.

لا أوصي بجعله أساسًا للوظائف التالية:

- PWA Offline والمزامنة.
- API الذي سيخدم Flutter.
- البيع السريع عالي التفاعل.
- الجرد ذي المسودات المحلية.
- النقل أو الاعتماد المالي والمخزني الحساس.
- أي شاشة تحتاج مشاركة منطقها مع تطبيق Flutter.

### السبب

- Livewire يحسن تجربة Blade لكنه لا يغني عن API.
- يعتمد غالبًا على اتصال مستمر بالخادم؛ لذلك لا يحل Offline.
- كثرة المكونات الدقيقة قد تزيد الطلبات على الخادم بدل تقليلها.
- منطق العمل داخل Component سيؤدي إلى تكراره عند بناء Flutter إن لم يستدع Service مشتركة.
- يمكنه التعايش مع Alpine والهوية الحالية إذا استخدم بحدود واضحة.

### شروط إدخاله

1. لا يضاف قبل قياس الصفحة الحالية وتحديد المشكلة.
2. تجربة Pilot في صفحة واحدة منخفضة المخاطر.
3. Component رفيع يستدعي Service؛ لا يحتوي قواعد العمل نفسها.
4. تحديد debounce وlazy loading وpagination لمنع ضغط الخادم.
5. اختبارات Component وFeature وصلاحيات.
6. عدم إضافة CSS محلي داخل Blade أو Component.
7. عدم خلط Livewire وJavaScript اليدوي على DOM نفسه دون عقد واضح.
8. قياس عدد الطلبات وحجمها قبل وبعد.

### أول مرشح مناسب

مركز الإشعارات أو قائمة إدارية ذات فلاتر هو أفضل Pilot. لا نبدأ بصفحة البيع أو الجرد أو النقل.

## خطة العمل التالية بعد اعتماد التقرير

1. إضافة اختبارات وصول للمسارات الإدارية Push والتقارير العامة وفحص البريد.
2. إضافة اختبار `UnifiedStoreGuard` بحساب محاسب فقط.
3. إضافة اختبارات استعادة كلمة المرور وتعداد البريد.
4. استخراج قائمة Routes فعلية بعد توفير dependencies.
5. تقديم PR أمني صغير منفصل لأخطر نتيجة بعد موافقة المالك.
6. تنظيف الكود المعلق والملفات الخاملة في PR مستقل لاحق، لا داخل إصلاح الأمان.
7. تدقيق واجهات الدخول وفق الهوية في مهمة مستقلة بعد استقرار المنطق.

## قرار الإغلاق

هذا النظام **غير مغلق**. الوثيقة تدقيق أولي فقط، وتحتاج النتائج الأمنية إلى اعتماد وترتيب قبل تنفيذ الإصلاحات.

## دفعة الإصلاح الأمني الأولى

تم تنفيذ دفعة صغيرة لا تمس قاعدة البيانات بعد عرض النتائج:

- حماية مسارات إرسال Push والإشعارات الداخلية وجلسة الدعم وأرشيف الدعم بـ`auth:web` و`is.admin`.
- إضافة Rate Limit لمسارات إرسال الإشعارات.
- حماية فحص بريد الموظف بحارس المالك مع Rate Limit مع الحفاظ على الرابط والاسم الحاليين.
- حماية عرض تقرير المحاسب بحارس المحاسب. تبقى ملكية الملف داخل المتجر بند تدقيق لاحق قبل اعتبار النتيجة مغلقة بالكامل.
- توحيد رسالة طلب استعادة كلمة المرور لمنع كشف وجود البريد، وإضافة Rate Limit للمسار.
- تصحيح `UnifiedStoreGuard` ليقرأ المحاسب من `accountant` guard صراحة.
- إضافة اختبار عقد ثابت يمنع رجوع هذه المسارات إلى الحالة العامة دون حماية.

لم تحذف Middleware أو دوال في هذه الدفعة؛ حذف الخامل ينتظر `route:list` واختبارات Feature في بيئة مكتملة.
