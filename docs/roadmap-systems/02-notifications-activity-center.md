# النظام 02: تدقيق الإشعارات ومركز النشاط

## حالة الوثيقة

- النوع: تدقيق أولي قبل الإصلاح.
- النطاق: الإشعارات الداخلية، القراءة والإخفاء والحذف، رموز الأجهزة، OneSignal، البث، المسارات، الأداء، والاستعداد لـPWA وFlutter.
- قاعدة البيانات: لم تعدل، ولم تنفذ Migration أو عملية بيانات.
- التنفيذ: لا يصلح خطر أو يحذف مسار قبل اختبارات حماية وموافقة صاحب المشروع.

## الهدف التشغيلي

بناء مصدر إشعارات داخلي موثوق يخدم الويب وPWA وFlutter، بينما تكون Push قناة توصيل إضافية لا المصدر الوحيد. يجب أن يعرف النظام بدقة:

- من أنشأ الإشعار.
- نوع المستلم: مالك، محاسب، متجر، أو الجميع.
- من قرأ أو أخفى الإشعار.
- إلى أي شاشة يقود الإشعار.
- هل وصل Push أم فشل.
- هل أعيدت المحاولة.

## ما يعمل حاليًا ويجب الحفاظ عليه

- يوجد Model مركزي للإشعارات وService للإرسال.
- يدعم النظام مستهدفين من أنواع متعددة.
- توجد قنوات إشعار داخلي وOneSignal.
- توجد صفحات للمالك والمحاسب والإدارة.
- رموز الأجهزة تحفظ في جدول مستقل.
- الإشعار الداخلي يبقى موجودًا حتى إذا لم يصل Push.
- توجد بداية للبث عبر Event.
- إعدادات OneSignal منفصلة عن الكود.

## نتائج أمنية تحتاج معالجة قبل PWA

### NOTIF-SEC-01 — حرج: تعديل إشعار غير موجه للمستخدم

`show()` يتحقق من استحقاق المستخدم، لكن `toggle()` و`markSelected()` لا يقيدان الاستعلام بالإشعارات الموجهة للمستخدم. معرفة ID قد تسمح بتعديل `read_by` لإشعار لا يخص الحساب.

**المقترح:** إنشاء Query scope واحد يأخذ هوية المستلم ونوعه، واستخدامه في العرض والقراءة والتحديد والحذف.

### NOTIF-SEC-02 — حرج: تصادم معرفات المالك والمحاسب

الاستعلامات الحالية تعتمد غالبًا على وجود الرقم داخل `target_ids` دون ربطه دائمًا بـ`target_type`. إذا كان `User #5` و`Accountant #5` موجودين، فقد يرى أحدهما إشعار الآخر أو يغير حالة قراءته.

**المقترح:** هوية مستلم مركبة من النوع والمعرف، أو جدول recipients مستقل مستقبلًا. لا تنفذ Migration قبل خطة توسع متوافقة للخلف ومقارنة البيانات.

### NOTIF-SEC-03 — عالٍ: Redirect غير موثوق بعد الحذف

`delete()` يعيد التوجيه مباشرة إلى قيمة `redirect_to` القادمة من الطلب. إذا لم تكن مقيدة فقد تستخدم كـOpen Redirect.

**المقترح:** قائمة مسارات داخلية مسموحة أو رجوع آمن `back()`، مع اختبار يمنع الروابط الخارجية.

### NOTIF-SEC-04 — عالٍ: عمليات الإدارة ذات مسار حذف واسع

المسار الإداري `DELETE /admin/{id}` عام جدًا وقد يتعارض مع مسارات إدارية أخرى أو يلتقط معرفًا خارج سياق الإشعارات.

**المقترح:** حصره تحت `/admin/notifications/{id}` وإزالة المسار القديم بعد فحص الروابط.

### NOTIF-SEC-05 — متوسط: رموز الأجهزة وهوية الحارس

`DeviceTokenController` يستخدم `auth()->user()` من الحارس الافتراضي، ثم يفحص `role`. هذا لا يدعم المحاسب المسجل عبر `accountant` guard بصورة موثوقة. كما توجد تعريفات متكررة لمسار `/device-token` في ملفات Routes مختلفة.

**المقترح:** خدمة هوية موحدة للمستلم، ومسار واحد بأسماء واضحة لكل Guard أو API token مستقبلًا.

### NOTIF-SEC-06 — متوسط: بيانات Push على شاشة القفل

لا توجد سياسة مركزية واضحة تمنع إرسال تفاصيل مالية أو شخصية في عنوان ورسالة Push. يجب أن يكون Push مختصرًا، وتعرض التفاصيل بعد فتح التطبيق والتحقق من الصلاحية.

## مشكلات اتساق ومنطق

### NOTIF-LOGIC-01 — اختلاف دلالة `target_type`

يوجد استخدام للقيم المفردة والجمع مثل `user/users` و`accountant/accountants` و`store/stores`. بعض الدوال تدعم مجموعة منها فقط، ما قد يؤدي إلى إنشاء إشعار لا يظهر لمستلمه أو لا يبث.

### NOTIF-LOGIC-02 — `read_by` يجمع القراءة والإخفاء

الحقل نفسه يحتوي معرفات قرأت الإشعار وقيمًا مثل `hidden_by_5`. هذا يخلط حالتين مختلفتين، ويصعب الاستعلام والفهرسة والمزامنة مع Flutter.

### NOTIF-LOGIC-03 — Scope غير مقروء يعتمد `read_at`

يوجد Scope للعداد يستخدم `read_at`، بينما النموذج الفعلي يعتمد `read_by`. هذه دالة متعارضة أو خاملة ويجب حسم استخدامها قبل بناء API.

### NOTIF-LOGIC-04 — التنظيف يحدث أثناء القراءة وباحتمال عشوائي

`Notification::booted()` قد يحذف إشعارات قديمة عند مجرد استرجاع أي إشعار وباحتمال عشوائي. القراءة يجب ألا تملك أثر حذف خفي، كما أن هذا السلوك يصعب اختباره وقد يزيد الاستعلامات.

**المقترح:** نقل التنظيف إلى Command مجدول وموثق مع Dry Run وسياسة احتفاظ.

### NOTIF-LOGIC-05 — حذف الإشعار العام غير موحد

يوجد `delete()` و`remov()` بسلوكين مختلفين للإشعار العام والخاص، ومسارات المالك والمحاسب ليست متطابقة. يلزم عقد واحد: حذف عالمي للإدارة، وإخفاء شخصي للمستلم.

### NOTIF-LOGIC-06 — البيانات الإضافية لا تحفظ بوضوح

Model يسمح بحقل `data`، لكن مسار `NotificationService::send()` الحالي لا يمرر `data` عند الإنشاء. هذا يمنع Deep Links موثوقة ويشجع بناء الرابط من النص.

## مشكلات أداء وضغط خادم

### NOTIF-PERF-01 — بث «للجميع» يتوسع خطيًا

الإرسال العام يجلب جميع معرفات الملاك والمحاسبين ثم يطلق Event لكل حساب داخل نفس التنفيذ. مع نمو المستخدمين قد يطيل الطلب ويضغط الذاكرة والـQueue.

**المقترح:** Job مجزأ batches أو Channel عام مصرح، وفق متطلبات القراءة الفردية.

### NOTIF-PERF-02 — تعليم الكل كمقروء ينفذ تحديثًا لكل إشعار

`markAll()` و`markAllAsReadFor()` يحملان مجموعة ثم يحدثان كل سجل على حدة، ما يسبب N updates ويكبر حقل JSON المشترك.

### NOTIF-PERF-03 — عداد المحاسب يحمل النتائج إلى PHP

`unreadNotificationsCountForAccountant()` يجلب الإشعارات ثم يفلترها في الذاكرة. يجب حساب العدد في قاعدة البيانات بعد توحيد نموذج المستلمين.

### NOTIF-PERF-04 — OneSignal يعمل متزامنًا دون Timeout معلن

طلب HTTP الخارجي ينفذ داخل طلب المستخدم ولا يظهر Timeout أو Retry أو Queue أو سجل فشل. بطء OneSignal قد يبطئ لوحة الإدارة، وفشله يعيد `false` دون معلومات تشغيلية كافية.

### NOTIF-PERF-05 — التنظيف الاحتمالي داخل retrieved

كل استرجاع يحمل احتمال تشغيل استعلام إعدادات ثم حذف، وهو حمل غير متوقع يزداد مع قراءة القوائم.

## دوال ومسارات خاملة أو مكررة مرشحة

لا تحذف قبل الاختبارات:

- التعريفات المعلقة الكثيرة لمسارات الإشعارات في `routes/web.php`.
- Import لـ`OneSignalController` إذا ثبت عدم وجود Controller أو استعمال فعلي.
- Scope `unreadCountFor` الذي يعتمد `read_at` إذا لم يستدع في أي موضع.
- دالة `remov()` بعد توحيد الإخفاء والحذف.
- `notificationsForAccountant()` أو العدادات المتعددة بعد اعتماد Query موحد.
- تعريف `/device-token` المكرر بين `routes/web.php` و`routes/admin.php`.

## العقد المستهدف دون Migration أولًا

قبل تغيير Schema نبني طبقة توافق تقرأ الشكل الحالي وتوحد الهوية منطقيًا:

```text
RecipientContext
- type: user | accountant | admin
- id
- store_ids
```

ثم توحد العمليات:

```text
visibleTo(recipient)
unreadFor(recipient)
markRead(notification, recipient)
hide(notification, recipient)
```

لا توضع قواعد الصلاحية داخل Blade أو Livewire أو Flutter؛ تستدعي جميعها Service مشتركة.

## خطة الإصلاح المرحلية

### الدفعة A — إغلاق ثغرات الوصول دون Schema

1. إضافة اختبارات تمنع toggle/markSelected/delete لإشعار غير موجه.
2. منع Open Redirect.
3. توحيد استعلام الرؤية حسب النوع والمعرف بالقيم الحالية.
4. توحيد مسارات الحذف والإخفاء مع الحفاظ على التوافق مؤقتًا.
5. إصلاح هوية Device Token لكل Guard.

### الدفعة B — إزالة الآثار الخفية وتحسين الأداء

1. إلغاء الحذف العشوائي من `retrieved`.
2. إنشاء Command تنظيف مع Preview وScheduler.
3. Queue لإرسال OneSignal مع Timeout وRetry وسجل فشل.
4. تجزئة الإرسال العام.
5. قياس عدد الاستعلامات ووقت الإرسال والعداد.

### الدفعة C — الاستعداد لـPWA وFlutter

1. حفظ `data` منضبط يتضمن route key وresource id، لا URL عشوائيًا.
2. API للقائمة والعداد والقراءة والإخفاء.
3. Device registration باستخدام API token.
4. Deep Link يفتح التطبيق ثم يعيد التحقق من الصلاحية.
5. مزامنة آخر إشعار باستخدام cursor بدل إعادة القائمة كاملة.

### الدفعة D — نموذج بيانات مستقبلي إن أثبتت الحاجة

بعد قياس الحجم ووضع Migration توسعية فقط، يمكن نقل المستلمين والقراءة إلى جدول منفصل. يبقى JSON الحالي خلال فترة مقارنة، ثم يحذف لاحقًا بقرار مستقل وفق Expand → Migrate → Verify → Switch → Contract.

## Livewire

لا يستخدم في جوهر الإشعارات أو API أو Push. يمكن تجربته لاحقًا في قائمة الإدارة أو مركز الإشعارات على الويب فقط، بشرط أن يستدعي Service الصلاحيات نفسها وألا يصبح مصدرًا لمنطق لا يستطيع Flutter استخدامه.

## الهوية البصرية

عند تعديل صفحات الإشعارات:

- قراءة مرجع الهوية أولًا.
- استخدام بطاقات وتنبيهات وشارات `ui-*`.
- منع CSS داخل Blade.
- إظهار المقروء وغير المقروء بالنص والأيقونة، لا اللون وحده.
- دعم الهاتف والوضعين المظلم والفاتح.
- عدم عرض معلومات حساسة في Push أو شاشة القفل.

## بوابة إغلاق النظام الثاني

لا يعتبر نظام الإشعارات مكتملًا حتى:

- لا يستطيع حساب قراءة أو تعديل إشعار حساب آخر حتى مع تصادم IDs.
- يوجد مسار Device Token صحيح للمالك والمحاسب والتطبيق.
- Push في Queue وله Retry وTimeout وسجل فشل.
- لا توجد عمليات حذف أثناء القراءة.
- العدادات لا تحمل القوائم كاملة إلى الذاكرة.
- Deep Links تختبر الصلاحية عند الفتح.
- تنجح اختبارات Feature وLoad على Staging.
- لا تمس أي Migration بيانات الإنتاج دون الخطة التوسعية المعتمدة.
