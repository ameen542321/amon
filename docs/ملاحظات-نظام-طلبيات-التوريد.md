# ملاحظات نظام طلبيات التوريد

**آخر تحديث:** 2026-08-08  
**الصفة:** المرجع التشغيلي المختصر للتعديلات الحالية.  
**المراجع المكملة:** `docs/المواصفات-المعتمدة-لنظام-طلبيات-التوريد.md` و`docs/مراجعة-شاملة-لنظام-طلبيات-التوريد-2026-08-08.md`.

## 1. الدورة الحالية

1. ينشئ المحاسب أو المالك الطلبية من دون تغيير المخزون.
2. يراجع المالك البنود، ويستطيع إعادتها للتعديل أو للجرد.
3. الجرد مراجعة فقط؛ لا يضيف إلى المخزون ولا ينقص منه.
4. بعد الإرسال للمورد يؤكد المحاسب الكمية والنوع والسعر الفعلي.
5. يفتح المالك صفحة **مراجعة تأكيد الاستلام**. هذه الصفحة لا تنفذ اعتمادًا مخزنيًا.
6. بعد تأكيد المالك للاستلام تنتقل الطلبية إلى **الاعتماد المخزني**.
7. عند ضغط زر الاعتماد يقفل النظام المنتج، ويحفظ الكمية والتكلفة في تلك اللحظة، ثم يسجل الحركة.

## 2. تأكيد الاستلام

- المنتج ذو الوحدة الواحدة لا يظهر له حقل نوع الاستلام.
- منتج الطقم يعرض الطقم/الحبة مع عدد حبات الطقم.
- منتج الرول يعرض الرول/المتر مع طول الرول.
- لا يظهر نص «مطابق للتكلفة»؛ يظهر الفرق عند وجود زيادة أو نقصان فقط.
- المحاسب يسجل سعر المورد، والمالك وحده يقرر تحديث تكلفة المنتج.
- يظهر تعديل المحاسب على بطاقة المنتج.

## 3. الربط وإنشاء المنتج

- توجد نافذة واحدة تسمح بربط منتج موجود، أو إنشاء منتج بيع، أو منتج مشتريات مالك.
- يربط المنتج ببند الطلبية فور الحفظ.
- إنشاء منتج بيع يحفظ القسم، الأسعار، الحد الأدنى، الباركود، سعة الكرتون، الهالك، ونوع البيع الافتراضي.

## 4. الاعتماد المخزني

- يظهر تاريخ اعتماد المالك للجرد أعلى بطاقات الاعتماد.
- تظهر الكمية الآن، الكمية المستلمة، نوع المستلم، تكلفة الاستلام، والتكلفة التي ستعتمد.
- لا تظهر لقطة الجرد في هذه الصفحة.
- تحفظ `stock_quantity_before`، `stock_quantity_after`، `cost_price_before`، و`cost_price_after` داخل معاملة الاعتماد وبعد قفل المنتج.

## 5. أدوات الدعم التقني

تظهر فقط عند وجود جلسة دعم نشطة بصفة المالك:

1. **تصحيح الحالة:** يعرض الحالة الحالية، ويطلب الحالة الصحيحة. سبب التصحيح اختياري؛ إذا ترك فارغًا يحفظ النظام رقم تذكرة الدعم. يسجل التغيير في أحداث الطلبية، ولا ينفذ حركة مخزنية.
2. **الحذف النهائي:** متاح للدعم في جميع مراحل الطلبية، بما فيها المسودة، الجرد، الاستلام، الاعتماد، الإلغاء، وبعد الحذف العادي. يظهر في القائمة وفي بطاقة أدوات الدعم. يتطلب رمز الطلبية، أما السبب فاختياري ويستخدم رقم التذكرة عند تركه. يحذف الطلبية، البنود، الأحداث، ومحاولات الجرد. لا يحذف المنتجات، مشتريات المالك الناتجة، أو حركات المخزون التي نُفذت سابقًا.
3. يسجل الحذف في تذكرة الدعم مع معرفات المنتجات التي بقيت محفوظة.
4. يظهر زر **استعادة الطلبية** في القائمة للدعم التقني فقط.

## 6. ملاحظات الأمان

- مسارات الدعم لا تكتفي بإخفاء الأزرار؛ تتحقق في الخادم من جلسة دعم نشطة للمالك.
- تصحيح الحالة لا يضيف مخزونًا، لا ينشئ مشتريات، ولا يحذف بيانات اعتماد سابقة.
- لا تتيح نافذة التصحيح وضع الطلبية في «معتمدة وموردة»؛ هذه الحالة ينشئها الاعتماد المخزني الفعلي فقط.

## 7. خطة الإصلاح على مرحلتين

ينفذ كل إصلاح في مرحلتين منفصلتين:

1. **مرحلة الإثبات:** إضافة اختبارات تثبت السلوك المطلوب، والصلاحيات، وعدم تغيير المخزون قبل الاعتماد.
2. **مرحلة التنفيذ:** تطبيق الإصلاح المحدود، ثم تشغيل اختبارات الإثبات والفحوص البصرية قبل الانتقال للإصلاح التالي.

### الإصلاح المنفذ: الإرسال للمورد

- **مرحلة الإثبات:** تغطية حفظ المورد والانتقال والحدث معًا، وإعادة فحص حالة قاعدة البيانات، والتراجع الكامل عند عدم اكتمال مراجعة الجرد.
- **مرحلة التنفيذ:** نقل تحديث المورد وحالة الطلبية والحدث إلى معاملة واحدة مع `lockForUpdate`، وإنشاء تنبيه المحاسب بعد نجاح المعاملة فقط.

### الإصلاح الثاني: توحيد حالات الطلبية

- **مرحلة الإثبات:** إضافة اختبار للتسمية العربية، وعدم إظهار القيمة البرمجية للحالة غير المعروفة، ومطابقة خيارات الدعم مع الانتقالات المسموحة.
- **مرحلة التنفيذ:** إنشاء مرجع مركزي للتسميات والشارات وتصحيحات الدعم، واستخدامه في قائمة الطلبيات وصفحة الطلبية ونافذة الدعم.

### الإصلاح الثالث الشامل: الدورة والمتابعة والمستندات

- **مرحلة الإثبات:** تغطية الدورة من الإرسال للمورد إلى تأكيد المحاسب ومراجعة المالك والاعتماد المخزني، وإثبات عدم تغير المخزون قبل الاعتماد، واختبار حالات PDF ومنع محاسب من مستند طلبية محاسب آخر.
- **مرحلة التنفيذ:** إضافة فلتر المرحلة التشغيلية للمالك والمحاسب، وحفظ الفلاتر عند التنقل بين الصفحات، وتوحيد بوابة حالة PDF في الخادم.

#### قواعد المستندات بعد الإصلاح

1. مستند الطلبية متاح في المسودة أو بعد الإرسال فقط.
2. مستند الاستلام متاح من الإرسال حتى الاعتماد.
3. سجل الاعتماد المخزني متاح بعد الاعتماد فقط.
4. ورقة الجرد متاحة أثناء إعادة الجرد أو حفظ مسودته فقط.

### الإصلاح الرابع: التزامن والتنبيهات وPDF والصيانة

- أصبحت انتقالات اعتماد الجرد، الرفض، إعادة الفتح، رفض بنود الجرد، استعادة البند، والإلغاء تعيد فحص الحالة بعد قفل رأس الطلبية داخل transaction.
- وُحد إنشاء تنبيهات الطلبيات بعد commit في خدمة مستقلة.
- نُقل تجهيز PDF إلى خدمة مستقلة، وأزيل `style="..."` من القالب لصالح classes مجمعة في رأسه.
- أضيفت اختبارات PDF لطلبيات من 1 و20 و100 بند، واختبار إخفاء الأسعار، واختبارات صلاحيات لمسارات المحاسب.

## 8. بوابة القبول التي ينفذها صاحب المشروع

```bash
composer install --no-interaction --prefer-dist
php artisan migrate --force
php artisan test --testsuite=Unit --filter='PurchaseOrder|StorePurchaseOrder'
php artisan test --testsuite=Feature --filter=PurchaseOrder
npm ci
npm run test:visual
npm run build
CHROME_BIN=/path/to/chromium npm run test:contrast
find app/Modules/PurchaseOrders routes -type f -name '*.php' -print0 | xargs -0 -n1 php -l
```

بعد نجاح الأوامر، ينفذ قبول يدوي للوضعين المظلم والفاتح على عروض 360 و768 و1366، مع صور للقائمة، مراجعة الاستلام، الاعتماد المخزني، وأدوات الدعم.
