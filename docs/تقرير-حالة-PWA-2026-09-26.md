# تقرير حالة مشروع PWA

**تاريخ التقرير:** 2026-09-26  
**النطاق المعتمد:** إكمال PWA مع تأسيس Backend قابل لاستهلاك Flutter مستقبلًا، دون إنشاء تطبيق Flutter حاليًا.  
**مرجع القرار:** `docs/roadmap-current-scope.md`  
**النسخة البرمجية التي روجعت:** `01e4be8`

## 1. الخلاصة التنفيذية

وصل المشروع إلى **اكتمال الأساس البرمجي لـPWA**، ويشمل قابلية التثبيت، Service Worker، Offline shell، تحديثًا آمنًا، مسودة جرد محلية، Outbox محدودًا، مفاتيح تعطيل تشغيلية، وDeep Links آمنة للإشعارات. كما أصبح Backend مهيأ لعميل هاتف مستقبلي من خلال API v1 وجلسات أجهزة قابلة للإبطال وعقود استجابة وIdempotency وDesign Tokens مشتركة.

المشروع **ليس جاهزًا للإطلاق العام بعد**؛ المتبقي الآن تشغيلي واختباري بالدرجة الأولى: اختبار أجهزة Android فعلية، بوابة Staging، اختبار Push حقيقي، قياسات الأداء ووضع SLOs، اختبار حمل، مراقبة تشغيلية، ثم Pilot محدود دون فروقات بيانات.

لا يتضمن النطاق الحالي تطبيق Flutter أو ملفات Dart أو APK/IPA.

## 3. المنجز في PWA

### 3.1 التثبيت والـShell

- Manifest عربي RTL بوضع `standalone`.
- أصل SVG قابل للتدرج بدل الاعتماد على حزمة أيقونات ثنائية قديمة.
- Offline shell عامة لا تعرض بيانات خاصة.
- تسجيل Service Worker فقط في السياق الآمن أو localhost.
- Cache بإصدار بناء صريح.
- استبعاد API والطلبات الخاصة وعمليات التعديل من Runtime Cache.

### 3.2 التحديث الآمن

- اكتشاف Worker جديد والتحقق من نسخته.
- عدم تفعيل التحديث قبل تجهيز المسودات المفتوحة.
- مهلة محددة لتحضير التحديث.
- إيقاف التحديث عند فشل حفظ البيانات المحلية.
- إعادة تحميل واحدة بعد تغير Controller.

### 3.3 التخزين المحلي وOutbox

- IndexedDB بمخازن منفصلة للمسودات وOutbox.
- عزل السجلات بحسب الحساب والمتجر.
- حدود لحجم وعدد السجلات.
- تنظيف بيانات الحساب عند تسجيل الخروج.
- السماح حصريًا بمسودة الجرد في Outbox.
- Idempotency Key لكل إرسال مؤجل.
- حالات `queued` و`sending` و`failed` و`conflict`.
- حد للمحاولات وعدم اعتماد Last Write Wins.
- بقاء العمليات المالية واعتماد الجرد وتعديل المخزون Online فقط.

### 3.4 ضوابط الإطلاق والرجوع

توجد مفاتيح مستقلة ومفعلة افتراضيًا:

- `PWA_SERVICE_WORKER_ENABLED`
- `PWA_UPDATES_ENABLED`
- `PWA_OUTBOX_ENABLED`

يمكن تعطيل Service Worker أو التحديثات أو الإرسال المؤجل بشكل مستقل. تعطيل Outbox لا يحذف المسودة ولا يحولها إلى عملية معتمدة.

### 3.5 الإشعارات وDeep Links

- Inbox الداخلي هو المصدر الأساسي للإشعار.
- Push يرسل من خلال Queue بمحاولات وTimeout محددين.
- Push وInbox يشتركان في معرف الإشعار نفسه.
- مسار Deep Link موحد ورقمي ومحدود بمعدل طلبات.
- فحص ظهور الإشعار للمستلم قبل تغيير حالة القراءة أو إعادة التوجيه.
- توجيه كل دور إلى صفحة التفاصيل المحمية الخاصة به.
- منع الروابط الخارجية أو اختلاف البروتوكول أو النطاق أو المنفذ.

## 4. تأسيس Flutter المستقبلي المنجز

لا يوجد تطبيق Flutter حاليًا، لكن الأساس المشترك المتاح مستقبلًا يشمل:

- API v1 بعقد نجاح وخطأ موحد.
- Request ID ونسخة API وHeaders تمنع Cache الخاص.
- Bearer access tokens مجزأة وقابلة للإبطال.
- Refresh rotation وحدود عدد الأجهزة.
- Abilities لكل جلسة جهاز.
- Push subscriptions مرتبطة بجلسة الجهاز.
- Design Tokens ذات نسخة وبصمة تحقق.
- Idempotency للعمليات المؤهلة.
- موارد API للقراءة عبر الأنظمة الموثقة.
- بقاء Laravel المصدر الوحيد لمنطق العمل.

هذا التأسيس لا يعني بدء Flutter ولا يضيف التزامًا ببناء التطبيق في المرحلة الحالية.

## 5. ما لم يكتمل بعد

### 5.1 بوابة الأجهزة الفعلية

يلزم اختبار Chrome/Android على جهاز ضعيف وآخر متوسط على الأقل:

1. التثبيت من المتصفح.
2. الفتح من أيقونة الشاشة الرئيسية.
3. Offline shell بعد زيارة ناجحة.
4. تحديث من Build قديم إلى Build جديد مع نموذج مفتوح.
5. انقطاع الشبكة أثناء تحرير مسودة الجرد.
6. عودة الشبكة ومزامنة واحدة فقط.
7. تعارض نسخة الخادم دون تعديل صامت.
8. تسجيل الخروج ثم الدخول بحساب آخر دون تسرب مسودة.

### 5.2 بوابة Staging

- HTTPS صالح ونطاق مطابق لـ`APP_URL`.
- Queue worker دائم ومراقب.
- بيانات مصطنعة أو منزوعة الهوية.
- مفاتيح OneSignal خاصة بـStaging.
- اختبار Push حقيقي لكل من المالك والمحاسب والمدير.
- اختبار Deep Link بعد انتهاء الجلسة وبعد تسجيل الدخول.
- تجربة مفاتيح التعطيل الثلاثة وخطة استعادتها.

### 5.3 الأداء والمراقبة

ينقص التقرير التشغيلي الرقمي التالي:

- p50 وp95 وp99 للمسارات الرئيسية.
- معدل 4xx و5xx.
- زمن البحث وحجم استجابة API.
- عدد الاستعلامات واكتشاف N+1.
- Queue lag وفشل Jobs.
- حجم حزمة JavaScript/CSS وزمن فتح PWA.
- معدل نجاح Push.
- معدل تعارض وفشل Outbox.

لا تعتمد SLOs قبل قياس Staging، ولا يعلن الإطلاق قبل نجاح الحدود المتفق عليها.

### 5.4 Pilot والإطلاق

لم يبدأ Pilot بعد. الترتيب المعتمد:

1. Staging.
2. فريق داخلي.
3. متجر تجريبي واحد.
4. مجموعة محاسبين محدودة.
5. 10% من المستخدمين.
6. 50% بعد استقرار المؤشرات.
7. إطلاق عام.

## 6. المخاطر المفتوحة

| الخطر | الأثر | الإجراء المطلوب |
| --- | --- | --- |
| عدم وجود اختبار Android فعلي | أخطاء تثبيت أو تحديث لا تظهر في الفحص الثابت | تنفيذ مصفوفة أجهزة موثقة |
| عدم اختبار OneSignal الحقيقي | نجاح الكود دون ضمان التسليم | Staging App وقياس التسليم والنقر |
| عدم وجود SLOs | لا يوجد معيار قرار إطلاق رقمي | قياس خط أساس ثم اعتماد حدود |
| عدم اختبار حمل | احتمال Queue lag أو بطء البحث وقت الذروة | سيناريوهات حمل واقعية |
| Composer `vendor` غير موجود في بيئة المراجعة الحالية | تعذر تشغيل PHPUnit وLaravel Runtime محليًا | تشغيل CI/بيئة مجهزة قبل الدمج |
| Outbox محدود بمسودة واحدة | ليس عيبًا؛ لكنه يمنع تعميم Offline | لا يوسع قبل نجاح Pilot الحالي |

## 7. التحقق الآلي المتاح

الأوامر الأساسية الموجودة في المشروع:

```bash
npm run test:pwa
npm run test:pwa:phase3
npm run test:pwa:outbox
npm run test:pwa:controls
npm run test:pwa:deep-links
npm run test:pwa:browser -- https://staging.example.com
npm run test:pwa:deployment -- https://staging.example.com
npm run test:notifications
npm run test:roadmap-scope
npm run test:visual
npm run build
```

الفحوص الثابتة والبناء لا تستبدل اختبارات Staging والأجهزة الفعلية وPHPUnit.

## 8. قرار المرحلة

**القرار: الأساس البرمجي لـPWA جاهز للانتقال إلى مرحلة التحقق التشغيلي، وليس للإطلاق العام المباشر.**

لا نضيف نطاقات Offline جديدة ولا عمليات حساسة جديدة قبل:

- نجاح مصفوفة الأجهزة.
- نجاح Staging وPush وDeep Links.
- توثيق الأداء وSLOs.
- نجاح اختبار الحمل.
- نجاح Pilot محدود دون فروقات بيانات.

## 9. الخطوة التالية المقترحة

تنفيذ حزمة **PWA Staging Acceptance** كخطوة واحدة، ومخرجها تقرير موقع يحتوي:

- البيئة ونسخة البناء والجهاز والمتصفح.
- نتيجة كل رحلة قبول.
- نتائج الأداء وQueue وPush.
- الأعطال المكتشفة والإصلاحات.
- قرار Go/No-Go.
- خطة Rollback ومفاتيح التعطيل المستخدمة.

بعد نجاح هذه الحزمة يبدأ Pilot محدود. يبقى Flutter مؤجلًا حتى قرار جديد صريح.
