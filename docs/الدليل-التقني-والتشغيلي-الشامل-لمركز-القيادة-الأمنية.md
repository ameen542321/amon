# الدليل التقني والتشغيلي الشامل لمركز القيادة الأمنية

## 1. تعريف المستند

هذا المستند هو المرجع التفصيلي للنظام الأمني المسمى **مركز القيادة الأمنية**. يشرح ما ينفذه النظام فعليًا الآن، والملفات والدوال والجداول والمسارات، وكيف ينشأ البلاغ، وكيف يعرض، وكيف يتعامل الأدمن معه، وما المشكلات التي يستطيع اكتشافها، وما الذي لا يكتشفه حاليًا، وأين يقع سبب كل مشكلة وأين يعالج.

> قاعدة دقة مهمة: وجود بند في خطة سابقة لا يعني أنه منفذ. قسم **حدود النظام الحالية** في هذا المستند يفرق صراحة بين المنفذ والمقترح.

## 2. الملخص التنفيذي

مركز القيادة طبقة داخل تطبيق Laravel تقوم بأربع وظائف:

1. **الرصد:** تستقبل أحداثًا محددة من تسجيل الدخول، حماية الإدارة، تقارير الاستثناءات، وفحص الصحة اليدوي/المرتبط بجلسة الأدمن.
2. **التجميع:** تجمع الحدث المتكرر خلال 24 ساعة في بلاغ واحد بدل إنشاء صف لكل محاولة.
3. **الإدارة:** تعرض البلاغات للأدمن فقط، وتسمح بالاستلام والتعيين والملاحظات والاحتواء والتحقق والإغلاق والرجوع.
4. **الصيانة:** توفر أزرارًا داخل صفحة الأمن للفحص والتقرير ومعاينة التنظيف والتنظيف؛ دون Cron أو Laravel Scheduler.

النظام ليس WAF، وليس مضاد فيروسات، وليس ماسح ثغرات شاملًا، ولا يضمن أن التطبيق غير مخترق. هو نظام تدقيق واستجابة داخل التطبيق للمصادر التي تم ربطها به فعلًا.

## 3. خريطة المعمارية

```text
مصدر الحدث
  ├─ LoginController
  ├─ IsAdmin Middleware
  ├─ Exception reporter في bootstrap/app.php
  └─ SecurityHealthCheck
          │
          ▼
SecurityEventService::record()
  ├─ استخراج IP والمسار والجهاز
  ├─ إنشاء fingerprint
  ├─ تنقيح evidence
  ├─ تجميع الحدث المفتوح خلال 24 ساعة
  ├─ رفع severity/confidence عند التكرار
  └─ إنشاء إشعار للبلاغ الجديد المرتفع/الحرج
          │
          ▼
security_events + security_event_activities
          │
          ▼
SecurityCommandCenterController
  ├─ index: الملخص والفلاتر والمؤشرات
  ├─ show: التقرير والأدلة والـPlaybook والسجل
  ├─ action: أوامر دورة الحادث
  └─ maintenance: فحص/تقرير/تنظيف يدوي
          │
          ▼
Blade + CSS مركزي + security-session-monitor.js
```

## 5. قاعدة البيانات بالتفصيل

### 5.1 جدول `security_events`

| الحقل | المعنى |
| --- | --- |
| `event_code` | رمز ثابت يحدد نوع الحدث، مثل `AUTH.LOGIN_FAILED` |
| `category` | التصنيف العام: `authentication`, `authorization`, `operations` أو غيرها |
| `severity` | `info`, `low`, `medium`, `high`, `critical` |
| `confidence` | ثقة التصنيف من 0 إلى 100؛ لا تعني نسبة احتمال اختراق رياضية |
| `status` | `new`, `investigating`, `contained`, `resolved`, `false_positive` |
| `title` | الرسالة العربية المختصرة ذات الصياغة العسكرية |
| `description` | شرح إضافي اختياري |
| `source_ip` | IP الخام المستخدم داخليًا للتجميع والتقييد؛ الواجهة تعرض نسخة منقحة |
| `user_agent` | المتصفح/الجهاز، بحد أقصى 1000 محرف عند التسجيل |
| `route`, `http_method` | المسار وطريقة HTTP عند توفر Request |
| `actor_type`, `actor_id` | علاقة polymorphic مع من نفذ النشاط إن عرف |
| `target_type`, `target_id` | علاقة polymorphic مع الحساب/العنصر المستهدف إن عرف |
| `fingerprint` | SHA-256 مبني من الكود وIP والمسار والموضوع |
| `occurrences` | عدد مرات تكرار الحدث المجمع |
| `evidence` | JSON منقح للأدلة |
| `resolution` | سبب/نتيجة الإغلاق |
| `verification_note` | نتيجة فحص التحقق قبل الحل |
| `response_action` | آخر استجابة قابلة للتتبع مثل `block_source` |
| `response_expires_at` | موعد انتهاء الاستجابة المؤقتة عند توفره |
| `assigned_to` | الأدمن المسؤول عن المتابعة |
| `acknowledged_by`, `acknowledged_at` | من استلم البلاغ ومتى |
| `verified_by`, `verified_at` | من تحقق من الحل ومتى |
| `first_seen_at`, `last_seen_at`, `detected_at` | أول وآخر رصد ووقت إنشاء البلاغ |
| `contained_at`, `resolved_at` | وقت الاحتواء والإغلاق |

### 5.2 جدول `security_event_activities`

يحفظ كل أمر إداري: البلاغ، الأدمن، اسم الإجراء، الحالة السابقة واللاحقة، الملاحظة، IP منفذ الأمر، والتوقيت. لا يوجد مسار في المركز لتعديل نشاط قديم؛ لكنه ليس مخزن WORM تقنيًا، ويمكن لمن يملك وصولًا مباشرًا لقاعدة البيانات تغييره.

### 5.3 العلاقات

- `actor()` و`target()` علاقات polymorphic.
- `assignee()`, `acknowledger()`, `verifier()` تعود إلى `User`.
- `activities()` تربط البلاغ بسجله الزمني.
- حذف البلاغ يحذف أنشطته بسبب `cascadeOnDelete`.

## 6. كيف يسجل الحدث؟

الدالة المركزية هي:

```php
SecurityEventService::record($code, $category, $severity, $title, $context)
```

### 6.1 بناء البصمة

البصمة تتكون من:

```text
event_code | source_ip | route | subject
```

ثم تحول إلى SHA-256. معنى ذلك أن محاولات من IP مختلف، أو لمسار مختلف، أو موضوع مختلف تنتج بلاغات منفصلة.

### 6.2 نافذة التجميع

يبحث النظام عن بلاغ:

- يحمل البصمة نفسها.
- حالته مفتوحة (`new`, `investigating`, `contained`).
- آخر رصد له خلال 24 ساعة.

إذا وجده، يزيد `occurrences` ويحدث `last_seen_at` ويرفع الخطورة والثقة عند الحاجة. يستخدم `lockForUpdate()` ومعاملة قاعدة بيانات لتقليل ضياع العد عند الطلبات المتزامنة.

### 6.3 متى ينشأ بلاغ جديد؟

ينشأ بلاغ جديد إذا لم يوجد بلاغ مفتوح مطابق خلال 24 ساعة. البلاغ المغلق لا يعاد فتحه تلقائيًا؛ تكرار الحدث بعد الإغلاق ينشئ بلاغًا جديدًا.

### 6.4 تنقيح الأدلة

المفاتيح التالية تستبدل بـ`[REDACTED]` مهما كانت قيمتها:

```text
password, password_confirmation, token, _token,
authorization, cookie, secret, api_key
```

التنقيح يعمل تكراريًا داخل المصفوفات، والنصوص الأخرى تقص إلى 2000 محرف. التنقيح يعتمد على **اسم المفتاح**؛ إذا وضع مطور سرًا تحت اسم غير مدرج، فلن يعرف النظام تلقائيًا أنه سر. لذلك يجب ألا تمرر أسرارًا أصلًا إلى `evidence`.

### 6.5 الإشعار

عند إنشاء بلاغ جديد بدرجة `high` أو `critical`، ينشأ إشعار داخلي بعد نجاح commit. لا يرسل إشعارًا جديدًا عند كل تكرار، ولا يرسل حاليًا إشعارًا إذا ارتفع بلاغ موجود من متوسط إلى مرتفع أثناء التجميع.

## 7. الأحداث المنفذة فعليًا

### 7.1 `AUTH.LOGIN_FAILED`

**أين يحدث؟** داخل `LoginController` بعد فشل حارسي `accountant` و`web`.

**كيف يحدث؟** يدخل شخص بريدًا وكلمة مرور غير صحيحة. يزيد RateLimiter، ثم يسجل الحدث. تصبح الخطورة `medium` عند المحاولة الثالثة فأكثر، وقبل ذلك `low`.

**ما الأدلة؟** hash للبريد وعدد المحاولات. لا تحفظ كلمة المرور ولا البريد الخام داخل evidence، لكن `subject` المستخدم في fingerprint هو البريد بعد تحويله إلى lowercase ولا يخزن كحقل مستقل.

**الحل التشغيلي:** راجع IP والتكرار، استلم البلاغ، قيد المصدر عند ثبوت الإساءة، ثم تحقق من عدم وجود دخول ناجح غير معتاد.

**مكان الحل:** تفاصيل البلاغ في مركز القيادة، وأمر `block_source` عند توفر IP.

### 7.2 `AUTH.RATE_LIMITED`

**أين يحدث؟** في بداية محاولة الدخول إذا بلغ مفتاح التقييد خمس محاولات.

**كيف يحدث؟** المفتاح هو SHA-256 للبريد lowercase مع IP. بعد خمس محاولات فاشلة خلال مدة decay البالغة ساعة، يرفض الطلب التالي ويظهر بلاغ مرتفع.

**المعالجة:** لا يوقف حساب الضحية. يمنع المحاولة بالمفتاح نفسه حتى انتهاء التقييد أو نجاح دخول قبل بلوغ الحد. يمكن للأدمن تقييد IP من البلاغ عند الحاجة.

**حد مهم:** المهاجم الموزع على IPs عديدة يحصل على عداد مستقل لكل IP؛ النظام الحالي لا يجمع حدًا ثانيًا عالميًا لكل حساب حتى لا يحول الحماية إلى أداة حجب للضحية.

### 7.3 `AUTH.ADMIN_LOGIN`

**أين يحدث؟** بعد نجاح دخول حارس `web` لمستخدم دوره admin وبعد تجديد الجلسة.

**كيف يعرض؟** حدث `info` يثبت دخول الأدمن وIP والجهاز والمسار.

**المعالجة:** لا يحتاج احتواء عادة. إذا لم يتعرف الأدمن على الدخول، يبدأ التحقيق ويفرض إعادة تعيين كلمة المرور وفق البلاغ المرتبط بالحساب إن كان actor/target محفوظًا.

### 7.4 `AUTHZ.ADMIN_DENIED`

**أين يحدث؟** داخل `IsAdmin` عندما يصل مستخدم غير أدمن أو غير مصادق إلى مسار يمر بهذا Middleware.

**كيف يحدث؟** طلب مباشر لمسار إداري محمي. يسجل بلاغًا متوسطًا ثم يحول إلى `no.access`.

**حد مهم:** المسارات التي لا تستخدم `is.admin` لا يغطيها هذا الحدث. كما أنه لا يسجل كل 403 في المشروع؛ يسجل رفض Middleware الإدارة هذا فقط.

### 7.5 `OPS.UNHANDLED_EXCEPTION`

**أين يحدث؟** في callback التقارير داخل `bootstrap/app.php` للاستثناءات غير المعالجة في طلبات الويب.

**الأدلة:** class الاستثناء واسم الملف فقط ورقم السطر. لا تحفظ رسالة الاستثناء لتقليل احتمال تسريب بيانات.

**الحل:** افتح logs الخادم، استخدم class/الملف/السطر للوصول إلى السبب، أصلح الكود في مهمة منفصلة، أعد إنتاج المشكلة، ثم احتو البلاغ وتحقق من توقف التكرار.

**حماية:** إذا فشل تسجيل الحدث نفسه، يمسك callback الخطأ حتى لا يخفي الاستثناء الأصلي أو ينشئ حلقة لا نهائية.

### 7.6 `OPS.DEBUG_ENABLED`

**أين يحدث؟** داخل `SecurityHealthCheck` عند `config('app.debug') === true`.

**السبب المعتاد:** `APP_DEBUG=true` في بيئة الإنتاج أو config cache قديم.

**الحل:** عدل `.env` إلى `APP_DEBUG=false` ثم نفذ `php artisan config:clear` أو أعد بناء config cache وفق طريقة النشر، وبعد ذلك أعد الفحص من زر **فحص أمني الآن**.

### 7.7 `OPS.FAILED_JOBS`

**أين يحدث؟** داخل فحص الصحة إذا كان جدول `failed_jobs` موجودًا وعدده أكبر من صفر.

**الخطورة:** `medium` من 1 إلى 9، و`high` من 10 فأكثر.

**الحل:** راجع `php artisan queue:failed` وسجل التطبيق، أصلح السبب، أعد المحاولة أو احذف المهام وفق قرار تشغيلي، ثم أعد فحص الأمن.

**حد مهم:** النظام يعد الصفوف فقط، ولا يحلل payload أو يحدد Job المسؤول، ولا يثبت أن Queue Worker يعمل.

### 7.8 `OPS.DISK_LOW`

**أين يحدث؟** داخل فحص الصحة عند انخفاض المساحة الحرة في filesystem الذي يحتوي `storage_path()` عن 10%.

**الحل:** افحص استخدام القرص من لوحة الاستضافة، نظف logs/backups/cache غير المطلوبة وفق سياسة آمنة، زد المساحة عند الحاجة، ثم أعد الفحص.

**حد مهم:** يفحص filesystem الخاص بـ`storage_path()` فقط، وقد لا يمثل قرص قاعدة البيانات أو خدمة تخزين خارجية.

## 8. تشغيل الفحص دون Cron أو Scheduler

لا يحتوي المشروع على `withSchedule`, `schedule()`, `RunScheduler`, أو `model:prune` فعّال. التشغيل بطريقتين فقط:

### 8.1 زر الفحص اليدوي

يرسل POST إلى `admin.security.maintenance.check`. يتحقق Controller من Policy، ثم يستخدم Cache key باسم `security:maintenance:health-lock`. الفحص اليدوي لا يتكرر خلال 60 ثانية.

### 8.2 فحص جلسة الأدمن كل 15 دقيقة

يوضع endpoint والمدة على navbar الأدمن. وحدة JavaScript:

- تسجل نشاط `pointerdown`, `keydown`, `touchstart`.
- تنتظر 900000ms.
- لا ترسل الطلب إذا كانت الصفحة مخفية.
- لا ترسله إذا مضت أكثر من 15 دقيقة دون نشاط.
- لا تبدأ طلبًا ثانيًا محليًا أثناء الأول.
- ترسل CSRF وcredentials.
- لا تكسر الواجهة إذا فشلت الشبكة.

الخادم يضع lock لمدة 900 ثانية للفحص التلقائي؛ لذلك لا تنفذ التبويبات المتعددة الفحص أكثر من مرة ضمن النافذة، بشرط أن تستخدم جميع عمليات PHP مخزن Cache مشتركًا.

### 8.3 ما المقصود بـ«جلسة نشطة»؟

ليست مجرد session موجودة على الخادم. المقصود أن صفحة أدمن ظاهرة في المتصفح وحدثت نقرة أو كتابة أو لمسة خلال آخر 15 دقيقة. إذا أغلق المتصفح أو أخفيت الصفحة أو توقف النشاط، لا يوجد طلب دوري.

## 9. Controller والدوال بالتفصيل

### `index(Request $request)`

- يفوض `viewAny` عبر Gate.
- يتحقق من فلاتر severity/status/category/search.
- يبحث في code/title/source_ip.
- يرتب حسب آخر رصد، ويعرض 20 بلاغًا في الصفحة.
- يحسب المفتوحة والمرتفعة/الحرجة والمحتواة اليوم والجديدة والمشكلات التشغيلية ومحاولات الدخول.
- يحمل أحداث 30 يومًا لحساب متوسط دقائق الاستلام والاحتواء والتحقق في PHP.
- يعرض نبضة الفحص ومفاتيح الاستجابة.

**ملاحظة أداء:** حساب الأداء يجلب جميع أحداث آخر 30 يومًا إلى الذاكرة، وليس aggregate SQL. إذا صار الحجم كبيرًا جدًا، يجب نقله إلى استعلامات قاعدة بيانات أو جدول metrics.

### `show(SecurityEvent $securityEvent)`

يفوض `view`، ويحمل الأنشطة والمستخدمين المرتبطين، ويجلب قائمة حسابات admin للتعيين.

### `action(...)`

يفوض `update`، ثم يمرر action/note/assigned_to إلى `SecurityEventService::transition()`، ويعيد رسالة نجاح.

### `runCheck(Request $request)`

يفرق بين `automatic=true` (قفل 15 دقيقة) واليدوي (قفل دقيقة)، ثم يستدعي أمر الفحص عبر `Artisan::call`. يرجع JSON للوحدة الخلفية أو redirect/flash للزر.

### `runReport()`

يشغل `security:weekly-report` عند الضغط. الاسم تاريخي؛ الزر يستطيع تشغيله في أي وقت، والتقرير يحسب آخر سبعة أيام.

### `previewCleanup()` و`runCleanup()`

الأول يستخدم `--dry-run` ويعرض العدد دون حذف. الثاني ينفذ الحذف بعد تأكيد الواجهة.

## 10. دورة البلاغ وأوامر الاستجابة

### الحالات المفتوحة

`new`, `investigating`, `contained` هي حالات `scopeOpen()`.

### الأوامر

| الأمر | ما يفعله | الشروط | طريقة الرجوع |
| --- | --- | --- | --- |
| `acknowledge` | يحول للتحقيق ويعين المنفذ ويثبت وقت الاستلام | بلاغ متاح | التعيين لاحقًا لأدمن آخر |
| `assign` | يغير المسؤول | `assigned_to` يجب أن يكون admin | إعادة التعيين |
| `add_note` | يضيف نشاطًا دون تغيير البلاغ | ملاحظة 5–1000 | لا يحذف من الواجهة؛ أضف ملاحظة تصحيح |
| `contain` | يحول إلى contained ويسجل الوقت | ليس مغلقًا | لا يوجد rollback مستقل؛ أكمل/أعد فتح حسب الحالة |
| `block_source` | يقيد IP في Cache | IP موجود، وليس IP الأدمن الحالي | `release_source` أو انتهاء المدة |
| `release_source` | يمسح Cache key | آخر response هو block_source | أعد block_source عند ثبوت الحاجة |
| `require_password_reset` | يضع flag ويمسح remember token | البلاغ مرتبط بـUser، وليس حساب الأدمن الحالي نفسه | `cancel_password_reset` أو إكمال reset |
| `cancel_password_reset` | يزيل flag | flag مفعل | أعد فرضه عند الحاجة |
| `verify_resolve` | يغلق مع verified_at/by/note | الحالة contained | `reopen` |
| `false_positive` | يغلق كإنذار كاذب | الاستجابة مفعلة | `reopen` |
| `reopen` | يعيد إلى investigating ويمسح حقول الحل/التحقق | resolved أو false_positive | احتواء ثم تحقق جديد |

كل الأوامر الحساسة تتوقف إذا كان `SECURITY_RESPONSE_ENABLED=false`. أما `SECURITY_AUTOMATIC_RESPONSE_ENABLED` فيعرض حالة الإعداد فقط حاليًا؛ لا يوجد كود ينفذ block/reset تلقائيًا بناء عليه.

## 11. تقييد IP

مدة التقييد الافتراضية 30 دقيقة من `SECURITY_BLOCK_MINUTES`. المفتاح لا يحتوي IP الخام؛ يحتوي SHA-256 للـIP. `BlockSecurityThreats` يمر على مجموعة web ويرجع 429 إذا وجد المفتاح.

### قيود مهمة

- التقييد داخل Cache التطبيق، وليس firewall الخادم.
- `cache:clear` يلغي التقييدات.
- عند استخدام cache محلي مع عدة خوادم، قد يقيد خادمًا دون الآخر؛ يلزم Redis/Cache مشترك.
- دقة IP تعتمد على ضبط Trusted Proxies. الضبط الخاطئ قد يرى IP الـproxy بدل العميل.
- NAT قد يجعل عدة مستخدمين يشتركون في IP؛ لذلك التقييد يدوي ومؤقت.

## 12. فرض إعادة تعيين كلمة المرور

عند تطبيق الأمر على بلاغ مرتبط بـ`App\Models\User`:

1. يصبح `must_reset_password=true`.
2. يمسح `remember_token`.
3. عند محاولة الدخول التالية ينجح فحص كلمة المرور أولًا، ثم يسجل الخروج ويلغي session ويوجه إلى طلب الاستعادة.
4. عند reset ناجح يصبح flag=false ويمسح remember token.

### حدود مهمة

- التنفيذ الحالي خاص بجدول `users`؛ لا يفرض reset على موديل `Accountant`.
- لا يبطل جميع الجلسات النشطة السابقة المخزنة على أجهزة أخرى فورًا. يمسح remember token ويمنع الدخول اللاحق، لكن جلسة سبق أن سجلت الدخول قد تبقى حتى انتهائها بحسب session driver. إذا كان المطلوب إبطال فوري شامل، يلزم نظام session revocation مستقل.
- لا يستطيع الأدمن فرض reset على حسابه الحالي من جلسته نفسها عبر هذا الأمر.

## 13. التقرير

`SecurityWeeklyReport` يحسب منذ `now()->subWeek()`:

- عدد صفوف البلاغات المكتشفة.
- عدد الصفوف التي احتويت خلال الأسبوع.
- عدد الصفوف التي تحققت خلال الأسبوع.
- عدد البلاغات المفتوحة الآن.

ثم ينشئ إشعارًا داخليًا موجهًا لكل User دوره admin.

**دقة الرقم:** `detected` يعد البلاغات المجمعة (rows)، وليس مجموع `occurrences`. لذلك 100 محاولة مجمعة في بلاغ واحد تظهر كبلاغ واحد في التقرير، بينما بطاقة محاولات الدخول تستخدم مجموع occurrences.

## 14. التنظيف والاحتفاظ

المدة الافتراضية 180 يومًا، والحد الأدنى البرمجي 30 يومًا حتى لو ضبطت قيمة أقل. التنظيف يستهدف فقط:

- `resolved`
- `false_positive`
- و`resolved_at` أقدم من المدة

`--dry-run` يحسب فقط. التنفيذ يحذف البلاغات، وبسبب cascade يحذف أنشطتها أيضًا.

> تنبيه: هذا تنظيف بالحذف وليس أرشفة إلى جدول مستقل. إذا كانت السياسة القانونية تتطلب الاحتفاظ غير القابل للحذف أو export، يجب إضافة أرشيف قبل استخدام زر الحذف.

## 15. الواجهة والهوية البصرية

- Blade يحتوي الهيكل والبيانات فقط.
- الأنماط الخاصة بالمركز في `resources/css/app.css`.
- تستخدم `ui-card`, `ui-badge`, `ui-input`, `ui-table`, `ui-btn`, `ui-alert`.
- الوضع المظلم افتراضي والفاتح مدعوم عبر التوكِنز المركزية.
- المصدر يعرض منقحًا: IPv4 يخفي الجزء الأخير، وIPv6 يعرض أول ثلاثة أجزاء تقريبًا.
- الجدول قابل للتمرير بلوحة المفاتيح، وله caption مخفي لقارئ الشاشة.
- أوامر الاستجابة تستخدم التأكيد المركزي `data-ui-confirm`.

## 16. الصلاحيات والحماية

توجد ثلاث طبقات:

1. مجموعة routes: `web`, `auth`, `is.admin`.
2. `SecurityEventPolicy`: viewAny/view/update للأدمن فقط.
3. `SecurityEventActionRequest::authorize()`: يتأكد من دور admin.

الأوامر POST/PATCH/DELETE محمية بـCSRF ضمن web. لا يكفي إخفاء الزر؛ الخادم يعيد التحقق.

## 18. ما لا يكتشفه النظام حاليًا

رغم أن خطة المشروع ذكرت نطاقًا أوسع، لا يوجد حاليًا كود مخصص يكتشف تلقائيًا:

- SQL injection من محتوى request.
- XSS من المدخلات.
- رفع ملفات ضارة أو MIME مزور.
- فشل CSRF 419 كتجميع مستقل.
- كل أخطاء 403 في التطبيق؛ المغطى هو `IsAdmin` فقط.
- مسح `.env`, `wp-admin`, `phpmyadmin` كرموز أحداث مستقلة.
- تغير دولة/مدينة الدخول أو الجهاز الجديد بالمقارنة التاريخية.
- توقف Queue Worker نفسه؛ المغطى وجود failed_jobs فقط.
- نجاح/فشل النسخ الاحتياطي.
- بطء استعلامات قاعدة البيانات.
- فشل البريد أو OneSignal كأحداث أمنية مستقلة.
- تغييرات سلامة البيانات المالية والمخزنية.
- malware أو تعديل ملفات الخادم.
- هجمات قبل وصول الطلب إلى Laravel.

هذه النقاط تحتاج Middleware/listeners أو WAF وخدمات بنية تحتية وموافقة منفصلة. لا يجوز للواجهة الادعاء بأنها تفحصها الآن.

## 19. إعدادات البيئة

```dotenv
SECURITY_RESPONSE_ENABLED=true
SECURITY_AUTOMATIC_RESPONSE_ENABLED=false
SECURITY_BLOCK_MINUTES=30
SECURITY_EVENT_RETENTION_DAYS=180
```

- بعد تغيير config في الإنتاج، أعد تحميل config وفق عملية النشر.
- `automatic_response_enabled` لا يفعل استجابة تلقائية في الإصدار الحالي.
- Cache مهم للتقييد وقفل الفحص والنبضة.

## 20. خطوات تشغيل أول مرة

1. خذ نسخة احتياطية.
2. نفذ migrations.
3. ابنِ Vite assets حتى تحمل وحدة session monitor.
4. سجل دخول الأدمن وافتح مركز القيادة.
5. اضغط **فحص أمني الآن**.
6. راجع النبضة وأي بلاغ debug/jobs/disk.
7. أنشئ بلاغًا تجريبيًا في بيئة اختبار، وجرب acknowledge/contain/verify/reopen.
8. جرب معاينة التنظيف فقط قبل أي حذف.
9. لا تضف Cron ولا `schedule:run`.

## 21. تشخيص الأعطال

### صفحة الأمن 403 أو تحول إلى no-access

- تحقق أن guard هو `web`.
- تحقق أن `role=admin`.
- تحقق من middleware والمسار وPolicy.

### خطأ table not found

- migrations لم تطبق.
- نفذ `php artisan migrate` بعد النسخة الاحتياطية.

### زر الفحص لا يحدث شيئًا

- راجع flash message.
- افحص Laravel log.
- تأكد أن الأمر مسجل وأن `vendor` مثبت.
- إذا ظهرت رسالة «نفذ مؤخرًا»، فهذا قفل حماية وليس عطلًا.

### الفحص التلقائي لا يعمل

- تأكد من بناء JS وتحميل الحزمة.
- تأكد أن navbar يحمل data-security-session-monitor.
- اترك الصفحة ظاهرة وتفاعل معها.
- افحص طلب `/admin/security-maintenance/check` في Network.
- تأكد من CSRF والجلسة.

### بلاغات متكررة كثيرة

- افحص هل IP/route/subject تختلف؛ اختلاف أي منها يغير fingerprint.
- البلاغ المغلق لا يجمع أحداثًا جديدة.
- افحص ثبات IP خلف proxy.

### لا يصل إشعار مرتفع

- الإشعار ينشأ عند **إنشاء** بلاغ high/critical جديد فقط.
- افحص وجود admin في users.
- افحص notifications schema وLaravel log.
- تصعيد بلاغ موجود لا يرسل إشعارًا ثانيًا حاليًا.

## 22. الاختبارات الحالية

`SecurityCommandCenterTest` يغطي:

- منع غير الأدمن.
- تجميع الحدث والتنقيح ورفع الخطورة.
- الاحتواء ثم التحقق والتدقيق.
- التعيين والملاحظات.
- Rate limiting دون إيقاف الضحية.
- إعادة فتح البلاغ.
- منع الحل دون احتواء.
- فرض reset والرجوع عنه.
- منع تكرار فحص الجلسة باستخدام Cache lock.

اختبارات ما زالت مطلوبة لتحسين الثقة:

- اختبار إشعار البلاغ المرتفع بعد commit.
- اختبار block/release عبر Middleware.
- اختبار أوامر التقرير والتنظيف والمعاينة.
- اختبار session monitor في متصفح حقيقي.
- اختبار المظهرين والموبايل ولقطة مرئية.
- اختبار Cache مشترك ومتعدد الخوادم.
- اختبار Trusted Proxies وIPv6.
- اختبار الحجم الكبير لمؤشرات 30 يومًا والتنظيف.

## 23. قواعد التطوير المستقبلية

- كل مصدر رصد جديد يجب أن يحدد code/category/severity/confidence/evidence غير حساسة.
- لا ترسل request payload كاملًا إلى evidence.
- كل استجابة حساسة يجب أن تكون قابلة للرجوع أو محدودة المدة ومقيدة بصلاحية.
- لا تغلق بلاغًا دون verification.
- لا تضف Scheduler أو Cron؛ ضع زر الصيانة داخل صفحة النظام الذي تخدمه، مع preview وCSRF وPolicy وCache lock.
- لا تضف CSS داخل Blade؛ استخدم CSS المركزي والتوكِنز المعتمدة.
- لا تعدل بيانات مالية أو مخزنية أو تقارير من مركز الأمن تلقائيًا.
- حدث هذا المستند عند إضافة event code أو action أو مصدر فحص.

## 24. قائمة تحقق تشغيلية للأدمن

### يوميًا عند استخدام النظام

- راجع البلاغات الجديدة والمرتفعة.
- استلم البلاغ قبل التحقيق.
- عين المسؤول إذا تعدد المدراء.
- اكتب ملاحظات واقعية لا تحتوي أسرارًا.

### عند حادث دخول

- راجع التكرار وIP المنقح والجهاز.
- لا توقف الحساب لمجرد محاولات فاشلة.
- قيد IP مؤقتًا فقط عند وجود دليل.
- استخدم reset للحساب المرتبط عند وجود اشتباه معتبر.

### قبل الإغلاق

- احتو البلاغ.
- نفذ شرط Playbook.
- اكتب دليل التحقق.
- استخدم **تحقق وإغلاق**، لا تعتبر توقف التكرار اللحظي حلًا نهائيًا.

### دوريًا

- اضغط إنشاء تقرير عند الحاجة.
- استخدم معاينة التنظيف قبل الحذف.
- راجع مدة الاحتفاظ مع سياسة المشروع.
- تحقق من حداثة النبضة أثناء جلسات الإدارة النشطة.

## 25. الخلاصة الدقيقة

النظام الحالي جاهز لإدارة مجموعة محددة من أحداث المصادقة وصلاحية الإدارة والاستثناءات وصحة debug/failed jobs/disk. يوفر تجميعًا وتنقيحًا ودورة استجابة موثقة وتشغيلًا يدويًا/مرتبطًا بجلسة الأدمن دون Cron. لا ينبغي وصفه بأنه ماسح اختراق شامل، وتظل الحماية الخارجية، إعداد proxy/cache، النسخ الاحتياطي، مراقبة Queue والخدمات، والتدقيق الأمني الدوري مسؤوليات منفصلة.
