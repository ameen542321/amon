# تشغيل نظام الإشعارات محليًا وعلى الاستضافة

## 1. الهدف وحدود المستند

يشرح هذا المستند تشغيل الأجزاء الموجودة حاليًا:

1. الإشعار الداخلي المحفوظ في جدول `notifications`.
2. إرسال Web Push بواسطة OneSignal عبر Queue.
3. تنظيف الإشعارات الأقدم من 15 يومًا بواسطة Scheduler.
4. صفحة المدير «ملخص وتحكم الإشعارات».

لا يطلب هذا الدليل إنشاء جداول جديدة في قاعدة الإنتاج، ولا ينفذ Migration أو
حذفًا تلقائيًا بمجرد قراءة المستند. افحص حالة الجداول أولًا، وخذ نسخة احتياطية
قبل أي أمر يغير قاعدة بيانات حقيقية.

## 2. لماذا نحتاج Queue مع وجود صفحة الإدارة؟

صفحة الإدارة وQueue لهما مسؤوليتان مختلفتان:

- **صفحة الإدارة:** تعرض السجلات والملخص، وتحذف إشعارًا محددًا أو الإشعارات
  المنتهية حسب سياسة الاحتفاظ.
- **Queue:** ينفذ اتصال OneSignal خارج طلب المتصفح، ويعيد المحاولة عند الفشل.
- **Scheduler:** يشغل التنظيف الدوري في الوقت المحدد.

يمكن ضبط `QUEUE_CONNECTION=sync` للاستعمال المحلي المؤقت، لكنه لا يلغي العمل؛
بل ينقله إلى طلب المستخدم نفسه. لذلك قد يصبح زر الإرسال بطيئًا أو يفشل عند بطء
OneSignal. في الإنتاج يوصى بإبقاء `database` أو استخدام Redis عند توفره.

## 3. المتطلبات الموجودة في المشروع

- القيمة الافتراضية في `config/queue.php` هي اتصال Queue المحدد في
  `QUEUE_CONNECTION`، والملف `.env.example` يستخدم `database`.
- يحتوي المشروع أصلًا على Migration لجداول `jobs` و`job_batches` و`failed_jobs`.
- مهمة Push هي `SendOneSignalNotification` وتملك Timeout ومحاولات وBackoff.
- أمر التنظيف هو `notifications:cleanup`.
- الجدولة اليومية معرفة داخل `routes/console.php` الساعة `02:30` دون تداخل.

> وجود Migration في المستودع لا يثبت أنها نُفذت على الاستضافة. افحص
> `php artisan migrate:status` ولا تشغل `migrate --force` على الإنتاج قبل نسخة
> احتياطية ومراجعة قائمة التغييرات المعلقة كاملة، لأن الأمر قد يشغل Migrations
> أخرى لا تخص الإشعارات.

## 4. التشغيل المحلي

### 4.1 تجهيز البيئة

```bash
composer install
cp .env.example .env
php artisan key:generate
npm install
npm run build
```

اضبط قاعدة تطوير منفصلة في `.env`. يمنع توجيه البيئة المحلية إلى قاعدة الإنتاج.

```dotenv
APP_ENV=local
APP_DEBUG=true
QUEUE_CONNECTION=database
```

إذا كانت قاعدة التطوير جديدة فقط:

```bash
php artisan migrate
```

إذا كانت القاعدة موجودة، افحص أولًا:

```bash
php artisan migrate:status
```

### 4.2 تشغيل التطبيق وQueue وScheduler

افتح ثلاث نوافذ أو عمليات طرفية:

```bash
php artisan serve
```

```bash
php artisan queue:work --queue=default --sleep=3 --tries=3 --timeout=60
```

```bash
php artisan schedule:work
```

بعد تعديل كود Job أثناء تشغيل العامل:

```bash
php artisan queue:restart
```

### 4.3 تجربة التنظيف دون حذف

ابدأ دائمًا بالمعاينة:

```bash
php artisan notifications:cleanup --dry-run
```

يمكن تجربة حجم دفعة مختلف دون تغيير السياسة:

```bash
php artisan notifications:cleanup --dry-run --chunk=200
```

لا تشغل الأمر دون `--dry-run` على بيانات مهمة إلا بعد مراجعة العدد. الحذف الفعلي
يحذف الإشعارات الأقدم من 15 يومًا نهائيًا.

### 4.4 اختبار Queue محليًا

1. شغل `queue:work`.
2. أرسل Push من لوحة المدير إلى حساب تجريبي فعال له Device Token.
3. راقب نافذة العامل و`storage/logs/laravel.log`.
4. تحقق من انخفاض عدد الصفوف في جدول `jobs` بعد التنفيذ.
5. افحص المهام الفاشلة:

```bash
php artisan queue:failed
```

إعادة محاولة مهمة فاشلة لا تنفذ إلا بعد فهم سبب الفشل:

```bash
php artisan queue:retry JOB_ID
```

## 5. التشغيل على VPS أو خادم كامل

### 5.1 متغيرات البيئة المقترحة

```dotenv
APP_ENV=production
APP_DEBUG=false
QUEUE_CONNECTION=database
```

لا تنسخ قيم OneSignal أو كلمات المرور إلى Git. إعداد الأسرار النهائي يخضع لقرار
نقل مستقل موثق في متطلبات الإشعارات.

### 5.2 Cron الخاص بـScheduler

أضف Cron واحدًا يعمل كل دقيقة، مع استبدال المسار ونسخة PHP حسب الخادم:

```cron
* * * * * cd /var/www/amon && /usr/bin/php artisan schedule:run >> /dev/null 2>&1
```

Laravel هو الذي يقرر داخل هذا الاستدعاء هل حان وقت `02:30`، فلا تضف Cron منفصلًا
لأمر التنظيف.

### 5.3 Supervisor لعامل Queue

مثال `/etc/supervisor/conf.d/amon-worker.conf`:

```ini
[program:amon-worker]
process_name=%(program_name)s_%(process_num)02d
command=/usr/bin/php /var/www/amon/artisan queue:work database --sleep=3 --tries=3 --timeout=60 --max-time=3600
directory=/var/www/amon
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=1
redirect_stderr=true
stdout_logfile=/var/www/amon/storage/logs/queue-worker.log
stopwaitsecs=90
```

ثم:

```bash
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl start amon-worker:*
sudo supervisorctl status
```

بعد كل نشر:

```bash
php artisan optimize:clear
php artisan queue:restart
```

## 6. التشغيل على استضافة مشتركة أو cPanel

المشكلة الأساسية ليست Laravel، بل أن بعض الاستضافات المشتركة تمنع عملية
`queue:work` الدائمة أو تقتلها بعد دقائق. توجد ثلاث حالات:

### الحالة A — الاستضافة تسمح بعملية دائمة

استخدم مدير العمليات الذي توفره الاستضافة وشغل أمر العامل نفسه. هذه أفضل حالة.

### الحالة B — لا تسمح بعملية دائمة لكنها تسمح Cron كل دقيقة

استخدم Cron للـScheduler، وأضف Cron منفصلًا يعالج الموجود ثم يتوقف:

```cron
* * * * * cd /home/ACCOUNT/amon && /usr/local/bin/php artisan queue:work database --stop-when-empty --sleep=1 --tries=3 --timeout=60 >> storage/logs/queue-cron.log 2>&1
```

يفضل استخدام `flock` إن كان متاحًا لمنع تداخل عاملين:

```cron
* * * * * flock -n /tmp/amon-queue.lock -c 'cd /home/ACCOUNT/amon && /usr/local/bin/php artisan queue:work database --stop-when-empty --tries=3 --timeout=60' >> /home/ACCOUNT/amon/storage/logs/queue-cron.log 2>&1
```

عيب هذا الحل أن Push قد ينتظر حتى دورة Cron التالية، لكنه أفضل من تنفيذ الاتصال
داخل طلب الويب.

### الحالة C — لا Queue worker ولا Cron متكرر

يمكن مؤقتًا استخدام:

```dotenv
QUEUE_CONNECTION=sync
```

لكن هذا حل توافقي أخير، وليس إعداد الإنتاج المفضل. ستعمل الرسالة داخل طلب
المدير، وقد يتأخر الطلب عند بطء OneSignal. إذا كانت الاستضافة لا توفر Cron ولا
عمليات خلفية ويكثر الإرسال، فترقية الخطة أو استخدام خدمة Queue خارجية أكثر أمانًا.

## 7. هل يسبب النظام ضغطًا أو مشكلات على الاستضافة؟

### التأثير الطبيعي

- اتصال `database` يضيف عمليات إدخال/قراءة/حذف صغيرة على جدول `jobs`.
- كل دفعة Push تحتوي بحد أقصى على 1000 Device Token.
- عامل واحد مناسب كبداية، ولا حاجة إلى عدة Workers قبل القياس.
- تنظيف الإشعارات ينفذ على دفعات، ومهمة الجدولة محمية من التداخل.

### المشكلات المحتملة وعلاماتها

| المشكلة | العلامة | الإجراء |
|---|---|---|
| عامل Queue متوقف | ارتفاع صفوف `jobs` وعدم وصول Push | شغل العامل وافحص السجل. |
| بيانات OneSignal غير صحيحة | انتقال المهام إلى `failed_jobs` | أصلح الإعداد ثم أعد محاولة المهام المطلوبة فقط. |
| Scheduler غير مفعل | بقاء إشعارات أقدم من 15 يومًا | افحص Cron بواسطة `php artisan schedule:list`. |
| `sync` في الإنتاج | بطء زر الإرسال | أعد `QUEUE_CONNECTION=database` وشغل العامل. |
| عدة Workers على استضافة ضعيفة | ارتفاع CPU واتصالات DB | ابدأ بعامل واحد وقس قبل الزيادة. |
| تراكم السجلات الفاشلة | نمو `failed_jobs` | راجع السبب ثم استخدم أوامر الحذف/التنظيف بحذر. |
| مسار PHP خاطئ في Cron | لا يعمل شيء دون خطأ ظاهر في الموقع | استخدم مسار PHP CLI الذي تعرضه لوحة الاستضافة. |

## 8. فحص الجاهزية بعد النشر

نفذ بالترتيب:

```bash
php artisan about
php artisan migrate:status
php artisan schedule:list
php artisan notifications:cleanup --dry-run
php artisan queue:failed
```

ثم:

1. افتح صفحة «ملخص وتحكم الإشعارات» بحساب المدير.
2. تحقق من الأعداد دون الضغط على الحذف.
3. أرسل إشعارًا إلى حساب تجريبي واحد.
4. تأكد من ظهور الداخلي فورًا.
5. تأكد من معالجة Job ووصول Push.
6. أوقف العامل مؤقتًا في Staging فقط، وأرسل تجربة، وتأكد من بقاء Job في `jobs`.
7. أعد تشغيل العامل وتأكد من معالجة المهمة المتراكمة.

## 9. أوامر الطوارئ والرجوع

- إيقاف Push مؤقتًا بأقل أثر: أوقف Worker؛ ستبقى المهام في `jobs`، بينما يستمر
  حفظ الإشعار الداخلي.
- لا تستخدم `queue:clear` أو حذف جدول `jobs` كإجراء أول؛ قد تفقد رسائل لم ترسل.
- عند نشر كود غير سليم، ارجع للإصدار السابق ثم نفذ `php artisan queue:restart`.
- لا تستخدم `migrate:fresh` أو `db:wipe` مطلقًا على قاعدة حقيقية.
- لا تنفذ حذف الإشعارات المنتهية قبل `--dry-run` ونسخة احتياطية في أول تشغيل.

## 10. API الإشعارات الأولي للـPWA

هذا API يعمل بجلسة الويب الحالية فقط، وليس API عامًا لتطبيق Flutter:

| العملية | المالك | المحاسب |
|---|---|---|
| القائمة | `GET /user/api/v1/notifications` | `GET /accountant/api/v1/notifications` |
| العداد | `GET /user/api/v1/notifications/unread-count` | `GET /accountant/api/v1/notifications/unread-count` |
| تعليم كمقروء | `PATCH /user/api/v1/notifications/{id}/read` | `PATCH /accountant/api/v1/notifications/{id}/read` |
| إخفاء | `DELETE /user/api/v1/notifications/{id}` | `DELETE /accountant/api/v1/notifications/{id}` |

- تقبل القائمة `limit` من 1 إلى 50 وتعيد `meta.next_cursor` للصفحة التالية.
- ترسل الصفحة التالية بإضافة `?cursor=...` دون بناء أرقام صفحات كبيرة.
- طلبات `PATCH` و`DELETE` تحتاج Cookie الجلسة وCSRF token كأي طلب ويب.
- جميع العمليات تعيد تطبيق استعلام المستلم؛ معرفة رقم إشعار آخر لا تمنح الوصول إليه.
- Rate Limit الحالي 120 طلبًا في الدقيقة لكل مجموعة.
- يمنع تخزين استجابة حساب في Cache مشترك. عند تسجيل الخروج يجب حذف Cache
  الإشعارات المحلي لذلك الحساب.
- لا تستخدم هذه المسارات من Flutter ولا ترسل Cookie الجلسة إلى تطبيق خارجي.
  مصادقة Flutter ستضاف بعد اعتماد دورة Token مستقلة وآمنة.
