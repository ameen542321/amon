# مستند مركز القيادة الأمنية وخطة التنفيذ

## حالة المستند

- **الغرض:** اعتماد مواصفات صفحة إدارية ترصد الحوادث الأمنية ومشكلات التشغيل والاستخدام، وتدير دورة التعامل معها.
- **النطاق:** الرصد، التصنيف، العرض، التنبيه، التحقيق، والاحتواء المنضبط دون المساس بالحسابات المالية أو المخزون أو التقارير.
- **المستخدم المخول:** المدير العام فقط عبر حارس `web` ووسيط `is.admin`.
- **مرجع الواجهة الملزم:** `docs/الهوية-البصرية-للمشروع.md`.
- **اسم الصفحة المقترح:** **مركز القيادة الأمنية — غرفة عمليات النظام**.

## الهدف

إنشاء مركز موحد يجيب بوضوح عن الأسئلة الآتية:

- هل توجد الآن محاولة دخول، استطلاع آلي، تجاوز صلاحية، أو طلب مشبوه؟
- هل توجد مشكلة تشغيلية مثل فشل المهام الخلفية أو توقف المجدول أو قرب امتلاء التخزين؟
- ما الذي اكتشفه النظام، وما درجة الثقة والخطورة؟
- هل احتوى النظام الحادث، أم يحتاج قرار المدير؟
- من استلم البلاغ، وما الإجراءات التي نفذت، وهل تحقق النظام من نجاحها؟

تستخدم الصفحة خطابًا عسكريًا عربيًا خفيفًا يمنحها شخصية واضحة، مثل: **«سيدي، رصدنا محاولة دخول مشبوهة»** و**«سيدي، تمت السيطرة على الموقف»**. ويظهر بجوار الخطاب دائمًا وصف تقني مباشر حتى لا تتحول الصياغة إلى ادعاء مبالغ فيه أو رسالة مبهمة.

## نتيجة فحص الوضع الحالي

يمتلك المشروع أساسًا يمكن البناء عليه:

- مسارات إدارية مجمعة ومحمية بالمصادقة ودور المدير.
- خدمة مركزية لسجلات العمليات تحفظ الفاعل ونوع العملية والتفاصيل وعنوان IP وبيانات المتصفح.
- لوحة مدير تعرض إحصاءات عامة وآخر الأنشطة.
- نظام إشعارات وجلسات دعم وسجل إجراءات يمكن الاستفادة من أنماطه التنظيمية.

لكن سجل العمليات العام لا يمثل نظام حوادث أمنية كاملًا؛ فهو لا يملك درجة خطورة ودورة معالجة ووقت احتواء وقرار إغلاق وأدلة مجمعة. كما أن عرض آخر الأنشطة لا يحلل الأحداث أو يفرق بين حادث أمني، مشكلة تشغيل، خطأ استخدام، أو إنذار كاذب.

### ملاحظة عاجلة في تسجيل الدخول

يعتمد مفتاح تقييد المحاولات الحالي على البريد الإلكتروني، ويمسح العداد للحساب النشط قبل فحص تجاوزه الحد. لذلك يجب في التنفيذ مراجعة التدفق باختبارات تثبت أن المحاولات الفاشلة تتراكم فعلًا. كما لا ينبغي إيقاف حساب الضحية تلقائيًا بسبب طلبات صادرة من مهاجم؛ لأن ذلك يسمح باستخدام آلية الحماية لحجب الخدمة عن صاحب الحساب.

المعالجة المعتمدة المقترحة هي مفتاح مركب ومدروس من هوية الحساب وعنوان المصدر، مع تأخير تدريجي وتنبيه وتقييد مؤقت للمصدر، وعدم إيقاف الحساب أو إبطال جلساته إلا وفق سياسة صريحة وإجراء مسجل.

## حدود النظام وتصنيف النتائج

يفصل المركز بين أربعة أنواع، ولا يخلطها في رقم واحد:

| النوع | التعريف | أمثلة |
| --- | --- | --- |
| حادث أمني | سلوك عدائي أو محاولة تجاوز محتملة | brute force، تجاوز صلاحية، استطلاع مسارات حساسة |
| مشكلة تشغيلية | خلل في البنية أو التطبيق | فشل Job، تعطل Queue Worker، مساحة تخزين منخفضة |
| مشكلة استخدام | تكرار سلوك صحيح في أصله لكنه يسبب أخطاء | إدخال غير صالح متكرر أو طلب مكرر من واجهة قديمة |
| سلامة بيانات | تعارض أو نقص يحتاج مراجعة متخصصة | علاقات مفقودة أو سجلات يتيمة، دون تعديل آلي للبيانات المالية أو المخزنية |

لا يقال **«تم اختراق النظام»** عند فشل تسجيل دخول، ولا **«تم منع الاختراق»** عند ظهور طلب `404`. تستخدم حالات دقيقة: رُصد، مشتبه به، قيد التحقيق، تم الاحتواء، تم الحل والتحقق، أو إنذار كاذب.

## مصادر الرصد المطلوبة

### المصادقة والجلسات

- محاولات الدخول الفاشلة والناجحة ذات الحساسية الأمنية.
- استهداف عدة حسابات من مصدر واحد أو حساب واحد من مصادر متعددة.
- محاولة استخدام حساب موقوف، وتكرار استعادة كلمة المرور.
- دخول إداري من جهاز جديد أو تغير غير معتاد في الجلسة.
- إبطال الجلسة أو تغيير كلمة المرور أو رفع مستوى الحماية، مع تسجيل من أمر بذلك.

### الصلاحيات والطلبات

- تكرار استجابات `403` و`419` و`429` والأخطاء `500`.
- محاولة مستخدم عادي دخول مسار إداري، أو الوصول إلى متجر أو مورد غير مصرح به.
- تبديل المعرفات للوصول إلى بيانات مستخدم آخر.
- أنماط SQL injection وXSS ورفع ملفات غير مسموحة والحمولات الكبيرة أو الحقول غير المتوقعة.
- استطلاع مسارات مثل `.env` و`phpmyadmin` و`wp-admin`، مع حفظ المسار المنقح دون أسرار.

### التشغيل وصحة المشروع

- المهام الخلفية الفاشلة وحالة Queue Worker والفحص اليدوي المرتبط بالصفحة.
- نجاح النسخ الاحتياطي وحداثته، دون عرض مفاتيح أو أسرار.
- مساحة القرص وقابلية الكتابة في المجلدات المطلوبة.
- تكرار الاستثناءات وبطء قاعدة البيانات وفشل البريد أو الإشعارات.
- إعدادات إنتاج خطرة مثل تشغيل debug، مع عرض النتيجة دون كشف قيم البيئة.

## نموذج البيانات المقترح

ينشأ جدول `security_events` مستقل، مع إمكانية ربطه بسجل العمليات الحالي، ويتضمن:

| الحقل | الغرض |
| --- | --- |
| `event_code` | رمز ثابت مثل `AUTH.BRUTE_FORCE` |
| `category` | مصادقة، صلاحيات، طلبات، ملفات، تشغيل، سلامة بيانات |
| `severity` | معلومات، منخفض، متوسط، مرتفع، حرج |
| `confidence` | درجة الثقة في التصنيف |
| `status` | جديد، قيد التحقيق، محتوى، محلول، إنذار كاذب |
| `source_ip` و`user_agent` | المصدر والجهاز بعد تطبيق سياسة الخصوصية |
| `route` و`http_method` | الهدف التقني للطلب |
| `actor_type` و`actor_id` | صاحب الحساب إن عرف |
| `target_type` و`target_id` | المورد المستهدف إن وجد |
| `occurrences` | عدد الأحداث المجمعة |
| `first_seen_at` و`last_seen_at` | نافذة التكرار |
| `detected_at` و`contained_at` و`resolved_at` | أزمنة دورة الحادث |
| `fingerprint` | بصمة لتجميع التكرارات المتطابقة |
| `evidence` | أدلة JSON منقحة من الأسرار والبيانات الحساسة |
| `resolution` | ملخص الإجراء والنتيجة |
| `assigned_to` و`acknowledged_by` | المسؤول ومستلم البلاغ |

ينشأ كذلك سجل زمني غير قابل للتحرير المباشر لتغييرات حالة الحادث وملاحظات التحقيق والأوامر المنفذة. لا تحفظ كلمات المرور أو رموز CSRF أو session cookies أو Authorization headers أو أسرار `.env` في الأدلة مطلقًا.

## دورة حياة الحادث

`رُصد ← صُنّف ← أُبلغ عنه ← استلمه المدير ← قيد التحقيق ← تم الاحتواء ← تم الحل والتحقق`

يمكن الانتقال إلى **إنذار كاذب** بسبب موثق. وكل انتقال يسجل الفاعل والتوقيت والملاحظة. وعبارة **تم الحل** لا تظهر إلا بعد تنفيذ فحص تحقق ناجح؛ أما إيقاف التكرار مؤقتًا فيوصف بأنه **تم الاحتواء**.

## مستويات الخطورة والخطاب

| المستوى | الخطاب المختصر | مثال الإجراء |
| --- | --- | --- |
| معلومات | سيدي، ورد تقرير اعتيادي | تسجيل فقط |
| منخفض | سيدي، رصدنا حركة غير معتادة | مراقبة وتجميع |
| متوسط | سيدي، توجد محاولة تستحق المراقبة | تنبيه المدير وتقييد المعدل |
| مرتفع | سيدي، قبضنا على محاولة اعتداء نشطة | احتواء مؤقت وفتح حادث |
| حرج | سيدي، نعلن حالة استنفار | إشعار عاجل وقرار إداري موثق |

يحدد المستوى من الأثر المحتمل، عدد التكرارات، حساسية الهدف، ودرجة الثقة. لا يعتمد على اللون وحده، بل يظهر نص الحالة والأيقونة والشرح التقني.

## مواصفات واجهة مركز القيادة

### رأس الموقف

يعرض ملخصًا مثل:

> **سيدي، الوضع تحت المراقبة. رصدنا ثلاثة أحداث خلال آخر 24 ساعة؛ تم احتواء حدثين، وحدث واحد ينتظر أمرك.**

ويعرض وقت آخر فحص وحالة المراقبة، مع تجنب الادعاء بأن النظام آمن بنسبة 100%.

### بطاقات الملخص

- حالة النظام: آمن تشغيليًا، تحت المراقبة، إنذار، أو حرج.
- التهديدات النشطة وأعلى درجة خطورة.
- الحوادث التي احتويت اليوم.
- البلاغات التي تحتاج قرار المدير.
- مشكلات التشغيل المفتوحة.
- محاولات الدخول الفاشلة خلال الساعة واليوم.

### سجل البلاغات

يعرض لكل بلاغ: الرقم، الرسالة العسكرية، التصنيف التقني، الخطورة والثقة، المصدر المنقح، أول وآخر رصد، عدد التكرارات، الإجراء الآلي، الحالة، والمسؤول. مثال:

> **بلاغ ميداني SEC-2026-0041 — سيدي، قبضنا على محاولة اقتحام متكررة لحساب إداري.**
>
> التصنيف التقني: 18 محاولة مصادقة خلال أربع دقائق.
>
> الإجراء: تقييد المصدر مؤقتًا. الحالة: تم الاحتواء. المطلوب: مراجعة الحساب.

ومثال تشغيلي:

> **بلاغ فني OPS-2026-0019 — سيدي، تعطلت ثلاث مهام خلفية أثناء إرسال الإشعارات.**
>
> أعاد النظام المحاولة مرتين، وما زال البلاغ يحتاج تدخلًا.

### البحث والفلاتر

الفترة، الخطورة، النوع، الحالة، المستخدم، المتجر، IP المنقح، رمز الحادث، يحتاج أمرًا، عولج تلقائيًا، إنذار كاذب، ومشكلات تشغيل فقط. يجب تنفيذ الترقيم من الخادم ومنع استعلامات بحث غير محدودة.

### أوامر المدير

- استلام البلاغ وتعيينه لمسؤول.
- إضافة ملاحظة تحقيق.
- اعتماد الاحتواء أو تعليم البلاغ كإنذار كاذب مع السبب.
- إغلاق البلاغ بعد التحقق.
- فتح تذكرة متابعة وتنزيل تقرير منقح.
- تقييد مصدر مؤقتًا أو إبطال جلسات أو فرض إعادة تعيين كلمة المرور فقط بعد تأكيد واضح ووفق صلاحية مستقلة.

لا يوجد زر **«إصلاح كل شيء»**. كل إجراء حساس منفصل، محدود المدة إن أمكن، قابل للتراجع، محمي بـCSRF، ويتطلب سببًا ويسجل في سجل التدقيق.

## الالتزام بالهوية البصرية وقواعد المشروع

- الوضع المظلم هو الافتراضي، ويجب اختبار المظلم والفاتح دون تغيير الألوان المعتمدة.
- تستخدم مكونات وكلاسات `ui-*` المركزية مثل `ui-card` و`ui-alert` و`ui-badge` و`ui-table` و`ui-btn`.
- يمنع `<style>` و`style="..."` وCSS عبر `@push` داخل Blade، ويضاف أي نمط ناقص إلى `resources/css/app.css` فقط.
- تستخدم ألوان الحالات المعتمدة: الأخضر للنجاح، الأصفر للتحذير، الأحمر للخطر، والأزرق للمعلومة؛ ولا يستخدم اللون وحده لنقل المعنى.
- الواجهة عربية RTL بخط Cairo، والنص التشغيلي واضح ومقروء، والتولتيب يشرح المصطلح ولا يخفي معلومة أساسية.
- لا يعدل التنفيذ أي حساب مالي أو مخزون أو تقرير أو نتيجة سلامة بيانات تلقائيًا. الفحص يرصد ويبلغ فقط، وأي إصلاح في هذه المجالات يصبح مهمة منفصلة بموافقة المالك.
- جميع مسارات المركز تحت مجموعة الأدمن المحمية، مع Authorization من الخادم لا بمجرد إخفاء الأزرار.

## الخطة التنفيذية — ثلاث خطوات فقط

### الخطوة الأولى: تأسيس الرصد الآمن وإصلاح المصادقة

**التنفيذ:**

- إضافة migrations وModels للأحداث الأمنية وتاريخ حالاتها، مع الفهارس وسياسة الاحتفاظ.
- إنشاء `SecurityEventService` موحد للتسجيل والتجميع والتصنيف وتنقيح الأدلة.
- التقاط أحداث المصادقة، وتجاوز الصلاحيات، والاستثناءات المهمة، وفشل Jobs، وفحوص التشغيل الدورية.
- إصلاح Rate Limiting للمصادقة بحيث لا يمسح عداد الحساب النشط قبل الفحص، واستخدام مفتاح يمنع التخمين الموزع وحجب حساب الضحية.
- منع أي احتواء تلقائي دائم في هذه المرحلة؛ المسموح تسجيل وتنبيه وتقييد مؤقت محافظ فقط.

**معايير القبول:**

- تسجل المحاولة الفاشلة دون كلمة مرور أو token، وتتجمع التكرارات الصحيحة في حادث واحد.
- تثبت الاختبارات أن الحد يعمل للحساب الموجود وغير الموجود، وأن نجاح الدخول فقط يصفر العداد المناسب.
- لا يستطيع مهاجم إيقاف حساب الضحية بتكرار كلمة مرور خاطئة.
- لا تغير الفحوص أي بيانات مالية أو مخزنية أو صلاحيات تجارية.

**بوابة الانتقال:** لا تبدأ الخطوة الثانية حتى تنجح اختبارات المصادقة والتجميع والتنقيح، وتراجع عينة السجلات للتأكد من خلوها من الأسرار.

### الخطوة الثانية: بناء مركز القيادة وفق الهوية البصرية

**التنفيذ:**

- إضافة Controller وForm Requests وPolicies/Authorization ومسارات تحت حماية الأدمن الحالية.
- بناء صفحة الملخص، سجل البلاغات، صفحة التفاصيل، الفلاتر، الاستلام، التعيين، الملاحظات وتحديث الحالة.
- إضافة رابط **القيادة الأمنية** إلى السايدبار، وإضافة الأنماط الناقصة إلى CSS المركزي فقط.
- تفعيل الإشعارات للأحداث المرتفعة والحرجة، وعرض الصياغة العسكرية مع الوصف التقني.
- دعم الموبايل ولوحة المفاتيح وقارئات الشاشة والحالات الفارغة والتحميل والخطأ.

**معايير القبول:**

- لا يستطيع غير المدير الوصول إلى الصفحة أو نقاطها النهائية، حتى بطلب مباشر.
- تطابق الأعداد الفلاتر والصفوف، ويعمل الترقيم دون تحميل جميع الأحداث.
- لا يوجد CSS داخل Blade ولا ألوان خارج التوكِنز المركزية.
- تنجح مراجعة الوضعين المظلم والفاتح على الهاتف وسطح المكتب، وتبقى الحالة مفهومة دون الاعتماد على اللون.
- لا يعرض المصدر أو الأدلة أي سر أو بيانات حساسة كاملة.

**بوابة الانتقال:** لا تبدأ الخطوة الثالثة حتى تنجح اختبارات Feature والصلاحيات، ومراجعة الهوية البصرية، ومراجعة يدوية لرسائل كل مستوى خطورة.

### الخطوة الثالثة: تفعيل الاستجابة والتحقق والإطلاق

**التنفيذ:**

- إضافة إجراءات الاستجابة المعتمدة: تقييد IP مؤقت، إبطال جلسات، فرض إعادة تعيين كلمة المرور، فتح تذكرة، وإغلاق موثق؛ كل إجراء مستقل وله تأكيد وسبب وخطة رجوع.
- إضافة Playbook واضح لكل فئة، وفحص تحقق يفرق بين الاحتواء والحل.
- تشغيل تجريبي في وضع الرصد، وضبط الحدود من البيانات الفعلية لتقليل الإنذارات الكاذبة قبل تفعيل الاستجابة.
- إضافة تنظيف وأرشفة يدويين من صفحة الأمن، وفحص اقتصادي أثناء نشاط جلسة الأدمن كل 15 دقيقة، ومراقبة ذاتية وتقرير يدوي عن زمن الرصد والاحتواء والحل؛ دون Laravel Scheduler أو Cron. وأي صيانة مستقبلية خاصة بنظام توضع داخل الصفحة التي تخدم ذلك النظام فقط.
- توثيق التشغيل والاسترجاع، ثم إطلاق تدريجي مع إمكانية تعطيل الاستجابة الآلية دون فقد الرصد.

**معايير القبول:**

- كل أمر حساس محمي ومؤكد ومسجل ويمكن معرفة من نفذه ولماذا ونتيجته.
- لا ينقل الحادث إلى **تم الحل** إلا بعد نجاح فحص التحقق.
- يؤدي فشل الإجراء إلى حالة واضحة وتنبيه، ولا يبتلع الخطأ أو يدعي النجاح.
- تنجح اختبارات Unit وFeature والتكامل، وفحص البناء، واختبار rollback في بيئة غير إنتاجية.
- يعتمد المالك الحدود والإجراءات الآلية وتقرير الإطلاق النهائي قبل تفعيلها في الإنتاج.

## الاختبارات الإلزامية عبر الخطوات الثلاث

- اختبارات Unit للتصنيف، البصمة، التجميع، الخطورة، التنقيح، وانتقالات الحالة.
- اختبارات Feature للمصادقة وRate Limiting وCSRF والصلاحيات والفلاتر والأوامر الحساسة.
- اختبارات تمنع IDOR وتثبت أن إخفاء الزر ليس وسيلة الحماية الوحيدة.
- اختبارات للأحداث المتزامنة تمنع تكرار الحادث أو ضياع عداد التكرار.
- فحص عدم تخزين password وtoken وcookie وAuthorization وأسرار البيئة.
- فحص بصري للمظلم والفاتح، الهاتف وسطح المكتب، حالات النجاح والتحذير والخطر والمعلومة، والوصول بلوحة المفاتيح.
- اختبار فحص جلسة الأدمن وQueue والفشل وإعادة المحاولة والتنبيه والتنظيف اليدوي وسياسة الاحتفاظ.

## تعريف الاكتمال النهائي

يعد مركز القيادة مكتملًا عندما يرصد المصادر المعتمدة دون أسرار، ويجمع الأحداث ويصنفها بدقة قابلة للشرح، ويعرضها للمدير فقط وفق الهوية البصرية، ويوثق دورة الحادث كاملة، وينفذ الاستجابات المعتمدة بأمان وقابلية رجوع، ويميز بصدق بين الرصد والاحتواء والحل، وتنجح جميع الاختبارات وبوابات القبول الواردة في الخطوات الثلاث.
