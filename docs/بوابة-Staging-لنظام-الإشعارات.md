# بوابة Staging لنظام الإشعارات

**مرجع البداية:** `AMON-HANDOFF-NOTIFICATIONS-2026-09-25`

هذه البوابة تثبت نظام الإشعارات الحالي بالتوازي مع تأسيس PWA، وقبل فتح API خاص بـFlutter. لا تضيف
Migration، ولا تكتب في قاعدة الإنتاج، ولا تغيّر قواعد المستلمين أو الحذف.

## 1. الفحص الثابت الآمن

نفذ محليًا وفي CI:

```bash
npm run test:notifications
```

يفحص الأمر وجود مكونات النظام وعقود العزل والتشغيل التالية:

- OneSignal يعمل من Job يطبق `ShouldQueue` وله `tries` و`timeout` و`backoff`.
- طلب HTTP الخارجي له مهلة اتصال واستجابة وRetry محدود.
- مفتاح OneSignal لا يدخل حقول السجل التشغيلي.
- تنظيف الإشعارات مجدول دون تداخل ويدعم `--dry-run`.
- قراءة الإشعارات لا تنفذ حذفًا عشوائيًا.
- API يقيد النتائج بالمستلم ويمنع التخزين المشترك.
- مسارات المالك والمحاسب محددة السرعة.
- PHPUnit مجبر على SQLite داخل الذاكرة لحماية البيانات الحقيقية.
- تأسيس PWA النصي موجود، وأيقونات PNG الثنائية ما زالت غير موجودة.

هذا فحص عقد وتشغيل أولي، ولا يثبت اتصال قاعدة البيانات أو عمل Queue worker.

## 2. فحص متغيرات Staging

شغّل الفحص في عملية تستقبل متغيرات Staging الفعلية:

```bash
APP_ENV=staging QUEUE_CONNECTION=database npm run test:notifications -- --staging-env
```

يمكن استبدال `database` بـRedis أو أي Driver غير متزامن معتمد في الاستضافة.
يجب ألا تكون القيمة `sync` أو `null`. لا تضع مفتاح OneSignal في سطر الأمر أو
السجلات؛ يكفي التحقق منه من صفحة الإعدادات الإدارية المحمية.

## 3. أوامر Laravel على Staging

نفذ على نسخة Staging فقط، بعد أخذ نسخة احتياطية قابلة للاستعادة:

```bash
php artisan about
php artisan route:list --path=notifications
php artisan schedule:list
php artisan notifications:cleanup --dry-run
php artisan queue:failed
```

معايير النجاح:

- تظهر مسارات الإشعارات خلف حارس المالك أو المحاسب المناسب.
- يظهر `notifications:cleanup` يوميًا الساعة 02:30 دون تداخل.
- يعرض `--dry-run` العدد ولا يحذف أي سجل.
- لا توجد Failed Jobs قديمة غير مفهومة قبل بدء الاختبار.

## 4. تشغيل العامل والمجدول

يجب أن تدير الاستضافة Queue worker بمدير عمليات مثل Supervisor أو خدمة المنصة،
وأن تستدعي Scheduler مرة كل دقيقة. لا تشغل `queue:work` داخل طلب ويب.

مثال فحص يدوي مؤقت على Staging:

```bash
php artisan queue:work --stop-when-empty --tries=3 --timeout=30
php artisan schedule:run
```

بعد تغيير الكود في النشر شغّل أمر إعادة تحميل العمال الذي تدعمه بيئتك، مثل:

```bash
php artisan queue:restart
```

## 5. مصفوفة اختبار العزل

استخدم حسابات ومتاجر تجريبية فقط:

| السيناريو | النتيجة المطلوبة |
|---|---|
| مالك يفتح إشعاره المباشر | يظهر له ويمكن تعليمه كمقروء |
| مالك آخر يستخدم رقم الإشعار نفسه | 404 ولا تتغير العلامات |
| محاسب ومعرّفه يساوي معرف مالك | لا يرى إشعار المالك |
| محاسب يخفي إشعارًا | يختفي عنه فقط |
| إشعار متجر | يظهر لمالك المتجر المصرح فقط |
| رابط خارجي داخل payload | لا يعرض كرابط قابل للفتح |
| Broadcast | يصل فقط إلى أنواع الحسابات المعتمدة |

سجل Request ID ووقت الاستجابة وعدد استعلامات كل سيناريو، دون تسجيل الرسالة
الحساسة أو API key أو Device Token كاملًا.

## 6. اختبار OneSignal المحدود

1. سجل جهازين تجريبيين، أحدهما للمالك والآخر للمحاسب.
2. أرسل إشعارًا بعنوان واضح أنه اختبار Staging.
3. تحقق أن طلب الويب يعيد الاستجابة قبل اكتمال اتصال OneSignal.
4. راقب Queue حتى تصبح المهمة مكتملة.
5. عطّل الإعداد مؤقتًا في Staging وتحقق من Retry ثم Failed Job دون كشف المفتاح.
6. لا تستخدم الإرسال العام `All` في هذا الاختبار.

## 7. القياسات المطلوبة

سجل في نتيجة المهمة التالية:

- p50 وp95 لقائمة الإشعارات والعداد.
- عدد استعلامات قاعدة البيانات لكل Endpoint.
- Queue lag قبل الإرسال وبعده.
- عدد المحاولات والفشل النهائي.
- عدد السجلات التي يعرضها cleanup dry-run وزمن العد.
- استهلاك الذاكرة عند قائمة كبيرة ممثلة للحجم المتوقع.

## قرار المرور

لا تعتبر البوابة ناجحة إلا إذا:

- نجح `npm run test:notifications` وFeature Tests الفعلية.
- نجحت جميع حالات العزل دون تعديل بيانات حساب آخر.
- ثبت تشغيل Worker وScheduler بعد إعادة تشغيل الخادم.
- لم تظهر أسرار أو Device Tokens في السجلات.
- وثقت القياسات والمشكلات المتبقية.

عند الفشل لا تبدأ PWA. افتح إصلاحًا صغيرًا لنظام الإشعارات وحده، ثم أعد هذه
البوابة كاملة.
