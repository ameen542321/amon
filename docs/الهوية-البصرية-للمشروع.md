# الهوية البصرية للمشروع

> ملاحظة تنفيذ: وُثقت في هذا المرجع أدوار الزر المشتركة بعد تطبيق إصلاحات المكونات المركزية.

> هذا المستند هو المرجع الرسمي الأول لأي عمل يخص واجهات المشروع أو الهوية البصرية أو CSS أو مكوّنات Blade.
> لا يبدأ أي تعديل بصري قبل قراءته كاملًا، ولا تُعتمد ألوان أو أنماط من صفحات قديمة إلا إذا كانت موثقة هنا أو في CSS المركزي المعتمد.

## 1. الهدف والنطاق

يحوّل هذا المستند الهوية البصرية من قواعد عامة إلى نظام تصميم عملي قابل للتطبيق والمراجعة داخل المشروع.

الأهداف الملزمة:

1. الحفاظ على جودة الوضع المظلم لأنه الوضع الافتراضي للمشروع.
2. دعم الوضع الفاتح دون نصوص باهتة أو حدود مخفية أو بطاقات غير واضحة.
3. توحيد البطاقات، الجداول، الحقول، الأزرار، المودالات، الشارات، التنبيهات، التولتيب، الهيدر، السايدبار، وصفحات الدخول.
4. منع CSS داخل Blade ومنع اختيار الألوان مباشرة داخل الواجهات.
5. جعل الإرشادات والتولتيب مفهومة للمالك أو المحاسب أو المستخدم التشغيلي، لا للمبرمج فقط.
6. حماية منطق النظام المالي والمخزني والصلاحيات من أي تعديل جانبي أثناء العمل البصري.

ينطبق هذا المستند على:

- ملفات Blade داخل `resources/views`.
- CSS المركزي داخل `resources/css/app.css` وأي ملف CSS عام معتمد.
- مكوّنات Blade المشتركة، خصوصًا `resources/views/components/ui`.
- صفحات الويب التفاعلية داخل لوحة التحكم وصفحات المصادقة والإدارة والتقارير.

صفحات الطباعة وPDF لها استثناء بصري محدود لأنها غالبًا تحتاج خلفية فاتحة وأبعاد طباعة، لكن يمنع تعديل محتواها الحسابي أو المالي دون موافقة صريحة.

### 1.1 هوية الطباعة والبريد الإلكتروني

- يبقى **Cairo** الخط الأول في صفحات الطباعة وPDF والبريد، مع `DejaVu Sans` أو `Amiri` كبدائل تقنية لمحركات PDF فقط.
- يسمح بـ`<style>` مضمّن في قالب الطباعة/PDF لأن بعض محركات التوليد لا تحمل CSS التطبيق، لكن تجمع القواعد في رأس القالب ويمنع تكرار `style="..."` على العناصر متى أمكن استخدام كلاس داخل القالب.
- الحد الأدنى للنص المطبوع `10px` للملاحظات الثانوية، و`11px` للنصوص الجدولية المهمة؛ لا تستخدم أحجام `7px` أو `8px` أو `9px`.
- خلفية مستند الطباعة بيضاء، والنص داكن، وتستخدم درجات Slate والحالات الأخضر/الأحمر/الأزرق الموثقة دون وردي أو برتقالي أو بنفسجي.
- أزرار معاينة الطباعة التي تظهر في المتصفح تلتزم بأدوار الهوية: رجوع ثانوي، تحميل/معلومة أزرق، وطباعة/تأكيد أخضر، وتختفي عند الطباعة.
- البريد الإلكتروني يستعمل ألوان العلامة والأسطح المعتمدة، ويحافظ على inline CSS فقط لتوافق عملاء البريد.

## 2. قواعد العمل قبل أي تعديل

### 2.1 تصنيف التعديل

قبل تعديل أي واجهة يجب تحديد نوع العمل، ثم الرجوع إلى هذا المستند أولًا قبل كتابة أي كلاس أو تغيير أي لون أو حجم أو حدود:

| النوع | أمثلة | القرار |
| --- | --- | --- |
| بصري فقط | لون، تباعد، حجم زر، ترتيب بطاقة، تحسين responsive | مسموح فقط بعد مطابقة هذا المستند واستخدام CSS مركزي |
| بصري مع احتمال منطق | إخفاء/إظهار مبلغ، تغيير ترتيب حسابات، تعديل حالات فاتورة، زر يعتمد على صلاحية | توقف وأبلغ صاحب المشروع قبل التنفيذ |
| منطق برمجي | Controller، Service، Migration، حساب مالي، تقرير، مخزون، صلاحيات | ممنوع ضمن العمل البصري إلا بعد موافقة واضحة |

### 2.2 ممنوع تعديل المنطق أثناء العمل البصري

يمنع تنفيذ أي تعديل يمس:

- الحسابات المالية، الأرباح، المديونيات، الآجل، التحصيلات، والموازنات.
- الشفتات والكاش المتوقع وحركات النقد.
- المخزون والجرد وحركات المنتجات.
- الفواتير والتقارير وPDF.
- صلاحيات المستخدمين والحسابات.
- أي Migration أو Controller أو Service يؤثر على البيانات أو النتائج.

إذا ظهر أن المشكلة البصرية لا تُحل إلا بتعديل منطق، يجب التوقف وإرسال ملخص لصاحب المشروع يتضمن:

1. ما الذي يحتاج تعديلًا.
2. لماذا لا يكفي الإصلاح البصري.
3. الأثر المتوقع على البيانات أو النتائج.
4. مخاطر التعديل.
5. خطة الرجوع الآمنة.

## 3. قاعدة CSS وBlade

### 3.1 ممنوع داخل Blade

قاعدة ملزمة: أي تعديل أو إصلاح أو إضافة في المشروع تخص الواجهة يجب أن تمر على هذا المستند أولًا، ثم تستخدم كلاسًا مركزيًا من CSS؛ لا يسمح بأن تتحول الواجهة إلى مكان لتعريف الألوان أو المسافات أو الأحجام.

لا يسمح داخل ملفات Blade أو الواجهات بـ:

- وسم `<style>`.
- خاصية `style="..."`.
- `@push('styles')` أو `@section('styles')` لإضافة CSS محلي غير مركزي.
- تحميل Tailwind CDN أو CSS خارجي عشوائي داخل صفحة.
- اختيار لون مباشر مثل `text-gray-500` أو `bg-blue-600` أو `border-red-500` لمعالجة مشكلة محلية.
- بناء شكل زر أو بطاقة كامل بكلاسات Tailwind مباشرة إذا كان له بديل `ui-*`.
- علاج مشكلة حدود أو مسافات بإضافة CSS محلي داخل الواجهة؛ البديل يكون كلاسًا مركزيًا في `resources/css/app.css`.
- التحكم بالعرض أو التمرير عبر JavaScript بكتابة `element.style...` داخل الواجهة؛ استخدم إضافة/إزالة كلاس مركزي مثل `hidden` أو `ui-scroll-lock`.

### 3.2 المسموح داخل Blade

يسمح داخل Blade بـ:

- استخدام مكوّن Blade معتمد مثل `x-ui.button` و`x-ui.card` و`x-ui.badge` عند توفره.
- استخدام كلاس مركزي موثق مثل `ui-card`, `ui-btn`, `ui-input`, `ui-alert`, `ui-table`, `auth-shell`.
- استخدام كلاسات التخطيط العامة غير اللونية مثل `grid`, `flex`, `gap-4`, `p-4`, `md:grid-cols-2` عند الحاجة.
- تمرير بيانات وعناوين وروابط وحالات فقط، دون تحديد درجات اللون داخل الصفحة.

قاعدة مختصرة:

> Blade يعرض الهيكل والبيانات. CSS المركزي يحدد الشكل والألوان والحالات.

أي واجهة تحتاج تعديلًا بصريًا خاصًا بها يعني غالبًا أن هناك كلاسًا مركزيًا ناقصًا؛ أضف الكلاس في CSS المركزي ثم استخدمه في الواجهة، ولا تكرر الحل داخل كل صفحة.

## 4. الوضعان: المظلم والفاتح

### 4.1 القاعدة العامة

الوضع الافتراضي هو **المظلم** عبر متغيرات `:root` و`html.dark`، أما الوضع الفاتح فيفعل فقط عبر `html.light`.

القواعد:

1. لا يتم إصلاح الوضع الفاتح بتخريب الوضع المظلم.
2. لا يتم إصلاح الوضع المظلم بإهمال الوضع الفاتح.
3. كل مكوّن رئيسي يجب أن يملك خلفية، نصًا، حدودًا، وحالة hover/focus واضحة في الوضعين.
4. أي صفحة يتم تعديلها يجب فحصها بصريًا في الوضعين.
5. لا تستخدم بطاقة بيضاء عشوائية في الوضع المظلم، ولا نصًا باهتًا في الوضع الفاتح.

## 5. نظام الألوان

### 5.1 قواعد عامة للألوان

1. الألوان المعتمدة هي: لون العلامة، درجات Slate للأسطح والنصوص والحدود، وألوان الحالات المركزية فقط.
2. يمنع استخدام البنفسجي، الوردي، الفوشيا، البرتقالي، أو أي درجات قريبة منها نهائيًا، ويشمل ذلك درجات Rose/Pink في Tailwind: لا نصوص، لا خلفيات، لا إطارات، لا أيقونات، ولا تأثيرات.
3. الأزرق لا يستخدم كهوية عامة؛ يسمح به فقط عبر حالة المعلومة المركزية للتولتيب المعلوماتي أو التنبيهات المعلوماتية.
4. الأصفر لا يستخدم كهوية عامة؛ يسمح به فقط عبر حالة التحذير المركزية لتولتيب التنبيه أو التحذيرات التشغيلية.
5. لا تستخدم `#64748b` أو `#94a3b8` كخلفية لزر أو بطاقة؛ هي درجات نص هادئة فقط.
6. لا تستخدم ألوان الحالة لتزيين بطاقة كاملة إلا إذا كانت البطاقة نفسها بطاقة حالة.
7. لا توضع خلفية خاصة خلف عنوان أو نص منفرد؛ الخلفية تكون للمكوّن الكامل.
8. لا تضاف أي ألوان جديدة إلى المستند أو CSS أو الواجهات، ولا يعدل هذا المستند لإضافة لون أو تغيير لون إلا بموافقة صاحب المشروع صراحة.

## 6. Typography والنصوص

### 6.1 الخط الأساسي واللغة والاتجاه

- الخط الأساسي المعتمد للمشروع هو خط **Cairo** العربي.
- يُحمّل الخط العربي المتغير `cairo-arabic-wght-normal.woff2` محليًا من `public/fonts/cairo` للأوزان من `200` إلى `1000`، مع بقاء ملفات TTF المحلية للمحارف غير العربية؛ ليصل Cairo إلى صفحات المصادقة ولوحة التحكم دون اتصال خارجي.
- يصرّح قالب المصادقة وقالب لوحة التحكم مسبقًا بتحميل ملف WOFF2 العربي المحلي، وتطبق قاعدة `auth-page` عائلة Cairo مباشرةً على الصفحة وعناصر النماذج؛ لا يستخدم `font-sans` هنا لأنه قد يعيد خط النظام الافتراضي عند اختلاف إصدار Tailwind.
- تبدأ قوالب المصادقة واللوحة بكلاس `ui-font-loading`، ولا يُظهر المحتوى إلا بعد تأكد وحدة `font-readiness` من جاهزية Cairo؛ لمنع ظهور خط النظام قبله.
- صفحات الدخول والاستعادة ترث `layouts.auth`. تبقى صفحتا الإيقاف والترحيب بوثيقتهما المستقلة لحماية عرضيهما المختلفين، لكنهما تحملان مدخل التطبيق وملف WOFF2 العربي المحلي ويستخدم جسمهما `auth-page` نفسه.
- يمنع تحميل Cairo من Google Fonts داخل قالب منفرد؛ القالبان يستخدمان مدخل التطبيق نفسه، وتبقى ملفات الخط المحلية هي المصدر الموحد.
- تستخدم بدائل النظام فقط إذا تعذر تحميل Cairo، ولا يعتمد خط آخر كهوية إلا بموافقة صاحب المشروع.
- الواجهة عربية وRTL افتراضيًا.
- الأرقام المالية والتواريخ يمكن أن تحتوي إنجليزية/أرقام لاتينية، لكن يجب ألا تكسر اتجاه النص.
- استخدم لغة واضحة للمحاسب والمالك: “المبلغ المتبقي”، “إجمالي التحصيل”، “المخزون الحالي”، وليس مصطلحات تقنية مثل `balance_due`.

### 6.2 أحجام الخطوط المعتمدة

| الدور | الشاشات الصغيرة/اللمس | الشاشات المتوسطة | الشاشات الكبيرة | الاستخدام |
| --- | --- | --- | --- | --- |
| عنوان صفحة | `1.5rem` | `1.625rem` إلى `1.75rem` | `1.875rem` إلى `2rem` | اسم الصفحة أو العملية الأساسية |
| عنوان قسم/بطاقة | `1.125rem` إلى `1.25rem` | `1.25rem` | `1.25rem` إلى `1.375rem` | عناوين البطاقات والأقسام |
| نص أساسي | `1rem` | `1rem` إلى `1.0625rem` | `1.0625rem` | قراءة يومية وأرقام تشغيلية |
| نص ثانوي | `0.9375rem` إلى `1rem` | `1rem` | `1rem` | شروحات وتعليمات |
| نص صغير/ملاحظة | لا يقل عن `0.8125rem` | لا يقل عن `0.875rem` | لا يقل عن `0.875rem` | ملاحظات غير حرجة فقط |
| زر أو حقل لمس | لا يقل عن `1rem` | `1rem` | `1rem` إلى `1.0625rem` | أزرار وحقول قابلة للمس |
| نص داخل حدود/إطار | لا يقل عن `0.9375rem` | `1rem` | `1rem` | شارات، أزرار صغيرة، خلايا محاطة بحد |

قواعد أحجام الخط الثابتة:

1. لا يقل حجم النص التشغيلي المهم عن `0.9375rem` في أي شاشة.
2. يمنع استخدام `text-[8px]` أو `text-[9px]` أو أحجام مشابهة لأي نص يعتمد عليه المحاسب أو المالك، وتبقى فقط لزخارف غير مؤثرة بعد موافقة.
3. أزرار اللمس والحقول يجب أن تكون مقروءة ومريحة، ولا تصغر لمجرد احتواء النص.
4. العناوين لا تعتمد على الحجم وحده؛ يجب أن تستخدم وزنًا واضحًا ولون `--ui-text`.
5. النصوص الطويلة داخل بطاقة يجب أن تقسم أو تنقل إلى تولتيب/مودال مساعدة حسب قواعد القسم 8.8.
6. أي نص داخل إطار أو حدود يجب أن يظهر في منتصف المساحة بصريًا، مع `line-height` مناسب وpadding متوازن، لا قريبًا من الأعلى أو ملتصقًا بجانب.
7. لا يتم تغيير درجات الخط أو أحجامه محليًا داخل صفحة لحل مشكلة ضيق؛ الحل يكون بتعديل التخطيط أو تحويل الشرح إلى تولتيب/مودال.

| عنوان بطاقة | `ui-title` | اسم المكوّن أو القسم |
| نص شرح مهم | `ui-text-soft` | تعليمات يعتمد عليها المستخدم |
| ملاحظة هادئة | `ui-text-muted` | معلومات ثانوية لا تؤثر على القرار |
| رقم مالي أو مخزني | `--ui-text` أو حالة معتمدة | لا يستخدم `ui-text-muted` |

قواعد النصوص:

1. لا تستخدم النص الهادئ للتعليمات أو القيم المالية أو التحذيرات.
2. كل صفحة يجب أن تملك عنوانًا واضحًا ووصفًا عند الحاجة.
3. لا تزيد فقرات الشرح داخل البطاقات؛ استخدم جملًا قصيرة ومباشرة.
4. في الجداول، رؤوس الأعمدة تستخدم نصًا ثانويًا واضحًا لا هادئًا جدًا.

## 7. المسافات، الحواف، والظلال

### 7.1 المسافات

القيم العملية الحالية:

| العنصر | المسافة المقترحة |
| --- | --- |
| بطاقة صغيرة | `p-4` |
| بطاقة عادية | `p-5` |
| بطاقة كبيرة أو مودال | `p-6` أو `1.25rem` داخل CSS |
| خلية جدول | `1rem` |
| زر | `.75rem 1rem` |
| حقل إدخال | `.75rem 1rem` |

القواعد:

- لا يلتصق النص بالحد أبدًا.
- المسافات داخل البطاقة يجب أن تكون متوازنة من الأعلى والأسفل واليمين واليسار.
- أي عنصر له حد أو إطار يجب أن يملك padding داخليًا متوازنًا يجعل النص في المنتصف تمامًا بصريًا، خصوصًا الأزرار والشارات وخلايا الجداول والتنبيهات.
- عند وجود نص داخل إطار صغير، يجب ضبط `align-items: center` و`justify-content: center` أو ما يعادلهما في الكلاس المركزي، لا عبر CSS داخل Blade.
- لا تُحل مشكلة المسافات بـ CSS داخل Blade.

### 7.2 نصف القطر والحدود

| العنصر | الشكل المعتمد |
| --- | --- |
| بطاقة | `1rem` |
| مودال | `1.25rem` |
| زر/حقل | `.875rem` |
| شارة | `999px` |
| Tooltip صغير | `.375rem` أو أكبر عند الحاجة |

القواعد:

- الحدود تستخدم `--ui-border` أو `--ui-border-soft` فقط.
- في الوضع المظلم يجب أن تكون حدود البطاقات أوضح من الخلفية، ولا تعتمد البطاقة على الظل وحده.
- لا تستخدم حدودًا حمراء/برتقالية صارخة للبطاقات. الاستثناء: زر إغلاق مودال أو زر خطر واضح.
- عند إصلاح الحدود أو الإطارات، تكون الأولوية لتوسيط النص داخل الإطار قبل إضافة أي لون أو ظل جديد.
- أي سطر محاط بحد داخل بطاقة أو مودال، مثل سطر “شغل اليد والمبلغ” في معاينة التحصيل أو سطر “المتوقع في الصندوق” في بطاقة الموازنة، يجب أن يستخدم إطارًا مركزيًا موحدًا مثل `ui-inline-frame` أو `ui-frame-row`.
- أي حدود في المشروع تظهر معها مشكلة مسافات أو عدم توسيط للنص تعدل بنفس القاعدة المركزية، ولا يكتفى بإصلاح الصفحة المتضررة فقط إذا كان النمط متكررًا.
- الإطار الداخلي الموحد يجب أن يحتوي `border: 1px solid var(--ui-border)`, خلفية من أسطح المشروع، padding لا يقل عن `.75rem`, ومحاذاة وسطية للنص والقيم.
- يمنع استخدام `border-current`, أو حدود حالة مستقلة، أو إطار بلون خارج الهوية لهذه الأسطر؛ الحالة تظهر بالنص أو الشارة وليس بلون الإطار.

## 8. المكونات المعتمدة

### 8.1 الصفحة

استخدم `ui-page` كحاوية عامة عندما تحتاج الصفحة إلى وراثة ألوان الهوية.

متطلبات الصفحة:

- خلفية `--ui-bg`.
- نص `--ui-text`.
- دعم الوضعين.
- لا تعتمد الإجراءات المهمة على hover فقط.

### 8.2 البطاقات

الكلاسات المعتمدة:

- `ui-card`: بطاقة رئيسية.
- `ui-card-muted`: بطاقة أو منطقة ثانوية.
- `ui-surface-chip`: شريحة سطح صغيرة داخل بطاقة.

قواعد البطاقات:

1. البطاقة تعرض مجموعة معلومات أو إجراء، لا تستخدم كزخرفة فقط.
2. لا تضع خلفية منفصلة خلف عنوان البطاقة.
3. لا تستخدم ألوان حالة لبطاقة كاملة إلا إذا كانت بطاقة حالة فعلية.
4. إذا احتاجت البطاقة padding مختلفًا استخدم خيار المكوّن أو كلاس تخطيط غير لوني.

### 8.3 الأزرار

الكلاسات المعتمدة:

| الدور | الكلاس | الاستخدام |
| --- | --- | --- |
| أساسي | `ui-btn ui-btn-primary` | الإجراء الرئيسي في الصفحة |
| ثانوي | `ui-btn ui-btn-secondary` | رجوع، إلغاء، عرض تفاصيل |
| خطر | `ui-btn ui-btn-danger` | حذف، إيقاف، إجراء مؤذٍ |
| تحذير | `ui-btn ui-btn-warning` | إجراء محاسبي/تشغيلي يحتاج انتباه |

ألوان أزرار العمليات الموحدة في الوضعين:

| العملية | الكلاس المعتمد | الهوية اللونية في المظلم والفاتح | القاعدة |
| --- | --- | --- | --- |
| عرض أو فتح | `ui-btn ui-btn-secondary` | سطح ثانوي + حد مركزي + نص واضح | إجراء قراءة لا يغيّر البيانات |
| معاينة | `ui-btn ui-btn-info` | أزرق المعلومات المعتمد بخلفية ظاهرة | قراءة تفاصيل العملية دون تغييرها |
| إدارة | `ui-btn ui-btn-secondary` | سطح ثانوي + حد مركزي + نص واضح | دخول لإدارة حالة قائمة، وليس إنشاء جديد |
| تعديل | `ui-btn ui-btn-secondary` | سطح ثانوي + حد مركزي + نص واضح | لا يستخدم لونًا خاصًا حتى لا يختلط مع الإضافة أو الخطر |
| إضافة | `ui-btn ui-btn-primary` | خلفية لون العلامة `--ui-brand` في الوضعين، ولا تتحول إلى أسود في الفاتح | الإجراء الأساسي لإنشاء سجل جديد |
| حفظ | `ui-btn ui-btn-primary` | لون العلامة/الزر الأساسي حسب الوضع | تأكيد حفظ بيانات النموذج |
| تأكيد | `ui-btn ui-btn-success` | خلفية خضراء من حالة النجاح في الوضعين | تأكيد إجراء غير مؤذٍ بعد المراجعة |
| تحصيل | `ui-btn ui-btn-success` أو `ui-btn ui-btn-secondary` داخل مودال تابع | الأخضر إذا كان تنفيذ التحصيل، والثانوي إذا كان مجرد فتح/إدارة |
| كامل | `ui-btn ui-btn-success` | خلفية خضراء من حالة النجاح في الوضعين | تحصيل/تنفيذ كامل عند وضوح الأثر |
| جزئي | `ui-btn ui-btn-warning` | أصفر/بني التحذير المعتمد بخلفية ظاهرة | تنفيذ غير كامل يحتاج تمييزًا عن التحصيل الكامل |
| إلغاء | `ui-btn ui-btn-danger` | خلفية خطر حمراء ظاهرة دائمًا في الوضعين | إغلاق أو رجوع دون تنفيذ، حسب اتفاق المشروع |
| حذف أو إغلاق خطر | `ui-btn ui-btn-danger` | خلفية خطر حمراء ظاهرة دائمًا في الوضعين + نص واضح | إجراء مؤذٍ أو إغلاق نافذة يحتاج وضوحًا |
| إيقاف | `ui-btn ui-btn-danger` أو `ui-btn ui-btn-warning` حسب خطورة الأثر | خطر إذا يمنع الوصول، وتحذير إذا كان تنبيهًا مؤقتًا | لا يستخدم لونًا جديدًا |
| تفعيل | `ui-btn ui-btn-primary` | لون العلامة/الزر الأساسي حسب الوضع | إعادة تشغيل أو اعتماد حالة إيجابية |
| استرجاع | `ui-btn ui-btn-secondary` مع شارة/نص نجاح عند الحاجة | سطح ثانوي + إشارة نجاح نصية فقط | لا يستخدم لون خطر، لأنه عكس الحذف |

قواعد الأزرار:

- لا تستخدم أكثر من زر أساسي واحد داخل نفس المجموعة البصرية إلا عند وجود سبب واضح.
- الأزرار الأيقونية يجب أن تحتوي `aria-label` واضحًا.
- حالة التعطيل يجب أن تكون واضحة بصريًا ولا تعتمد على اللون فقط.
- كل زر يجب أن يكون نصه في المنتصف تمامًا أفقيًا وعموديًا، مع padding متوازن وعدم التصاق النص بالحد.
- لا يسمح أن يظهر زر أساسي بخلفية سوداء في الوضع الفاتح؛ الزر الأساسي يبقى بلون العلامة، والزر الثانوي يجب أن يملك خلفية سطح واضحة لا شفافة.
- نص الزر الأساسي في الوضع الفاتح يستخدم `--ui-text` فوق خلفية `--ui-brand` لضمان التباين في الحالة الأساسية و`hover`.
- أزرار عرض/فتح ومعاينة وإدارة وتعديل وإضافة وحفظ وتأكيد وإلغاء وكامل وجزئي وتحصيل وحذف وإيقاف وتفعيل واسترجاع يجب أن تلتزم بالجدول أعلاه في كل الصفحات.
- لا يكفي أن يحمل الزر اسم كلاس الحالة؛ يجب أن تكون خلفيته ممتلئة ومرئية في الوضعين، مع نص وحد واضحين، ويمنع الزر الشفاف لإجراءات المعاينة أو التحصيل الجزئي أو التأكيد أو الإلغاء.
- أي إصلاح يعتمد لألوان الأزرار أو أحجام النصوص أو تباعدها يصبح قاعدة عامة: عند العثور على العنصر نفسه في صفحة أخرى يطبق عليه الكلاس المركزي ذاته، ولا ينشأ حل خاص بالصفحة.
- مراتب النصوص داخل بطاقات العمليات ثابتة: الاسم أو العنوان `ui-text-body` أو أكبر، التاريخ والوصف `ui-text-meta`، والمبلغ لا يتجاوز العنوان بصريًا إلا إذا كان هو القيمة الأساسية للبطاقة.
- لا يستخدم الأزرق كزر عام أو للعلامة؛ يقتصر على إجراء معلومات واضح مثل المعاينة عبر `ui-btn-info`، ويبقى البنفسجي والوردي ممنوعين نهائيًا.
- لون التأكيد والتنفيذ الناجح أخضر (`ui-btn-success`) وليس تراكوزي؛ التراكوزي يبقى للعلامة أو إجراءات عامة غير تأكيدية.

### 8.4 الحقول والنماذج

الكلاس الأساسي: `ui-input`.

قواعد الحقول:

1. كل حقل يحتاج label واضحًا.
2. النص المساعد المهم يستخدم `ui-text-soft`.
3. الأخطاء تستخدم نظام الخطر المركزي.
4. focus يجب أن يظهر بوضوح عبر لون العلامة أو focus ring مركزي.
5. لا تضع placeholder كبديل عن label.
6. حقلا الكاش والشبكة في الدفع المختلط/الميكس يبدآن فارغين تمامًا دون قيمة أو placeholder رقمي، ولا يملأ أحدهما تلقائيًا من إجمالي العملية؛ يكتب المستخدم القيمتين ويحسب الإجمالي المقروء فقط بعد الإدخال.

### 8.5 الجداول

الكلاسات المعتمدة:

- `ui-table-wrap`: حاوية تمرير وحدود.
- `ui-table`: الجدول.
- `ui-table-head`: رأس جدول عند الحاجة.

قواعد الجداول:

1. الجداول تستخدم فقط للبيانات الجدولية الحقيقية.
2. الجداول الطويلة يجب أن تكون داخل تمرير أفقي أو تتحول إلى بطاقات مختصرة على الجوال.
3. الأعمدة المالية يجب أن تكون واضحة ومقروءة ولا تستخدم نصًا هادئًا.
4. لا تستخدم hover كوسيلة وحيدة لإظهار إجراء مهم.
5. صفوف الحالة تستخدم شارة أو نص حالة، وليس تلوينًا عشوائيًا للصف كاملًا.
6. سجل العمليات يتحول على الشاشات الصغيرة إلى صفوف/بطاقات رأسية تحمل أسماء الحقول؛ لا يكفي الاعتماد على تمرير أفقي يصعّب قراءة العملية.
7. إذا كانت للعملية ملاحظة أو وصف مسجل فيجب إظهاره داخل سجل العمليات، ولا يجوز إسقاطه من العرض المختصر.

### 8.6 المودالات والنوافذ

الكلاسات المعتمدة:

- `ui-modal-backdrop`.
- `ui-modal-panel`.
- `ui-modal-panel-wide` لنوافذ التفاصيل والجداول الواسعة، مع بقاء العرض مقيدًا بالشاشة.
- `ui-modal-panel-transfer` لنوافذ عرض التفاصيل؛ وهو الغلاف المعتمد المطابق بصريًا لنافذة التولتيب/المساعدة.
- `ui-help-modal-header`, `ui-help-modal-close`, `ui-help-modal-body` لرأس وجسم وإغلاق نوافذ عرض التفاصيل والمساعدة الهادئة.
- `ui-modal-close-danger` لزر الإغلاق إذا كان الإغلاق نفسه إجراء خطرًا أو جزءًا من تأكيد مؤذٍ، وليس لإغلاق نافذة تفاصيل عادية.
- `ui-modal-close-text-danger` لزر الإغلاق النصي في الإجراءات الخطرة فقط.

قواعد المودالات:

- نافذة المساعدة في صفحة إنشاء النقل المخزني هي مرجع شكل النافذة المركزي: خلفية التعتيم، السطح، الحد، الاستدارة، الظل، وقيود الارتفاع المتجاوبة.

1. يجب أن يكون للمودال عنوان واضح.
2. خلفية المودال والنافذة يجب أن تكون من خلفيات المشروع المعتمدة `--ui-bg` و`--ui-surface` و`--ui-surface-muted`، ويمنع أن تكون شاذة أو شفافة بشكل يضعف القراءة.
3. خلفية التعتيم خلف المودال لا تختار عشوائيًا ولا تكون شفافية زائدة تكشف الصفحة وتشتت المستخدم.
4. زر الإغلاق الأيقوني `X` يطابق زر نافذة النقل المخزني المرجعية: سطح هادئ، حد واضح، وحالة hover مركزية.
5. حرف `X` يجب أن يكون في منتصف الدائرة/المربع تمامًا أفقيًا وعموديًا، لذلك يكون الزر مربعًا بأبعاد ثابتة، `inline-flex`, `align-items: center`, `justify-content: center`, و`line-height: 1`.
6. زر الإغلاق الأيقوني يكون `X` أو أيقونة إغلاق داخل الزر الهادئ المركزي، مع `aria-label` واضح.
7. زر الإغلاق النصي يستخدم خلفية خطر حمراء مركزية ونصًا واضحًا مثل “إغلاق”.
8. كل زر إغلاق يجب أن يكون واضحًا وله `aria-label="إغلاق"` عند كونه أيقونيًا.
9. لا يوضع `bg-gray-900` أو خلفية منفصلة خلف عنوان المودال.
10. المحتوى الطويل يجب أن يكون قابلًا للتمرير دون كسر الصفحة.
11. إذا كان المودال يؤكد حذفًا أو إجراءً ماليًا، يجب أن تكون الصياغة واضحة ومباشرة.
12. المودال قطعة واحدة متصلة بصريًا؛ يمنع إنشاء هيدر ثابت أو `sticky` مع جسم مستقل التمرير أو بخلفية مختلفة. يتحرك العنوان وزر الإغلاق مع محتوى النافذة، ويكون التمرير على صندوق المودال كاملًا عند الحاجة.
13. نوافذ عرض التفاصيل العادية تستخدم شكل نافذة التولتيب/المساعدة نفسه: `ui-modal-panel-transfer` مع `ui-help-modal-header` و`ui-help-modal-close` و`ui-help-modal-body`، حتى تكون مطابقة بصريًا لنافذة المصباح في السطح والحد والاستدارة وزر الإغلاق.
14. لا يستخدم عنوان عام موحّد لكل النوافذ؛ يجب أن يكون العنوان محددًا حسب المحتوى مثل “إجمالي المبيعات”، “مصروفات تشغيلية”، “تفاصيل الرواتب والسحوبات”، أو “تفاصيل الطلبيات المعتمدة”.
15. لا تضغط البطاقة كاملة لفتح الشرح أو التفاصيل عندما تحتوي البطاقة نصوصًا وأرقامًا؛ توضع أيقونة المصباح بجانب اسم البطاقة للشرح، ويستخدم زر واضح مثل “عرض التفاصيل” عند وجود جدول أو نافذة تفاصيل.
16. أي قيمة داخل بطاقة تساوي صفرًا لا تعرض كسطر مستقل؛ إما تخفى البطاقة إذا كانت كلها صفرية أو تخفى الأسطر الصفرية داخلها.

### 8.7 الشارات والتنبيهات

- شارة عدد العمليات أو الإشعارات تستخدم `ui-count-badge` بخلفية خطر ظاهرة ونص واضح في الوضعين، ولا تعتمد على لون نص البطاقة أو حدودها.

الكلاسات المعتمدة:

- `ui-badge` مع `ui-badge-success|warning|danger|info`.
- `ui-alert` مع نوع حالة مثل `ui-alert-warning`.
- `ui-alert-row`, `ui-alert-meta`, `ui-alert-active` عند الحاجة.

قواعد الاستخدام:

- الشارة للحالة القصيرة: نشط، متأخر، مكتمل، مرفوض.
- التنبيه لشرح يحتاج انتباهًا أو إجراءً.
- لا تستخدم الشارات كزخرفة أو لإضافة لون فقط.

### 8.8 نظام التولتيب والمساعدة

يوجد نوعان معتمدان فقط للتولتيب القابل للنقر، وكلاهما يفتح مودال شرح ولا يعتمد على hover وحده:

| النوع | الرمز | اللون | الخلفية | الاستخدام |
| --- | --- | --- | --- | --- |
| تولتيب معلومات | أيقونة مصباح داخل مربع صغير بحواف مستديرة | لون المعلومة، ويبرز بلون العلامة في الوضع الفاتح | سطح ثانوي | شرح معنى حقل، رقم، مصطلح، أو طريقة قراءة معلومة |
| تولتيب تنبيه | أيقونة مثلث تنبيه داخل مربع صغير بحواف مستديرة | أصفر التحذير عبر `--ui-warning-text` | أصفر باهت عبر `--ui-warning-bg` | تحذير، تنبيه تشغيلي، أو ملاحظة قد تؤثر على القرار |

الكلاسات/المكوّنات المعتمدة:

- `x-ui.help` للمساعدة المعلوماتية الطويلة أو المهمة.
- `ui-help-btn` و`ui-help-btn-sm` لأيقونة المصباح المركزية.
- `ui-warning-help-btn` لأيقونة مثلث التنبيه الموثقة في CSS المركزي.
- `ui-tooltip-popover` للتلميح القصير غير الحرج فقط.
- `ui-help-modal-backdrop`, `ui-help-modal-panel`, `ui-help-modal-header`, `ui-help-modal-close`, `ui-help-modal-body` للنافذة العامة الوحيدة التي تخدم جميع أزرار المساعدة.

قواعد التولتيب:

1. التولتيب يشرح قرارًا أو مصطلحًا للمحاسب/المالك، لا يشرح اسم متغير برمجي.
2. التولتيب المعتمد في المعلومات والتحذيرات يفتح مودال عند الضغط على الأيقونة.
3. لا يعتمد التولتيب المهم على hover فقط؛ يجب أن يعمل بالنقر أو focus أو يظهر كمساعدة ثابتة عند الحاجة.
4. طول التولتيب القصير: جملة واحدة. أي شرح طويل أو تعليمات تشغيلية طويلة داخل بطاقة أو رأس صفحة يجب تحويلها إلى أيقونة مصباح أو مثلث تحذير يفتح نافذة مساعدة، ولا تترك كفقرة طويلة تزاحم الواجهة.
5. أيقونة المصباح أو مثلث التحذير توضع أمام النص أو العنوان المرتبط بالشرح مباشرة وفي نفس السطر قدر الإمكان، ولا توضع وحيدة في سطر فارغ أو تحت النص بدون ارتباط بصري واضح.
6. أي صفحة تحتوي نصوصًا كثيرة أو شروحات طويلة يجب إبلاغ صاحب المشروع أولًا لبحث تحويل الشرح إلى تولتيب/مودال مساعدة بدل ازدحام الواجهة.
7. لا تضع في التولتيب معلومات ضرورية لا يمكن الوصول لها من شاشة لمس.
8. الصياغة تكون عملية: “يعرض المبلغ المتبقي بعد التحصيلات المسجلة”، لا “computed from collections table”.
9. يمنع استخدام البرتقالي أو الوردي في أي تولتيب، حتى لو كان الغرض تحذيريًا أو سلبيًا.
10. التحذير المرتبط بسجل بعينه يوضع بجانب اسم السجل بأيقونة مثلث التنبيه، ويفتح مودالًا بالنص الكامل بدل إبقاء فقرة تحذير طويلة داخل البطاقة.
11. نافذة التولتيب أو المساعدة تظهر في منتصف شاشة العرض، خصوصًا على الشاشات الصغيرة، ولا ترتبط بحافة قد تدفعها خارج الشاشة.
12. نص التولتيب ومحتوى نافذة المساعدة يكون متوسطًا أفقيًا، مع عرض أقصى وهوامش آمنة من جانبي شاشة الجوال.
13. يمنع استخدام علامة الاستفهام النصية أو أيقونة السؤال لأي زر مساعدة؛ تستبدل جميعها بأيقونة المصباح المركزية، بينما يستخدم التحذير أيقونة مثلث التنبيه.
14. المساعدة التي تشرح حقلًا أو طريقة استخدام تستخدم المصباح، أما التحذير من أثر تغيير أو إجراء فيستخدم مثلث التنبيه؛ يمنع استخدام علامة التعجب النصية أو أيقونة التعجب المنفردة كزر تولتيب.
15. نافذة المساعدة العامة ونوافذ عرض التفاصيل العادية تطابق نافذة تعديل المنتج المرجعية: تعتيم أسود بنسبة `70%`، سطح `--ui-surface-muted`، حد مركزي، حواف `1rem`، ورأس أفقي بمسافة داخلية `1rem 1.25rem` يفصل بين العنوان وزر الإغلاق. يكون عرض نافذة المساعدة القصيرة أقصى `32rem`، وتستخدم نافذة التفاصيل `ui-modal-panel-wide` عند وجود جدول واسع.
16. زر إغلاق نافذة المساعدة أو عرض التفاصيل يكون مربعًا `2.25rem` بحواف `.75rem`، وخلفية `--ui-surface-muted` وحد `--ui-border` ونص `--ui-text-muted`، وليس زر خطر أحمر.
17. محتوى نافذة المساعدة متوسط أفقيًا، بحجم `.875rem` وارتفاع سطر `1.75rem` ومسافة داخلية `1rem 1.25rem`، ويستخدم `ui-text-muted` مطابقةً للمرجع.
18. لا يتغير هذا الشكل بين أحجام الشاشات؛ يقتصر التجاوب على عرض آمن داخل الشاشة وارتفاع أقصى مع تمرير محتوى النافذة عند الحاجة.

### 8.8.1 قاعدة التنبيهات والتأكيدات

- SweetAlert هو النافذة الأساسية المعتمدة لكل تنبيه أو تأكيد تفاعلي.
- `window.alert` و`window.confirm` يسمح بهما كاحتياط فقط عندما لا تكون SweetAlert محملة أو لا تعمل، ولا يستدعيهما Blade مباشرة.
- تمرر الواجهات نص التأكيد عبر `data-ui-confirm` وتستخدم وحدة التأكيد المشتركة بدل `onclick` أو `onsubmit` المباشر.
- لا تعرض رسائل تنبيه أو تأكيد ثابتة بصورة دائمة داخل الواجهات؛ الاستثناء هو صفحة البيع السريع، حيث يسمح ببقاء التنبيهات التشغيلية الثابتة اللازمة لسلامة عملية البيع.
- لا يحذف نص تحذير مالي أو مخزني قائم لمجرد تطبيق هذه القاعدة؛ يراجع نطاقه أولًا وينقل إلى SweetAlert في دفعة الواجهة المعنية دون تغيير شرط العملية أو نتيجتها.
- رسالة النجاح أو الخطأ العامة تظهر في SweetAlert بنص مختصر يصف النتيجة، ولا تعرض استثناءً أو مسمى برمجيًا.
- خطأ الحقل أو السطر يظهر في SweetAlert، ويثبت أيضًا بجانب الحقل أو السطر المعني حتى يصححه المستخدم؛ ولا يكتفى بنافذة تختفي دون تعيين موضع الخطأ.
- ينتقل التركيز إلى أول حقل غير صحيح عندما يكون ذلك آمنًا، ويربط الخطأ الثابت بمدخل أو سطر واحد بوضوح.
- يستخدم التنبيه الثابت فقط لمعلومة تشغيلية يجب أن تبقى ظاهرة، مثل خطأ إدخال لم يصحح أو حدث حديث محدد المدة؛ أما الشرح فمكانه نافذة المساعدة.

### 8.8.2 قاعدة الشرح ومسميات الأدوار

1. يمنع وضع فقرة شرح أو تعليق تقني داخل الصفحة؛ يوضع مصباح مساعدة بجانب العنوان أو الحقل المراد شرحه، ويفتح نافذة مساعدة بالنص الكامل.
2. يبقى نص الحقل، واسم الحالة، ورسالة الخطأ، ونتيجة العملية ظاهرة؛ لأنها معلومات تشغيلية وليست شرحًا.
3. يخاطب نص المساعدة من يستخدم الصفحة بلغة عمل بسيطة، ويشرح ماذا يفعل وماذا سيحدث بعد ذلك، من دون أسماء جداول أو حقول أو حالات برمجية.
4. يمنع وضع مصباح دون عنوان واضح لنافذته، كما يمنع تكرار الشرح نفسه في الصفحة ونافذة المساعدة.
5. تستبدل عبارة «المالك» أو «مالك المتجر» باسم صاحب المتجر عند توفره؛ ويظهر «مالك المتجر» كقيمة احتياطية إذا كان الاسم فارغًا أو غير صالح للعرض.
6. تستبدل عبارة «المحاسب» باسم المحاسب عند الحديث عن شخص محدد؛ ويبقى «المحاسب» فقط عند الحديث عن الدور عمومًا أو عند تعذر الوصول إلى الاسم.
7. يجب هروب الأسماء قبل عرضها، ويمنع إنشاء HTML من اسم المستخدم أو المتجر من دون هروب؛ لحماية الواجهة من النصوص المدخلة.

### 8.9 اختيار نوع الدفع

- يستخدم خيار الدفع المركزي `ui-payment-option` في تحصيل الآجل وتحصيل المديونية وأي نافذة دفع مماثلة.
- ترتيب الخيارات ثابت: كاش، شبكة، ميكس، وبالهوية نفسها في الوضعين المظلم والفاتح.
- يمنع إنشاء شكل مستقل لنوع الدفع داخل كل صفحة؛ أي إصلاح بصري لهذا المكوّن ينفذ مرة واحدة في CSS المركزي.
- حقلا الكاش والشبكة في الميكس يبدآن فارغين، ويظهر الخيار المحدد بخلفية واضحة لا بمجرد حد أو تغير نص.

### 8.10 الهيدر والسايدبار والتنقل

الكلاسات المعتمدة:

- `ui-topbar`, `ui-topbar-action`.
- `ui-dropdown-panel`, `ui-dropdown-header`, `ui-dropdown-item`.
- `ui-mobile-menu`.
- `ui-sidebar`, `ui-sidebar-link`, `ui-sidebar-link-active`.
- `ui-nav-action`, `ui-nav-action-icon`.

القواعد:

- الرابط النشط يميز بلون العلامة لا بألوان خارجية.
- القوائم المنسدلة تستخدم سطحًا وحدًا مركزيين.
- عناصر التنقل يجب أن تكون قابلة للضغط على شاشات اللمس.
- لا تُخفى النصوص المهمة في السايدبار بدرجات هادئة جدًا.

### 8.10 شريط التقدم

الكلاسات المعتمدة:

- `ui-progress` أو `ui-progress-bar`.
- `auth-progress` داخل صفحات المصادقة.

قواعد شريط التقدم:

1. لون الامتلاء الأساسي يكون لون العلامة `--ui-brand`، لأنه يمثل الحركة والتقدم دون إدخال لون جديد.
2. يسمح بتدرج محدود بين `--ui-brand` و`--ui-brand-strong` فقط إذا كان معرفًا في CSS المركزي.
3. خلفية المسار تكون `--ui-surface-strong` أو `--ui-surface-soft` حسب السياق، حتى تظهر بوضوح في الوضعين.
4. لا يستخدم الأزرق أو البرتقالي أو الوردي أو ألوان الحالات كشريط تقدم عام.
5. إذا كان شريط التقدم يمثل خطرًا أو تأخرًا فعليًا، لا يغير لونه مباشرة؛ تضاف شارة أو تنبيه حالة بجانبه.

### 8.11 صفحات المصادقة

الكلاسات المعتمدة:

- `auth-page`, `auth-page-center`.
- `auth-shell`, `auth-shell-wide`, `auth-card`.
- `auth-brand`, `auth-logo`, `auth-logo-accent`, `auth-brand-line`, `auth-tagline`.
- `auth-label`, `auth-link`, `auth-check`, `auth-progress`.

القواعد:

- صفحات الدخول جزء من الهوية وليست استثناءً.
- لا تستخدم خلفيات أو تدرجات خارج لون العلامة والأسطح المعتمدة.
- رسائل الخطأ أو الإيقاف تستخدم نظام الخطر المركزي.

## 9. التجاوب وتجربة الشاشات الصغيرة وهيكل الصفحات

القواعد الملزمة:

1. كل صفحة يجب أن تعمل على الشاشات الكبيرة والمتوسطة والصغيرة واللمس.
2. الأصل في بناء الواجهات: بطاقات، قوائم، مجموعات حقول، وتخطيط مرن. الجداول ليست حلًا افتراضيًا.
3. هيكل الصفحة لا يبنى على عمود أيمن وعمود أيسر كقاعدة عامة؛ المطلوب تدفق واضح من الأعلى إلى الأسفل، ثم شبكات بطاقات مرنة عند الحاجة.
4. واجهات عمليات المحاسب على الموظفين، مثل الغياب والسحب والعهدة والدين والتحصيل وأي عملية مشابهة، يجب أن تكون عمودًا واحدًا في جميع أنواع الشاشات: كبيرة، متوسطة، صغيرة، ولمس.
5. صفحات العمليات الحساسة لا تستخدم تخطيط عمودين حتى على الشاشات الكبيرة؛ الهدف أن يقرأ المحاسب الخطوات بالترتيب دون تشتت بين يمين ويسار.
6. يسمح باستخدام عمودين فقط في صفحات العرض والتحليل غير الحساسة، وعند وجود سبب وظيفي واضح، ويجب أن يتحول التخطيط إلى عمود واحد على الشاشات الصغيرة.
7. لا يعتمد إجراء مهم على hover فقط.
8. أزرار الإجراءات يجب أن تكون بمساحة لمس مناسبة وواضحة.
9. الجداول الطويلة داخل `ui-table-wrap` أو تتحول إلى بطاقات مختصرة على الجوال.
10. المودالات يجب ألا تتجاوز ارتفاع الشاشة، ويجب أن يكون محتواها قابلًا للتمرير.

## 10. إمكانية الوصول Accessibility

الحد الأدنى الإلزامي:

1. لا يعتمد معنى الحالة على اللون وحده؛ أضف نصًا أو أيقونة أو شارة واضحة.
2. كل زر أيقوني يحتاج `aria-label`.
3. كل حقل يحتاج label مرتبطًا أو تسمية واضحة.
4. focus يجب أن يكون مرئيًا في الأزرار والحقول والروابط.
5. لا تضع نصًا مهمًا بدرجة `ui-text-muted`.
6. لا تجعل التولتيب مصدرًا وحيدًا لمعلومة تشغيلية مهمة.
7. الأزرار والعناصر القابلة للنقر يجب أن تكون قابلة للاستخدام باللمس ولوحة المفاتيح.

## 11. حالات المحتوى

كل صفحة بيانات يجب أن تراعي الحالات التالية:

| الحالة | المطلوب بصريًا |
| --- | --- |
| تحميل | مؤشر أو نص واضح داخل سطح مركزي |
| فارغ | رسالة بسيطة + إجراء واضح عند الحاجة |
| خطأ | `ui-alert` بنوع خطر أو تحذير حسب الحالة |
| لا توجد صلاحية | رسالة واضحة دون كشف تفاصيل تقنية |
| نجاح عملية | شارة أو تنبيه نجاح دون مبالغة لونية |
| بيانات كثيرة | تقسيم، تمرير، أو بطاقات مختصرة |

## 12. الأيقونات والرسوم

- الأيقونات مساعدة وليست بديلًا للنص في الإجراءات المهمة.
- لون الأيقونة يتبع نص العنصر أو حالة مركزية.
- لا تستخدم أيقونات متعددة الألوان داخل لوحة العمل إلا إذا كانت جزءًا من شعار ثابت.
- الأيقونات داخل الأزرار يجب أن تكون متوازنة مع النص عبر `gap` مركزي.
- أيقونة عدد الإشعارات تعتمد شكل دائرة صغيرة ثابتة فوق أيقونة الإشعارات، بخلفية خطر مركزية `--ui-danger-text` ونص واضح عالي التباين، مع حد من لون خلفية الصفحة `--ui-bg` حتى تظهر في الوضعين.
- إذا وصل عدد الإشعارات إلى أكثر من رقمين، يعرض الشكل المختصر مثل `99+` بدل كسر الدائرة أو توسيعها بشكل مشوه.

## 13. المصطلحات التشغيلية المعتمدة

القواعد النصية الملزمة:

1. تستخدم الواجهة كلمة “اليوم” وحدها دون إضافة وصف تقني زائد.
2. تستخدم الواجهة كلمة “التاريخ” وحدها دون إضافة وصف تقني زائد.
3. لا تستخدم المصطلحات الطويلة إذا كانت لا تضيف معنى للمحاسب أو المالك.
4. إذا كان المصطلح المختصر قد يسبب لبسًا في تقرير أو PDF، يجب إبلاغ صاحب المشروع قبل تغييره.

## 14. قواعد خاصة بالمجال المالي والمخزني

لأن المشروع يتعامل مع عمليات مالية ومخزنية، يجب الالتزام بالآتي:

1. الأرقام المالية والمخزنية لا تعرض بنص هادئ جدًا.
2. المبالغ السالبة أو المتأخرة تستخدم حالة خطر أو تحذير واضحة حسب السياق.
3. لا تغيّر ترتيب أو معنى الأعمدة المالية أثناء تحسين الشكل دون موافقة.
4. لا تختصر نصًا ماليًا إذا كان الاختصار قد يغير فهم المالك أو المحاسب.
5. عند عرض حالة خطرة، اشرح الإجراء المطلوب أو سبب الخطورة بلغة تشغيلية.

## 15. سياسة إضافة مكوّن أو توكِن جديد

يسمح بإضافة مكوّن أو توكِن جديد فقط عند تكرار الحاجة أو عدم وجود بديل واضح، وبشرط ألا يضيف لونًا جديدًا.

خطوات الاعتماد:

1. تأكد أن الموجود لا يغطي الحاجة.
2. اختر اسمًا يبدأ بـ `ui-*` للمكوّن أو `--ui-*` للتوكِن.
3. أضفه في CSS مركزي، لا داخل Blade.
4. وثّق الاستخدام هنا قبل استخدامه الواسع إذا كان توثيقه لا يتضمن لونًا جديدًا.
5. اختبره في الوضعين وعلى شاشة صغيرة.

ممنوع:

- إضافة لون جديد داخل Blade.
- إضافة درجة لون عشوائية في CSS.
- إضافة لون جديد إلى هذا المستند أو تعديله لفتح ألوان جديدة إلا بموافقة صاحب المشروع صراحة.
- تعديل هذا المستند نفسه في قواعد الألوان أو منع الألوان إلا بموافقة صاحب المشروع.
- تكرار نفس الدور البصري بأسماء متعددة.

## 16. قائمة مراجعة قبل اعتماد أي واجهة

قبل إنهاء أي تعديل بصري، راجع الآتي:

- [ ] لا يوجد `<style>` داخل Blade.
- [ ] لا يوجد `style="..."` داخل Blade.
- [ ] لا توجد ألوان مباشرة لحل مشكلة محلية عند وجود بديل `ui-*`.
- [ ] لا يوجد لون برتقالي أو وردي في نص أو خلفية أو إطار أو أيقونة.
- [ ] الصفحة تعمل في الوضع المظلم.
- [ ] الصفحة تعمل في الوضع الفاتح.
- [ ] الخط الأساسي للواجهة هو Cairo أو يرثه من التخطيط العام.
- [ ] لا توجد أحجام صغيرة جدًا للنصوص التشغيلية، خصوصًا على الشاشات الصغيرة واللمس.
- [ ] النصوص المهمة ليست `ui-text-muted`.
- [ ] النصوص الطويلة تم الإبلاغ عنها لصاحب المشروع لتحويلها إلى تولتيب/مودال مساعدة عند الحاجة.
- [ ] الإجراءات المهمة لا تعتمد على hover فقط.
- [ ] لا يوجد تخطيط ثابت بعمود أيمن وعمود أيسر يكسر الجوال.
- [ ] واجهات عمليات المحاسب على الموظفين عمود واحد في جميع الشاشات.
- [ ] الجداول الطويلة داخل حاوية تمرير أو لها بديل للجوال.
- [ ] الأزرار الأيقونية لها `aria-label`.
- [ ] زر إغلاق المودال الأيقوني يطابق زر نافذة النقل المخزني الهادئ، وزر الإغلاق النصي يستخدم الدور المركزي.
- [ ] شريط التقدم يستخدم لون العلامة فقط ولا يستخدم ألوانًا جديدة أو برتقاليًا/ورديًا.
- [ ] الأسطر الداخلية ذات الحدود مثل شغل اليد/المبلغ والمتوقع في الصندوق تستخدم `ui-inline-frame` أو `ui-frame-row`.
- [ ] أزرار عرض/فتح وتعديل وإضافة وحذف وإيقاف وتفعيل واسترجاع مطابقة لجدول أزرار العمليات.
- [ ] تستخدم نصوص الواجهة الصيغ القصيرة “اليوم” و“التاريخ” و“الشهر”.
- [ ] خلفيات المودالات من خلفيات المشروع وليست شاذة أو شفافة بشكل مربك.
- [ ] لا يوجد تعديل منطق مالي/مخزني/صلاحيات ضمن العمل البصري.
- [ ] أي ثغرة تصميمية أو برمجية ظهرت أثناء المراجعة تم إبلاغ صاحب المشروع بها قبل علاجها.
- [ ] أي صفحة أو واجهة تحتاج مراجعة أُبلغ صاحب المشروع بها.
- [ ] أي ملف أو واجهة أو دالة غير مرتبطة تم التحقق منها قبل الحذف، وحذفها لا يمس منطقًا أو بيانات، وتم إبلاغ صاحب المشروع باسمها وسبب حذفها.
- [ ] أي مكوّن أو توكِن جديد موثق هنا ومضاف في CSS مركزي دون إضافة ألوان جديدة.
- [ ] لا يوجد أكثر من تعريف أساسي واحد لكل توكِن أو مكوّن `ui-*` داخل CSS المركزي؛ يسمح فقط بقواعد الاستجابة أو الحالة المحددة التي لا تعيد تعريف المكوّن كاملًا.
- [ ] نجحت بوابة الواجهة الموحدة `npm test` التي تشغّل فحص عقد الهوية ثم البناء بالترتيب.

## 17. أمثلة سريعة

### صحيح

```blade
<x-ui.card>
    <h2 class="ui-title text-lg">ملخص التحصيل</h2>
    <p class="ui-text-soft mt-2">يعرض إجمالي التحصيلات المسجلة خلال الفترة المحددة.</p>
    <x-ui.button class="mt-4">عرض التفاصيل</x-ui.button>
</x-ui.card>
```

### خاطئ

```blade
<div class="bg-blue-600 text-gray-100 rounded-xl p-4" style="box-shadow: 0 0 20px red">
    ملخص التحصيل
</div>
```

سبب الخطأ: لون مباشر، CSS داخل Blade، وخروج عن مكوّنات الهوية.

## 18. خريطة المكوّنات الحالية

| العنصر | الكلاس/المكوّن الحالي | ملاحظات |
| --- | --- | --- |
| بطاقة | `ui-card`, `x-ui.card` | مع padding اختياري داخل المكوّن |
| زر | `ui-btn`, `x-ui.button` | يدعم primary/secondary/warning/danger عبر الأدوار المركزية المعتمدة |
| شارة | `ui-badge`, `x-ui.badge` | success/warning/danger/info |
| مساعدة | `x-ui.help`, `ui-help-btn` | للمساعدة القابلة للنقر |
| حقل | `ui-input` | مع focus مركزي |
| جدول | `ui-table-wrap`, `ui-table` | للبيانات الجدولية |
| مودال | `ui-modal-backdrop`, `ui-modal-panel` | مع زر إغلاق واضح |
| تنبيه | `ui-alert`, `ui-alert-warning` | يمكن توسيعه لحالات أخرى مركزيًا |
| تنقل | `ui-topbar`, `ui-sidebar`, `ui-dropdown-panel` | للهيدر والسايدبار والقوائم |
| مصادقة | `auth-*` | صفحات الدخول والاستعادة والإيقاف |

## 19. قاعدة الحسم عند التعارض

عند التعارض بين صفحة قديمة وهذا المستند:

1. يعتمد هذا المستند.
2. إذا كان CSS المركزي الحالي يخالف هذا المستند، يتم فتح تعديل واضح لتصحيح CSS لا لتجاوز المستند داخل Blade.
3. إذا كان التصحيح قد يمس منطقًا ماليًا أو مخزنيًا أو صلاحيات، توقف واطلب موافقة صاحب المشروع.
4. يمنع تعديل قواعد الألوان أو السماح بالبرتقالي أو الوردي أو إضافة ألوان جديدة دون موافقة صاحب المشروع.
5. إذا ظهرت صفحة كثيرة النصوص، أو ثغرة تصميمية/برمجية، أو صفحة بحاجة مراجعة، أو ملف/واجهة/دالة بلا ارتباط واضح، يجب إبلاغ صاحب المشروع بما وُجد وبالإجراء المقترح قبل الاستمرار إذا كان الإجراء قد يمس منطقًا أو حذفًا غير بصري.
