# تقرير المراجعة الشاملة لمطابقة خارطة PWA

**تاريخ المراجعة:** 2026-09-28  
**النطاق:** العقد البرمجي لـPWA، التخزين المحلي، Outbox، Service Worker، الإشعارات والروابط العميقة، API الهاتف، نظام التصميم، وخطة القبول التشغيلي.  
**المرجع الحاكم:** `docs/roadmap-current-scope.md` و`docs/خارطة-طريق-PWA-Flutter.md` و`docs/قاعدة-PWA-لكل-تغيير.md`.

## الحكم التنفيذي

الأساس البرمجي متوافق بدرجة جيدة مع الخارطة بعد إصلاح عطلين اندماجيين كانا يمنعان تشغيل بوابات الفحص ويكسران عقد Blade الخاص بمسودة الجرد. نجحت العقود الثابتة لـPWA، Outbox، مفاتيح التعطيل، Deep Links، API الهاتف، ونظام التصميم.

المشروع **غير جاهز للإطلاق العام**؛ بوابة Staging والأجهزة الفعلية وPush الحقيقي والأداء والحمل وPilot ما زالت غير منفذة أو غير موثقة بنتائج فعلية. كذلك توجد ثلاثة استخدامات لـ`localStorage` تحتاج قرارًا وإصلاحًا منفصلًا لأنها تمس تدفقات مالية/مخزنية، ولذلك لم تُعدّل في هذه المراجعة التزامًا بمنع تغيير منطق المال والمخزون دون موافقة المالك.

## الأعطال والأسطر التي لم تعد تعمل

### 1. ملف `package.json` غير قابل للتحليل — أصلح

- كان تعريف `test:pwa:deep-links` مكررًا بعد `test:pwa:performance` مع فاصلة مفقودة.
- النتيجة السابقة: كل أوامر `npm run ...` والبناء تتوقف عند قراءة `package.json` بخطأ JSON، أي أن بوابات الخارطة كلها كانت معطلة عمليًا.
- الإصلاح: حذف السطر القديم المكرر والإبقاء على التعريف الفعال الموجود في موضعه الصحيح.

### 2. استبدال Blade غير مكتمل في شاشة الجرد — أصلح

- كانت قيمة `$browserDraftVersion` معرفة ثلاث مرات متتالية: كتلتان صريحتان ثم الصيغة القديمة `@php(...)`.
- الصيغة القديمة كانت هي التي استبدلتها المعالجة الحديثة بكتلة صريحة لتفادي التباس مترجم Blade مع null-safe، لكنها بقيت بالخطأ مع نسختين من البديل.
- النتيجة: فشل `test:pwa:outbox` في حارس «كتل PHP الصريحة المتوازنة»، مع احتمال عودة خطأ Blade الذي أنشئ الحارس لمنعه.
- الإصلاح: إبقاء كتلة صريحة واحدة فقط.

### 3. فحص مكرر داخل عقد Outbox — أصلح

- كان فحص وجود `_idempotency_key` نفسه منفذًا مرتين على الملف نفسه وبالرسالة نفسها.
- لم يكسر التنفيذ، لكنه سطر قديم زائد يجعل عدد الفحوص مضللًا ولا يضيف تغطية.
- الإصلاح: حذف النسخة المكررة والإبقاء على فحص واحد.

## نقاط غير مطابقة تحتاج موافقة قبل الإصلاح

### P0 — مفتاح البيع السريع غير معزول بالحساب أو المتجر

- `quickSalePendingKey()` يعيد مفتاحًا عامًا ثابتًا هو `quick-sale-pending-operation`.
- السجل المحلي يتضمن معرف العملية وإجمالي البيع ويبقى حتى عشر دقائق.
- لا يمسح تنظيف الخروج المركزي هذا المفتاح؛ وبذلك يستطيع حساب تالٍ على المتصفح نفسه قراءة حالة العملية السابقة ومحاولة التحقق منها.
- المطلوب المقترح: جعل المفتاح بنطاق نوع الحساب ومعرفه والمتجر، ومسحه ضمن دورة تسجيل الخروج/تبديل الحساب، مع إبقاء البيع Online-only وعدم تحويل هذا السجل إلى Outbox.
- **لم ينفذ الإصلاح** لأنه يمس حماية تكرار عملية بيع مالية ويحتاج اعتماد المالك واختبارات مالية وصلاحيات.

### P0 — علامة اعتماد طلب التوريد في `localStorage`

- تحفظ الواجهة `purchase-order-approval-pending-{orderId}` عند بدء الاعتماد.
- المفتاح غير معزول بالحساب أو المتجر ولا يدخل في تنظيف بيانات الحساب.
- هذه ليست مزامنة Offline، لكنها حالة مرتبطة باعتماد مخزني محظور Offline حسب العقد، وقد تبقى بعد فشل الشبكة أو تبديل الحساب.
- المطلوب المقترح: إبقاء الاعتماد Network-only، واستخدام حالة ذاكرة/جلسة قصيرة أو مفتاح معزول يُمسح يقينًا عند الخروج والنجاح والفشل، بعد مراجعة دورة الاعتماد كاملة.
- **لم ينفذ الإصلاح** لأنه يمس تدفق اعتماد مخزني.

### P1 — مسودة طلب التوريد ما زالت في `localStorage`

- المفتاح نفسه معزول بالمالك والمتجر ومدة صلاحيته سبعة أيام، وهذه نقطتان صحيحتان.
- لكن المسودة تحتوي اسم المورد، الملاحظات، المنتجات، الكميات، وتكلفة التوريد، ولا تُمسح عبر منظومة `client-storage-lifecycle` المركزية عند تسجيل الخروج.
- خارطة الطريق تعتمد IndexedDB للبيانات المنظمة والمسودات، وتشترط تنظيف بيانات المستخدم عند الخروج؛ لذلك العزل بالاسم وحده لا يغلق بوابة تبديل الحساب.
- المطلوب المقترح: نقلها إلى مخزن Drafts ذي schema/version/limits، تسجيل نوعها في دورة التنظيف، واختبار تبديل الحساب وانتهاء الصلاحية. لا تضاف إلى Outbox ولا ترسل تلقائيًا لأن اعتماد/إرسال طلب التوريد Online-only.
- **لم ينفذ الإصلاح** لأنه يغير مسودة مرتبطة بالمخزون والتكلفة.

## المطابقة مع مراحل الخارطة

| المسار | نتيجة المراجعة | الدليل/المتبقي |
| --- | --- | --- |
| Manifest وOffline shell | مطابق برمجيًا | عقد PWA ومرحلة 3 نجحا؛ الاختبار الفعلي على Android وHTTPS متبقٍ |
| Service Worker والـCache | مطابق ثابتًا | API والطلبات الخاصة مستثناة، والتنقل يستخدم fallback عامة؛ تجربة نشر إصدارين متتاليين متبقية |
| التحديث الآمن | مطابق ثابتًا | انتظار تجهيز المسودة وفشل التجهيز يمنع التفعيل؛ تجربة نموذج مفتوح على جهاز فعلي متبقية |
| IndexedDB/Outbox | مطابق لمسودة الجرد بعد الإصلاح | allowlist وIdempotency والتعارض والحدود والتنظيف موجودة؛ اختبار الانقطاع والعودة والتزامن الفعلي متبقٍ |
| العمليات الحساسة Offline | مطابق في Outbox | القائمة البيضاء لا تقبل إلا مسودة الجرد؛ ملاحظات `localStorage` أعلاه تحتاج إغلاقًا دفاعيًا |
| Kill switches | مطابق ثابتًا | يلزم قلب المفاتيح الثلاثة فعليًا في Staging والتحقق من الرجوع |
| الإشعارات وDeep Links | مطابق ثابتًا | يلزم OneSignal حقيقي وQueue worker واختبار الأدوار وانتهاء الجلسة |
| API v1 وجلسات الأجهزة | العقود الثابتة ناجحة | اختبارات Runtime/PHPUnit ودورة متعددة الأجهزة لم تنفذ في بيئة المراجعة لغياب `vendor` |
| API الأنظمة | عقود القراءة ناجحة | الكتالوج، المخزون، الأشخاص، العمليات، التقارير، الحوكمة، الشفتات، المبيعات، الطلبيات، والنقل اجتازت فحوص الجاهزية |
| نظام التصميم | مطابق ثابتًا | العقد والسمات وRTL والتوكِنات نجحت؛ لا يوجد تغيير بصري في هذه المراجعة |
| الأداء وSLO | غير مكتمل | لا توجد قياسات Staging لـp50/p95/p99 أو الأخطاء أو Queue lag أو Push/Outbox |
| الحمل وPilot | غير مكتمل | لا توجد نتائج حمل موثقة ولم يبدأ Pilot |
| Flutter | مطابق لقرار التأجيل | لا توجد ملفات Flutter، والإطلاق الحالي لا يعتمد عليه |

## الفحوص المنفذة

- نجحت بوابات: change policy، عقد PWA، المرحلة 3، Outbox بعد الإصلاح، controls، Deep Links، notifications، roadmap scope، mobile API/sessions وجميع عقود الأنظمة المحمولة، design system، visual identity، وخطة Staging.
- نجح بناء Vite. ظهرت رسائل أن مسارات خطوط Cairo المطلقة ستُحل وقت التشغيل؛ الملفات العامة موجودة، لذلك ليست فشل بناء، لكن يجب التحقق منها عبر Staging/المتصفح.
- فحص deployment يحتاج رابط HTTPS منشورًا؛ تشغيله دون رابط أعاد شاشة الاستخدام، ولذلك لا يعد اختبار نشر ناجحًا.
- لم تُشغّل PHPUnit أو Laravel Runtime لأن مجلد `vendor` غير متوفر في بيئة المراجعة.

## بوابة الإطلاق المطلوبة بالترتيب

1. الحصول على موافقة منفصلة لمعالجة مفاتيح البيع السريع واعتماد/مسودة طلب التوريد، ثم إضافة اختبارات عزل الخروج وتبديل الحساب.
2. تشغيل PHPUnit واختبارات Laravel في CI أو بيئة تحتوي `vendor`.
3. نشر Staging على HTTPS وتشغيل `test:pwa:deployment` و`test:pwa:browser` و`test:pwa:staging` و`test:pwa:performance` بعنوان البيئة الحقيقي.
4. اختبار Android ضعيف ومتوسط: التثبيت، standalone، Offline shell، تحديث إصدارين، مسودة الجرد، التعارض، وتبديل الحساب.
5. اختبار OneSignal الحقيقي وDeep Links لكل دور قبل وبعد انتهاء الجلسة.
6. توثيق SLOs ونتائج الحمل والمراقبة، ثم Pilot محدود دون فروقات بيانات قبل أي إطلاق تدريجي.

## قرار أثر PWA لهذا التغيير

**PWA ينطبق.** أصلح التغيير بوابة أوامر PWA وعقد Blade/Outbox نفسه، ولم يوسع Offline ولم يغير عملية مالية أو مخزنية. شُغلت الفحوص الدنيا والعقود ذات الصلة والبناء. تبقى اختبارات Staging والأجهزة وLaravel Runtime بحالة **PENDING** للأسباب المذكورة أعلاه.
