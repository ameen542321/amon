# المتبقي لإكمال نظام طلبيات التوريد

> **مستند تاريخي:** يعاد تحديد العمل المتبقي من `docs/المواصفات-المعتمدة-لنظام-طلبيات-التوريد.md`، ولا تعتمد هذه القائمة لتنفيذ الدورة الجديدة.

## 1. غرض المستند

يحصر هذا المستند العمل المتبقي للوصول بنظام طلبيات التوريد إلى إغلاق وظيفي قابل للاعتماد. وهو مكمل لمستند `docs/تطوير-طلبيات-التوريد.md` وليس بديلًا عنه.

هذه قائمة تنفيذ وتحقق، ولا تعني أن كل بند فيها عطل مؤكد. البنود التي تغير المخزون أو الصلاحيات أو البيانات المالية لا تنفذ إلا بعد موافقة صاحب المشروع على السلوك المطلوب.

## 2. ما أنجز حاليًا

- دورة الطلبية الأساسية: مسودة، مرسلة، مستلمة، معتمدة، وملغاة.
- إنشاء الطلبيات للمالك والمحاسب مع مشاركة قوالب القائمة والإنشاء والعرض.
- حجب أرصدة المخزون وفروقات الجرد عن المحاسب في الواجهات المشتركة.
- إرجاع الطلبية للجرد، حفظ جرد المحاسب، إرساله للمالك، حفظ لقطة النظام، واعتماد المراجعة.
- منع إرسال الطلبية للمورد ما دامت مراجعة الجرد غير مكتملة.
- نموذج PDF للجرد لا يكشف رصيد النظام أو الفروقات.
- إشعار المالك عند إنشاء المحاسب طلبية، وعند إرسال المحاسب الجرد للمراجعة.
- هجرات توافقية تضيف حقول دورة الجرد الناقصة فقط، من دون إعادة إنشاء الأعمدة الموجودة.
- اسم تشغيلي موحد بصيغة «طلبية + اسم الموزع + يوم-شهر» بدل رقم السجل.
- حصر اسم المورد والملاحظة العامة بالمالك، مع إظهار منتجات مشتريات المالك في بحث المحاسب.

## 3. المتبقي قبل الإغلاق

### الأولوية العليا: حماية الدورة بالاختبارات

- [ ] إضافة اختبار Feature كامل لإنشاء المحاسب طلبية والتحقق من ربطها بمتجره فقط.
- [ ] إضافة اختبارات صلاحيات تثبت أن المحاسب لا يعرض أو يعدل طلبية لمتجر آخر، ولا ينفذ إجراءات المالك.
- [ ] إضافة اختبار لدورة الحالات: `draft` ثم مراجعة الجرد الاختيارية ثم `sent` ثم `received` ثم `approved`.
- [ ] إضافة اختبارات لكل انتقال في مراجعة الجرد، ولمنع الانتقال من حالة غير صحيحة.
- [ ] إضافة اختبار يثبت أن لقطة المخزون تحفظ عند الإرسال فقط، ولا تتغير بعد حركة مخزنية لاحقة.
- [ ] إضافة اختبار يثبت أن اعتماد مراجعة الجرد لا يغير رصيد المخزون.
- [ ] إضافة اختبارات تثبت أن صفحات المحاسب وPDF الجرد لا تحتوي على رصيد النظام أو الفروقات.
- [ ] إضافة اختبار انحدار للمسار الذي لا يطلب جردًا، حتى يبقى الإرسال والاستلام والاعتماد كما هو.

### الأولوية العالية: إكمال التتبع والإشعارات

- [ ] حسم ما إذا كان سجل العمليات المركزي يغطي كل انتقالات الطلبية والجرد.
- [ ] إذا لم يكفِ السجل المركزي، إضافة سجل أحداث غير قابل للفقد يحفظ المنفذ، الوقت، الحالة السابقة، الحالة الجديدة، والملاحظة.
- [ ] إشعار المحاسب عند إرجاع الطلبية للجرد.
- [ ] إشعار المحاسب عند إعادة الجرد مرة أخرى أو رفض الطلبية، بعد اعتماد نصوص الإشعارات وحالاتها.
- [ ] إضافة اختبارات للإشعارات تتحقق من المستقبل والرابط، ومن عدم تسريب كميات أو فروقات مخزنية.

### الأولوية المتوسطة: التعديل بعد الجرد

- [ ] تحديد قرار المشروع حول التعديل بعد إرسال الجرد: هل يمنع كليًا، أم يسمح به مع إبطال المراجعة السابقة.
- [ ] عند السماح بالتعديل، تعليم السطر الذي تغير بعد الجرد وعرض تنبيه واضح للمالك.
- [ ] إعادة أي سطر مخزني مضاف أو مغير إلى دورة جرد جديدة قبل الإرسال.
- [ ] الحفاظ على أثر السطر المحذوف الذي سبق جرده ضمن سجل الأحداث.
- [ ] إضافة اختبارات للتعديل والإضافة والحذف بعد الجرد.

### الأولوية المتوسطة: التحقق البصري والتشغيلي

- [ ] تشغيل دورة يدوية كاملة بحسابي مالك ومحاسب على قاعدة بيانات اختبارية.
- [ ] فحص صفحات القائمة، الإنشاء، العرض، والجرد في الوضعين المظلم والفاتح.
- [ ] فحص الشاشات الصغيرة، وتحديدًا الجداول، حقول الكميات، المودالات، وأزرار الإجراء.
- [ ] فحص PDF الطلبية وPDF الجرد بالعربية ومع طلبية طويلة متعددة الصفحات.
- [ ] تشغيل فحص الهوية البصرية وفحص التباين، ومعالجة أي مخالفة في CSS المركزي فقط.
- [ ] توثيق نتيجة القبول اليدوي واسم بيئة الاختبار وتاريخها.

### الأولوية المتوسطة: الهجرات والترقية

- [ ] تجربة `php artisan migrate` على قاعدة جديدة.
- [ ] تجربة الهجرات على نسخة آمنة من قاعدة سبق إضافة بعض حقول الجرد إليها يدويًا.
- [ ] التحقق من أن إعادة التشغيل لا تنشئ عمودًا مكررًا ولا تحذف بيانات موجودة.
- [ ] توثيق نسخة احتياطية وخطة رجوع قبل الترقية في البيئة الفعلية.

## 4. قرارات مطلوبة من صاحب المشروع

قبل تنفيذ البنود التي تمس المنطق، يجب اعتماد القرارات التالية:

1. هل يسمح بتعديل البنود بعد إرسال الجرد، أم تقفل الطلبية حتى يعيدها المالك؟
2. هل المطلوب سجل أحداث خاص بالطلبيات، أم إظهار أحداثها في سجل العمليات المركزي؟
3. من يستقبل إشعارات الإلغاء والإعادة إذا تعدد محاسبو المتجر: منشئ الطلبية فقط أم جميع محاسبي المتجر؟
4. هل يبقى الحذف النهائي متاحًا بعد الإلغاء، أم يكتفى بالإلغاء والأرشفة لحماية السجل؟

## 5. ترتيب التنفيذ المقترح

1. تثبيت التبعيات وتشغيل الاختبارات الحالية كخط أساس.
2. إضافة اختبارات دورة الطلبية والجرد والصلاحيات.
3. حسم قرارات صاحب المشروع المذكورة أعلاه.
4. تنفيذ سجل الأحداث والإشعارات الناقصة.
5. تنفيذ قاعدة التعديل بعد الجرد واختبارها.
6. تجربة الهجرات على قواعد جديدة وقديمة آمنة.
7. الفحص البصري والتشغيلي الكامل، ثم توثيق القبول.

## 6. أوامر التحقق قبل الإغلاق

```bash
composer install
php artisan migrate:fresh --env=testing
php artisan test
npm run test:visual
npm run test:contrast
npm run build
```

ينفذ اختبار الهجرة على نسخة قاعدة قديمة بأمر منفصل ووسط آمن، ولا يستخدم `migrate:fresh` على أي قاعدة تحتوي بيانات فعلية.

## 7. معيار الإغلاق

يعد نظام الطلبيات مكتملًا لهذه المرحلة عندما:

- تنجح اختبارات الحالات والصلاحيات واللقطة وعدم تغيير المخزون بسبب مراجعة الجرد.
- لا تظهر أي بيانات مخزنية محجوبة للمحاسب في HTML أو JavaScript أو PDF.
- تسجل كل الانتقالات المهمة وتصل الإشعارات إلى الدور الصحيح.
- يكون سلوك التعديل بعد الجرد معتمدًا ومختبرًا.
- تنجح الهجرات في حالتي قاعدة جديدة وقاعدة سابقة جزئية التحديث دون فقد بيانات.
- تنجح فحوص الهوية البصرية والتباين والبناء، ويمر القبول اليدوي للدورة الكاملة.
