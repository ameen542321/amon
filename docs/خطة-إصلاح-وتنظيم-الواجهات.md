# خطة إصلاح وتنظيم الواجهات

> **الحالة:** خطة ملزمة قبل التنفيذ، وليست إذنًا بتنفيذ تغييرات برمجية أو تغييرات بيانات.
> **النطاق:** CSS وJavaScript وPHP الموجود داخل واجهات Blade وما يرتبط بها مباشرة.
> **المرجع البصري الثابت:** `docs/الهوية-البصرية-للمشروع.md`.

## 1. الهدف

تنظيف الواجهات وتنظيم مسؤولياتها بأقل عدد عملي من دفعات الإصلاح والملفات الجديدة، مع الحفاظ التام على نتائج النظام الحالي وبياناته الحقيقية. يعالج الملف المتأثر، عند الحاجة، جوانب CSS وJavaScript وPHP معًا حتى لا تتكرر زيارته في دفعات منفصلة.

لا تهدف الخطة إلى إعادة كتابة المشروع، ولا تمنح إذنًا بتغيير الحسابات أو الصلاحيات أو بنية البيانات أو سلوك العمليات.

## 2. قواعد الأمان غير القابلة للتجاوز

1. المشروع تشغيلي ويحتوي إدخالات وعمليات وبيانات حقيقية؛ الأصل هو الحفاظ على السلوك والنتائج، لا تحسينهما ضمن عمل التنظيف.
2. يمنع تعديل قاعدة البيانات أو البيانات المخزنة أو آلية قراءتها أو كتابتها دون عرض التغيير وأثره ومخاطره والحصول على موافقة صريحة مستقلة.
3. يمنع تنفيذ Migration أو أمر تنظيف بيانات أو تحديث جماعي أو حذف سجلات أو إعادة احتساب بيانات ضمن هذه الخطة.
4. يمنع تغيير منطق مالي أو مخزني أو تقريري أو صلاحيات أو حالات الفواتير والعمليات ضمن تنظيف الواجهة. عند اكتشاف الحاجة إليه يتوقف العمل في الملف، ويوثق السبب، ويعرض على صاحب المشروع قبل التنفيذ.
5. كل نقل لمنطق PHP من Blade يجب أن يكون نقلًا محافظًا على السلوك، مدعومًا باختبار يثبت تطابق المدخلات والمخرجات قبل النقل وبعده.
6. لا يحذف ملف أو دالة أو route أو event listener أو كلاس لمجرد عدم العثور على استدعائه بنص مباشر؛ يجب فحص الاستدعاءات الديناميكية، وBlade، وroutes، وcontainer bindings، وevents، وjobs، وcommands، والاختبارات أولًا.
7. الحذف يقتصر على الكود الخامل المثبت، وينفذ في commit واضح يمكن الرجوع عنه، ولا يخلط مع تغيير وظيفي.
8. لا تستخدم بيانات الإنتاج لتجربة الإصلاح. تستخدم بيئة اختبار وقاعدة بيانات اختبار معزولة، ويحظر تشغيل اختبارات الكتابة على قاعدة البيانات الحقيقية.
9. لا تعتبر هذه الخطة أو الموافقة عليها موافقة على أي تغيير بيانات أو حسابات؛ كل حالة من هذا النوع تحتاج موافقة صريحة منفصلة.

## 3. ثبات مرجع الهوية البصرية

1. ملف `docs/الهوية-البصرية-للمشروع.md` مكتمل وهو المرجع الملزم للتنفيذ.
2. لا يعدل ملف الهوية البصرية أثناء هذه الخطة، ولا تضاف إليه قاعدة أو لون أو مكوّن أو استثناء بصورة تلقائية.
3. إذا ظهر تعارض أو نقص لا يمكن حله بالكلاسات والمكونات المعتمدة، يتوقف الجزء البصري ويبلغ صاحب المشروع بما يلزم تعديله ولماذا وأثره.
4. لا يجرى أي تعديل على ملف الهوية إلا بعد إخبار صاحب المشروع والحصول على موافقته الصريحة على التعديل المحدد.
5. لا تستخدم صفحة قديمة مرجعًا بصريًا بديلًا عن ملف الهوية.

## 4. مبادئ تنظيم التنفيذ

### 4.1 أقل عدد ممكن من الدفعات

تنفذ الخطة في **ثلاث دفعات أساسية فقط**. لا تفتح دفعة رابعة إلا إذا ظهر مانع أمني أو نطاق منطقي يحتاج موافقة مستقلة.

داخل كل دفعة يختار **نظام وظيفي كامل** لا صفحة منفردة منه. نظام المنتجات مثلًا يشمل الرئيسية والإنشاء والتعديل وسلة المحذوفات، ونظام المخزون عند بدئه يشمل كل واجهاته المرتبطة في جرد وخطة تنفيذ واحدة. لا يغلق النظام على خطوات صغيرة منفصلة لـCSS ثم JavaScript ثم PHP؛ تراجع هذه الجوانب معًا لكل ملفات النظام، مع بقاء شرط الموافقة الصريحة قبل أي تغيير يمس البيانات أو منطق المخزون.

### 4.2 إصلاح الملف مرة واحدة

عند إدخال ملف Blade في دفعة إصلاح، تراجع في الجلسة نفسها الجوانب الثلاثة:

1. **CSS:** إزالة CSS غير المسموح داخل Blade، واستبداله بكلاسات مركزية موجودة أو مشتركة.
2. **JavaScript:** إزالة السكربتات والمعالجات المباشرة المكررة، وربط الواجهة بوحدة مشتركة واضحة عند الحاجة.
3. **PHP:** تصنيف كتل PHP، وتبسيط منطق العرض، ونقل التحضير غير المناسب بعد ثبوت تطابق السلوك وبعد الموافقات المطلوبة.

لا يشترط تعديل الجوانب الثلاثة إذا كان أحدها غير موجود أو لا يحتاج إصلاحًا، لكن يجب توثيق أنه روجع.

### 4.3 أقل عدد ممكن من الملفات الجديدة

1. يمنع إنشاء ملف CSS أو JavaScript أو PHP لكل واجهة.
2. يعاد استخدام `resources/css/app.css` كنقطة CSS المركزية ما دام قابلًا للصيانة.
3. يعاد استخدام `resources/js/app.js` كنقطة دخول JavaScript.
4. لا ينشأ ملف جديد إلا إذا كان يخدم سلوكًا مكررًا في أكثر من واجهة أو يفصل مسؤولية كبيرة مثبتة.
5. قبل إنشاء أي ملف جديد، يسجل في تقرير الدفعة: اسمه، مسؤوليته، الملفات التي ستستخدمه، ولماذا لا يكفي ملف موجود.
6. تنشأ الملفات المشتركة المعتمدة في **بداية الدفعة وقبل تعديل الواجهات التابعة لها** حتى لا تظهر حلول مؤقتة داخل Blade.
7. الحد الابتدائي المقترح، ولا يعتمد كله تلقائيًا:
   - CSS: لا ملف جديد افتراضيًا؛ يستخدم `resources/css/app.css`.
   - JavaScript: بحد أقصى ملف عام مشترك وملف مجال واحد في الدفعة عند ثبوت الحاجة.
   - PHP: Service أو ViewModel واحد للمسؤولية المشتركة، لا طبقة جديدة لكل صفحة.

#### استثناء إلزامي لصفحة البيع السريع

1. صفحة البيع السريع استثناء مقصود من قاعدة عدم إنشاء ملف لكل واجهة بسبب حساسية عملياتها وترابط حساباتها ومدخلاتها.
2. إذا احتاج JavaScript الخاص بصفحة البيع السريع إلى أي تعديل، ينشأ لها أولًا وقبل تعديل الواجهة ملف مستقل باسم واضح مثل `resources/js/features/quick-sale.js`، ثم ينقل إليه السلوك الخاص بها بصورة محافظة على النتائج.
3. لا يدمج منطق البيع السريع الخاص داخل ملف الفواتير العام أو ملف JavaScript مشترك لمجرد تقليل عدد الملفات.
4. يسمح للملف المستقل باستيراد أدوات عامة عديمة المعرفة بمنطق البيع، مثل فتح المودال أو ربط التأكيد، لكن تبقى حسابات الصفحة وتنسيق بنود البيع وحالة الدفع وسلوك إرسال الطلب داخل نطاق البيع السريع الواضح.
5. لا ينقل أي حساب من الخادم إلى المتصفح، ولا يغير مصدر السعر أو الضريبة أو الإجمالي أو الخصم أو الكمية أو المخزون أثناء فصل السكربت.
6. قبل ربط الملف الجديد، توثق الطلبات والأحداث والحقول والنتائج الحالية، وبعد الربط تقارن القيم و`payload` وعدد الطلبات وترتيبها وحالات النجاح والفشل مع خط الأساس.
7. إنشاء ملف البيع السريع المستقل لا يعد إذنًا بتعديل منطق البيع أو البيانات، وأي تغيير يتجاوز الفصل الحرفي يتوقف ويعرض على صاحب المشروع.

### 4.4 الأسماء الواضحة

1. يمنع إدخال أسماء مبهمة مثل `data`, `item`, `temp`, `value`, `result`, `obj`, `el`, `fn` عندما يوجد أكثر من معنى محتمل في السياق.
2. الاسم الجديد يصف المجال والغرض، مثل:
   - `saleDeletionConfirmationButton` بدل `btn`.
   - `editableSaleRows` بدل `data`.
   - `selectedPaymentMethod` بدل `type`.
   - `storeMonthlyFinancialSummary` بدل `summary`.
3. أسماء الدوال تبدأ بفعل يصف أثرها، مثل `openSaleEditModal`, `buildStoreTransferRows`, `formatInvoiceAmount`.
4. أسماء Boolean تبدأ بما يكشف طبيعتها، مثل `is`, `has`, `can`, `should`.
5. عند تعديل اسم قائم، تفحص كل مراجع الاسم آليًا ويدويًا، ولا يغير contract عام أو payload أو اسم حقل قاعدة بيانات لمجرد تحسين التسمية.
6. لا تعاد تسمية مفاتيح API أو request أو session أو بيانات مخزنة إلا بموافقة مستقلة وخطة توافق خلفي.

## 5. بوابة ما قبل التنفيذ

قبل أول تعديل في كل دفعة يجب إنجاز الآتي:

1. تثبيت حالة Git نظيفة وتسجيل commit الأساس الذي ستقارن به النتائج.
2. تحديد الواجهات والملفات المرتبطة مباشرة بها: Blade وCSS وJavaScript وController/Service والاختبارات والمسارات.
3. إعداد مصفوفة لكل ملف تتضمن:
   - CSS الموجود داخل Blade.
   - وسوم `<script>` ومعالجات الأحداث المباشرة.
   - كتل `@php` والاستعلامات والحسابات والتنسيقات.
   - الدوال والكلاسات المكررة أو المحتمل خمولها.
   - مستوى الخطورة: عرض فقط، سلوك واجهة، قراءة بيانات، كتابة بيانات، مالي/مخزني/صلاحيات.
4. تصوير أو تسجيل السلوك الحالي للواجهات المستهدفة في الوضعين المظلم والفاتح، وعلى شاشة صغيرة وكبيرة، عندما يكون التغيير مرئيًا.
5. تثبيت اختبارات characterization للسلوك المهم قبل نقله، خصوصًا payloads والطلبات والتحقق والحسابات المعروضة.
6. التحقق من أن الاختبارات تستخدم بيئة وقاعدة بيانات اختبار معزولة.
7. عرض أي تغيير محتمل في القراءة أو الكتابة أو الحسابات على صاحب المشروع والتوقف حتى الموافقة.
8. تحديد الملفات المشتركة الجديدة الضرورية، إن وجدت، وإنشاؤها أولًا في الدفعة.

## 6. مراجعة التكرار والكود الخامل

مهمة التنظيف **إلزامية داخل كل دفعة نظام** وليست اقتراحًا مؤجلًا. قبل إغلاق النظام يجب فحص كل ملف معدل بحثًا عن:

- دوال أو متغيرات معرفة ولا تقرأ إلا عند تعريفها.
- حالات ومتغيرات تسند ولا تؤثر في أي قرار لاحق.
- كلاسات مخصصة لا تعريف CSS لها ولا يقرأها JavaScript.
- تعليقات قديمة تصف الكود بأنه «مضاف» أو «مستعاد» أو تشرح حالة لم تعد موجودة.
- أسطر مكررة، معالجات مكررة، كتل فارغة، وملفات لم تعد مستوردة أو مستدعاة.

لا يحذف العنصر بالحدس: يثبت عدم استخدامه عبر `rg` وفحص الاستدعاءات الديناميكية والاختبارات. يسجل في تقرير الدفعة ما حذف وسبب أمان حذفه، وما أبقي رغم الاشتباه وسبب بقائه.

### 6.1 جرد الدوال قبل التعديل

تنشأ قائمة للدوال والسلوكيات الموجودة في ملفات الدفعة، ويثبت لكل عنصر:

- موضع التعريف.
- مواضع الاستدعاء المباشر.
- الاستدعاءات المحتملة عبر Blade/Alpine/events/routes/container.
- المدخلات والمخرجات والآثار الجانبية.
- هل يقرأ بيانات أم يكتبها.
- هل توجد نسخة أخرى تؤدي المسؤولية نفسها.
- قرار العنصر: إبقاء، دمج، نقل، إعادة تسمية، أو مرشح حذف.

### 6.2 شروط اعتبار الدالة أو الملف خاملًا

لا يعتمد الحذف إلا عند اجتماع ما ينطبق من الشروط التالية:

1. لا توجد مراجع ثابتة أو ديناميكية بعد البحث الشامل.
2. لا يوجد route أو event أو job أو command أو service container binding يصل إليه.
3. لا يعتمد عليه Blade أو Alpine باسم نصي.
4. لا يظهر في اختبارات أو إعدادات أو توثيق تشغيلي حالي.
5. يوجد بديل معتمد ومستخدم إن كانت المسؤولية ما زالت مطلوبة.
6. تمر الاختبارات والبناء بعد الحذف.
7. يسجل سبب الحذف وطريقة الرجوع عنه.

إذا بقي شك، لا يحذف؛ يوصف بأنه **مرشح خمول يحتاج تحققًا**.

### 6.3 قاعدة دمج التكرار

- يدمج الكود عندما تتطابق المسؤولية والمدخلات والنتيجة، لا لمجرد التشابه الشكلي.
- لا تدمج عمليات مالية مختلفة في دالة عامة تخفي اختلاف قواعدها.
- لا تنشأ abstraction قبل وجود استخدامين فعليين واضحين على الأقل.
- لا يستخدم الدمج لتغيير ترتيب العمليات أو نصوص التأكيد أو قواعد التحقق.

## 7. مخطط الدفعات الثلاث

## الدفعة الأولى: الأساس المشترك والتنظيف منخفض الخطورة

**الهدف:** تجهيز البنية المشتركة وإزالة المخالفات العرضية دون المساس بمنطق البيانات.

تشمل:

1. حصر وتثبيت نقطة تحميل Alpine وJavaScript مرة واحدة، بعد اختبار عدم اعتماد أي واجهة على التحميل المكرر.
2. نقل CSS غير المسموح من واجهات الويب العادية إلى `resources/css/app.css` باستخدام أسماء `ui-*` المعتمدة.
3. إنشاء وحدة JavaScript عامة واحدة فقط إذا ثبت تكرار المودالات أو التأكيد أو ربط الأحداث في عدة واجهات.
4. استبدال `onclick` ونظائره في الملفات الداخلة في الدفعة بـ`data-*` أو مكوّن Alpine مشترك دون تغيير الطلب المرسل.
5. تنظيف التعليقات والكود المعلق والدوال الخاملة المثبتة فقط.
6. مراجعة PHP العرضي البسيط مثل خرائط الكلاسات، دون نقل استعلامات أو حسابات.

**ممنوع في هذه الدفعة:** تغيير Controller أو query أو payload أو حساب مالي أو مخزني.

**معيار الإغلاق:** تطابق السلوك، نجاح الفحوص، وعدم وجود تحميل مكتبة مكرر أو CSS محلي غير مسموح في الملفات المستهدفة.

## الدفعة الثانية: الواجهات التفاعلية المتكررة

**الهدف:** دمج السلوك المتكرر في أقل عدد من وحدات المجال.

ترتب الواجهات بحسب كثافة التكرار، وتجمع في مجموعات وظيفية، مثل:

1. المنتجات: إنشاء/تعديل/قائمة/مخزون.
2. عمليات الموظفين: غياب/سحب/دين/تحصيل/مصروف.
3. الفواتير، دون دمج سكربت البيع السريع الخاص بها.
4. البيع السريع في ملف JavaScript مستقل وفق الاستثناء الإلزامي أعلاه.
5. النقل بين المتاجر وأوامر الشراء.

لكل مجموعة:

- ملف JavaScript مجال واحد بحد أقصى عند الحاجة المثبتة.
- المكونات المشتركة الموجودة تعاد استخدامها قبل إنشاء مكوّن جديد.
- يراجع كل Blade من CSS وJavaScript وPHP في المرور نفسه.
- يحافظ على أسماء الحقول والطلبات والـroutes والاستجابات كما هي.
- لا ينقل حسابًا ماليًا أو مخزنيًا إلا إلى قائمة الدفعة الثالثة وبعد الموافقة.
- عند دخول البيع السريع في الدفعة، ينشأ ملفه المستقل قبل أول تعديل JavaScript، وتطبق عليه مقارنات إضافية للأسعار والكميات والإجماليات والدفع والطلب المرسل.

**معيار الإغلاق:** اختفاء التكرار المثبت، وعدم وجود ملف لكل صفحة، وتطابق الطلبات والسلوك وحالات الخطأ والنجاح.

## الدفعة الثالثة: PHP وتجهيز بيانات العرض

**الهدف:** جعل Blade يعرض بيانات جاهزة دون استعلامات أو حسابات معقدة داخله.

تبدأ هذه الدفعة فقط بعد اعتماد نطاقها؛ لأنها قد تمس آلية قراءة البيانات أو الحسابات.

التسلسل الإلزامي:

1. كتابة اختبارات characterization للنتائج الحالية على بيانات اختبار ممثلة.
2. توثيق كل استعلام وحساب داخل Blade ومدخلاته ومخرجاته.
3. تصنيف النقل إلى Controller خفيف، أو Service موجود، أو Query Object، أو ViewModel، مع تفضيل الموجود وعدم إنشاء طبقة جديدة بلا حاجة.
4. مقارنة النتائج قبل النقل وبعده آليًا، بما يشمل المبالغ والتقريب والترتيب والحالات الفارغة والفترات الزمنية.
5. إبقاء Blade مسؤولًا عن الشروط العرضية البسيطة والتكرار بالقوالب فقط.
6. حذف النسخة القديمة بعد ثبوت استخدام المصدر الجديد واجتياز المقارنة.

**ممنوع:** تغيير معنى رقم أو مصدره، إصلاح معادلة مشتبه بها ضمن النقل، أو دمج حسابات متشابهة ظاهريًا دون إثبات تكافئها.

**معيار الإغلاق:** لا استعلامات قاعدة بيانات داخل Blade المستهدف، ولا حسابات مالية مركبة داخله، والنتائج متطابقة ومثبتة بالاختبارات.

## 8. قواعد CSS وJavaScript وPHP داخل الملف الواحد

### CSS

- واجهات الويب تستخدم CSS المركزي والمكونات المعتمدة فقط.
- PDF والطباعة والبريد تعامل حسب استثناءات ملف الهوية، مع تجميع القواعد وتقليل `style=""` المتكرر دون تغيير المحتوى المالي.
- لا يضاف لون أو token أو قاعدة هوية جديدة دون الرجوع إلى صاحب المشروع.

### JavaScript

- يمنع JavaScript المباشر المتكرر داخل Blade.
- يفضل event delegation و`data-*` للسلوك العام، وAlpine للمكونات المحلية التفاعلية.
- تمرر بيانات الخادم عبر `@js` أو JSON آمن، ولا تبنى سلاسل JavaScript من مدخلات غير مهربة.
- لا تغير أسماء الحقول أو payloads أو ترتيب الطلبات أثناء الفصل.
- كل وحدة تهيئة تتحقق من وجود جذر الواجهة قبل العمل، حتى يمكن تحميل bundle واحد دون أخطاء.

### PHP

- يبقى التنسيق البسيط والشروط العرضية الواضحة في Blade عند عدم وجود تكرار أو أثر جانبي.
- تنقل الاستعلامات وتجميع البيانات والحسابات المركبة خارج Blade وفق بوابة الأمان والموافقة.
- يمنع إنشاء استعلام خفي في accessor أو component يؤدي إلى N+1.
- لا تنقل مسؤولية إلى Service جديد إذا كانت هناك خدمة قائمة معتمدة تؤديها.

## 9. الاختبارات والمقارنات الإلزامية

لكل دفعة، بحسب نطاقها:

1. `npm test` لتشغيل عقد الواجهة وبناء Vite في بوابة واحدة.
2. اختبارات PHP الحالية المرتبطة بالملفات المتأثرة.
3. اختبارات Feature للطلبات التي قد تتأثر بالفصل.
4. مقارنة status code وredirect وsession messages وأخطاء validation وrequest payload.
5. مقارنة نتائج التقارير والمبالغ والقيم والتقريب قبل/بعد عند وجود PHP منقول.
6. اختبار الوضعين المظلم والفاتح والشاشات الصغيرة والكبيرة.
7. اختبار لوحة المفاتيح واللمس للمودالات والأزرار والحقول المتأثرة.
8. فحص Console وNetwork للتأكد من عدم تكرار listeners أو requests وعدم وجود أخطاء JavaScript.
9. عدم اعتماد الدفعة عند فشل اختبار بحجة أن الفشل سابق إلا بعد توثيق دليل واضح وعزل أثر التعديل.

## 10. شكل تقرير كل دفعة

قبل الدمج يقدم تقرير مختصر ودقيق يحتوي:

1. قائمة الملفات المعدلة والجديدة والمحذوفة.
2. سبب كل ملف جديد ودليل الحاجة إليه.
3. ما روجع من CSS وJavaScript وPHP في كل Blade.
4. قائمة الدوال المدمجة أو المنقولة أو المعاد تسميتها.
5. قائمة المحذوفات ودليل خمولها.
6. تأكيد عدم تغيير قاعدة البيانات أو البيانات أو آلية القراءة/الكتابة، أو إرفاق الموافقة الصريحة إن حدث ذلك.
7. مقارنة السلوك والنتائج قبل/بعد.
8. أوامر الاختبار ونتائجها.
9. المخاطر المتبقية وخطة الرجوع.
10. تأكيد أن ملف الهوية البصرية لم يعدل، أو إرفاق الموافقة المحددة إذا عدل.

## 11. شروط إيقاف الدفعة فورًا

يتوقف التنفيذ ويبلغ صاحب المشروع عند:

- ظهور فرق في مبلغ أو تقرير أو مخزون أو صلاحية أو حالة عملية.
- الحاجة إلى Migration أو تعديل schema أو بيانات مخزنة.
- الحاجة إلى تغيير query أو آلية كتابة أو مصدر حقيقة.
- اكتشاف دالة تبدو خاملة لكن لها استدعاء ديناميكي غير محسوم.
- تعذر إثبات تطابق السلوك بعد نقل PHP أو JavaScript.
- الحاجة إلى تعديل ملف الهوية البصرية.
- توسع عدد الملفات الجديدة عن الحد المخطط دون مبرر وموافقة.
- ظهور طلب خارج ملفات ونطاق الدفعة الحالية.

## 12. تعريف اكتمال الخطة

تعد الخطة مكتملة فقط عندما:

1. تمر الواجهات المستهدفة بمراجعة CSS وJavaScript وPHP موثقة.
2. لا توجد حلول محلية مكررة يمكن دمجها بأمان.
3. لا توجد ملفات أو دوال خاملة مثبتة ضمن النطاق.
4. لا ينشأ ملف لكل واجهة، ويكون كل ملف جديد ذا استخدام مشترك واضح.
5. تستخدم الأسماء الجديدة الواضحة وتبقى العقود الخارجية متوافقة.
6. تتطابق النتائج والطلبات والسلوك مع خط الأساس.
7. تنجح جميع الاختبارات المطلوبة.
8. لا تعدل البيانات الحقيقية أو ملف الهوية البصرية دون موافقة صريحة مستقلة.
