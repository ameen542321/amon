# خارطة طريق المهمة التالية لإكمال ومراجعة الواجهات

> الغرض: إغلاق المهمة الحالية بوضوح، وبدء مهمة جديدة محددة النطاق لإكمال الملفات الحساسة والمراجعة النهائية دون خلط العمل البصري بمنطق البيانات.

## 1. نقطة البداية المعتمدة

- البنية العامة للواجهة والمكونات المشتركة وعقود `data-*` والفحص البصري المركزي موجودة.
- `npm test` هو بوابة القبول الأمامية الموحدة؛ يشغّل عقد الواجهة ثم بناء Vite.
- توجد أربعة ملفات مستثناة مؤقتًا من منع event handlers المضمّنة:
  1. `resources/views/accountants/pos/collection.blade.php`
  2. `resources/views/accountants/pos/debt.blade.php`
  3. `resources/views/dashboard/accountant/index.blade.php`
  4. `resources/views/user/stores/daily.blade.php`
- توجد سكربتات متخصصة داخل قوالب Blade أخرى، لكنها لا تحتوي حاليًا خصائص أحداث مضمّنة مستثناة من البوابة العامة.

## 2. تعريف المهمة الجديدة المقترح

**العنوان المقترح:** إكمال استخراج الواجهات الحساسة والمراجعة النهائية الشاملة.

**الهدف:** إزالة الاستثناءات الأربعة، نقل السلوك التفاعلي المتبقي إلى وحدات مستقلة، ثم تنفيذ مراجعة وظيفية وبصرية نهائية دون تغيير النتائج المالية أو المخزنية أو الصلاحيات.

## 3. قواعد لا تبدأ المهمة دونها

1. اقرأ `docs/الهوية-البصرية-للمشروع.md` قبل أي تعديل.
2. اعتبر كل مبلغ أو كمية أو شفت أو حالة دفع أو مديونية عقدًا محميًا لا يتغير أثناء الاستخراج.
3. قبل أي تعديل يتطلب تغيير Controller أو Service أو Model أو Route أو طلب أو استعلام أو قاعدة بيانات، توقف واعرض الأثر والمخاطر وخطة الرجوع، ثم انتظر الموافقة الصريحة.
4. لا تُقرأ أو تُعدل بيانات الإنتاج، ولا تُغير آلية قراءتها أو كتابتها، دون موافقة صريحة.
5. نفّذ كل نظام في التزام مستقل حتى يمكن مراجعته أو الرجوع عنه منفردًا.

## 4. المرحلة الأولى: تثبيت خط الأساس

### الأعمال

- تشغيل الفحوص الحالية وتسجيل نتائجها قبل التعديل.
- حصر أسماء الحقول والمسارات وطرق HTTP والنصوص التأكيدية في الملفات الأربعة.
- حصر الوظائف العامة التي تعدّل DOM فقط، وفصلها عن الوظائف التي تحسب مبلغًا أو كمية أو قرار شفت.
- إضافة اختبارات عقد ساكنة لكل ملف قبل نقله، بحيث تثبت الحقول والمسارات والجذور المطلوبة.

### أوامر التحقق

```bash
git status --short
npm test
rg -n "onclick=|onchange=|oninput=|onsubmit=" \
  resources/views/accountants/pos/collection.blade.php \
  resources/views/accountants/pos/debt.blade.php \
  resources/views/dashboard/accountant/index.blade.php \
  resources/views/user/stores/daily.blade.php
```

### شرط القبول

- وجود سجل واضح للعقود الحالية قبل أي نقل.
- عدم وجود تعديل وظيفي في هذه المرحلة.

## 5. المرحلة الثانية: واجهة تحصيل الآجل

### النطاق

- فتح وإغلاق مودال التحصيل ومعاينة العمليات.
- التحصيل الكامل والجزئي.
- حقول الدفع: كاش، شبكة، وميكس.
- حالات الانتظار ومنع الإرسال المتكرر.

### خطة التنفيذ

1. إنشاء وحدة مثل `resources/js/features/accountant/credit-collection.js`.
2. تمرير المسارات والقيم عبر JSON آمن أو `data-*` دون بناء JavaScript داخل Blade.
3. استبدال handlers المضمّنة بجذر `data-accountant-credit-collection` وأزرار ذات عقود واضحة.
4. الحفاظ على أسماء حقول الدفع والمبلغ المتبقي حرفيًا.
5. إضافة فحص يمنع رجوع handlers إلى الملف.

### اختبارات القبول

- فتح وإغلاق كل مودال بلوحة المفاتيح واللمس.
- التحصيل الكامل والجزئي بالقيم الحدية.
- الكاش والشبكة والميكس، بما في ذلك مجموع حقلي الميكس.
- عدم إرسال النموذج مرتين.
- عدم تغير المسار أو payload أو نص التأكيد.

## 6. المرحلة الثالثة: واجهة المديونيات

### النطاق

- فتح سجل المديونية ومودال التحصيل.
- التحصيل الكامل والجزئي.
- تعبئة بيانات الموظف والمديونية المحددة.
- حالات الدفع والتحذيرات.

### خطة التنفيذ

1. إنشاء وحدة مثل `resources/js/features/accountant/debt-operations.js`.
2. حفظ معرفات المديونية والمبالغ في بيانات آمنة على العناصر.
3. نقل بناء الصفوف الديناميكية إلى DOM آمن باستخدام `textContent` و`createElement`.
4. عدم تعديل أصل المديونية أو طريقة حساب المتبقي.
5. إضافة عقود تحقق للحقول والمسارات ودوال الدفع.

### اختبارات القبول

- مديونية واحدة وعدة مديونيات وعدم وجود مديونية.
- تحصيل كامل وجزئي ودفع مختلط.
- عدم السماح بمبلغ يتجاوز المتبقي وفق السلوك الحالي.
- تطابق payload قبل النقل وبعده.

## 7. المرحلة الرابعة: موازنة المحاسب وقرار الشفت

### النطاق

- `confirmNextShiftDecision` فقط في البداية.
- قرار الشفت الثاني لنفس تاريخ العمل أو الانتقال لتاريخ العمل التالي.
- حالة إصدار موازنة التاريخ المرجع.

### بوابة موافقة إلزامية

هذه المرحلة مرتبطة بإغلاق الشفت والموازنة. قبل أي تغيير يتجاوز نقل العرض الحرفي للتأكيد يجب عرض:

- شروط ظهور كل قرار.
- القيم المرسلة في `next_shift_decision`.
- أثر كل قرار على الشفت وتاريخ العمل.
- خطة اختبار وخطة رجوع.

### اختبارات القبول

- التاريخ المرجع لا يغلق شفت تاريخ اليوم الحالي.
- اختيار اليوم التالي يحافظ على التحذير الحالي.
- إلغاء SweetAlert لا يرسل النموذج.
- fallback يعمل عند غياب SweetAlert.
- لا تتغير قيمة `actual_cash` أو الملاحظات أو تعديلات المديونية المضمنة.

## 8. المرحلة الخامسة: المبيعات اليومية

### سبب وضعها أخيرًا

هذا أكبر الملفات حساسية، ويجمع البيع والمنتجات والوحدات والكميات والأسعار والدفع والأجل والمديونية وشغل اليد واسترجاع المخزون.

### تقسيم التنفيذ الداخلي

1. **عرض التفاصيل فقط:** فتح وإغلاق صفوف العمليات والتفاصيل المالية.
2. **مودال تعديل العملية:** فتح وإغلاق وتعبئة البيانات دون حفظ.
3. **صفوف المنتجات:** البحث والإضافة والحذف وتغيير الوحدة.
4. **الكميات والأسعار:** حدود الكمية ومزامنة الإجمالي.
5. **الدفع:** نقدي وشبكة وميكس ومدفوع ومتبقي.
6. **الأجل والمديونية:** تسجيل المتبقي ودين الموظف.
7. **الحفظ والتأكيد:** payload النهائي ومنع الإرسال المتكرر.

### بوابة موافقة إلزامية

- أي تعديل يمس حساب الإجمالي أو حدود الكمية أو المخزون أو الأجل أو الدين يحتاج موافقة صريحة قبل التنفيذ.
- الاستخراج يجب أن يحافظ على الدوال والمعادلات حرفيًا أولًا؛ التحسين أو إعادة التصميم مهمة أخرى مستقلة.

### اختبارات القبول

- عملية بمنتج واحد وعدة منتجات.
- منتج عادي وكسري ورول وطقم وحبة.
- زيادة ونقصان وحذف وإضافة صف.
- نقدي وشبكة وميكس وآجل ومديونية وشغل يد.
- مخزون غير كافٍ وحدود الكمية.
- إلغاء المودال لا يغير البيانات.
- payload قبل النقل وبعده متطابق.

## 9. المرحلة السادسة: إزالة الاستثناءات

### الأعمال

- إزالة الملفات الأربعة من `protectedLegacyInlineEventFiles`.
- جعل منع event handlers عامًا بلا استثناءات.
- التأكد من عدم وجود handlers مضمّنة في أي Blade.
- تحديث وثيقة الإغلاق لتعلن إزالة القائمة المحمية بدل إبقائها.

### شرط القبول

```bash
rg -n "\s(onclick|onchange|oninput|onsubmit|onkeydown|onkeyup)=" resources/views --glob '*.blade.php'
```

يجب ألا يعيد الأمر أي نتيجة.

## 10. المرحلة السابعة: مراجعة السكربتات المتبقية داخل Blade

بعد إزالة الاستثناءات، راجع ملفات Blade التي ما زالت تحتوي `<script>`، وصنف كل سكربت إلى:

- سكربت عرض عام يمكن نقله مباشرة.
- سكربت يحتاج config آمن من Blade.
- سكربت مالي أو مخزني يحتاج موافقة واختبارات نطاقية.
- سكربت طباعة أو PDF له استثناء تقني موثق.

لا يكون الهدف حذف `<script>` رقميًا فقط؛ الهدف أن يبقى Blade للهيكل والبيانات، وأن توجد السلوكيات القابلة للصيانة في وحدات واضحة.

## 12. المرحلة التاسعة: الاختبارات النهائية

```bash
git diff --check
node --check scripts/check-visual-identity.mjs
npm test
php artisan test
```

إذا تعذر `php artisan test` بسبب غياب `vendor`، تسجل النتيجة كقيد بيئي ولا يدّعى نجاح اختبارات PHP.

يجب كذلك تنفيذ اختبار متصفح يدوي أو آلي للتدفقات الأربعة الحساسة قبل إعلان الاكتمال.

## 13. تعريف الاكتمال النهائي

لا يعلن اكتمال المهمة الجديدة إلا عند تحقق جميع الآتي:

- إزالة قائمة `protectedLegacyInlineEventFiles` بالكامل.
- صفر event handlers مضمّنة داخل Blade.
- نجاح فحص الهوية والبناء.
- نجاح اختبارات PHP في بيئة مكتملة الاعتمادات.
- اختبار تدفقات التحصيل والمديونية والموازنة والمبيعات اليومية.
- عدم تغير أي payload أو مسار أو نتيجة مالية أو مخزنية.
- توثيق أي استثناء تقني متبقٍ بسبب PDF أو البريد فقط.
