# مراجعة شاملة لنظام طلبيات التوريد

**تاريخ المراجعة:** 2026-08-08  
**النطاق:** المسارات، الصلاحيات، دورة الحالات، الجرد، الاستلام، الاعتماد المخزني، PDF، الواجهات، الاختبارات، والملفات المشتبه في قدمها.  
**المرجع البصري:** `docs/الهوية-البصرية-للمشروع.md`.  
**المرجع الوظيفي:** `docs/المواصفات-المعتمدة-لنظام-طلبيات-التوريد.md`.

## 1. القرار التنفيذي

النظام يملك أساسًا وظيفيًا جيدًا: يفصل الجرد عن تغيير المخزون، يؤجل الإضافة الفعلية إلى الاعتماد النهائي، ويقيد طلبيات المالك بمتجره وطلبيات المحاسب بمتجره. لكنه **ليس جاهزًا للإغلاق النهائي** قبل إغلاق نقاط السباق والتتبع، وتثبيت الدورة باختبارات Feature متكاملة.

لم تُعدَّل الحسابات أو المخزون أو الصلاحيات، ولم يُحذف أي ملف، لأن قواعد المشروع تشترط إبلاغ المالك قبل هذه التغييرات. الأقسام 7 و2 أدناه هي الإبلاغ المطلوب وتحدد الموافقات اللازمة.

## 2. الثغرات والمخاطر البرمجية

### P0 — يمنع الاعتماد حتى يُحسم

1. **الاختبار الكامل غير ممكن في البيئة الحالية.** مجلد `vendor` غير مثبت، ومحاولة `composer install --no-interaction --prefer-dist` توقفت بسبب HTTP 403 من GitHub. لذلك لا يوجد دليل تشغيلي من هذه المراجعة على سلامة الحسابات والهجرات.
2. **الدورة مغطاة باختبار خدمة، ويبقى التشغيل الفعلي.** أضيف اختبار يغطي `draft → sent → received → approved` ويثبت عدم تغير المخزون قبل الاعتماد. يبقى تشغيله وإضافة دورة HTTP متكاملة بعد توفر `vendor`.

### P1 — مخاطر عالية

1. **أغلقت مخاطر السباق.** أصبحت الانتقالات الحساسة تعيد قراءة الطلبية بقفل `lockForUpdate()` داخل transaction قبل تغيير الحالة.
2. **وُحدت التنبيهات بعد نجاح المعاملة.** تستخدم عمليات الطلبيات خدمة تنبيهات مركزية تنفذ الإنشاء عبر `DB::afterCommit`.
3. **وُسعت اختبارات HTTP للملكية.** تغطي العرض والتعديل والجرد والاستلام وPDF لمنع محاسب من طلبية محاسب آخر. يبقى تشغيلها في بيئة Laravel مكتملة.

### P2 — مخاطر متوسطة

1. **أغلقت ملاحظة الفلترة.** تدعم قائمتا المالك والمحاسب الفلترة بحالة `workflow_status` مع تسميات عربية مركزية.
2. **القواعد موزعة بين controller كبير وservice كبير.** ملف العرض يتجاوز 1300 سطر، و`form-interface.js` يتجاوز 800 سطر، و`show-interface.js` يتجاوز 500 سطر. هذا يزيد مخاطر الانحدار وليس دليلًا على أنها غير مستخدمة. يقترح تقسيمها بحسب المرحلة بعد إضافة اختبارات انحدار، لا حذفها.
3. **الهجرات التوافقية تعتمد على فحوص مخطط متكررة.** هذا مقصود لحماية قواعد سابقة، لكن يجب اختبار الترقية من لقطة حقيقية بالإضافة إلى `migrate:fresh`.

## 3. مراجعة الحالات ومتطلباتها

| المرحلة | الحالة الأساسية | حالة الدورة | المنفذ | المتطلبات | الأثر |
| --- | --- | --- | --- | --- | --- |
| إنشاء | `draft` | `pending_owner_review` | مالك/محاسب | بند صالح على الأقل، متجر مصرح | لا أثر مخزني |
| إرجاع للتعديل | `draft` | `returned_for_edit` | المالك | ملاحظة إلزامية | يفتح التعديل للمحاسب المرتبط |
| إرجاع للجرد | `draft` | حالة مراجعة المالك | المالك | منتجات مخزنية محددة وملاحظة | لا تسوية مخزنية |
| حفظ الجرد | `draft` | `count_draft` | المحاسب | كمية ووحدة لكل سطر مطلوب | لا تغيير للمخزون |
| إرسال الجرد | `draft` | `pending_owner_after_count` | المحاسب | حفظ لقطة النظام والمحاولة | مقارنة فقط |
| إرسال للمورد | `sent` | `pending_receipt_confirmation` | المالك | مورد، بنود، وانتهاء/تجاوز الجرد | يقفل المسودة؛ لا مخزون |
| تسجيل الاستلام | `received` | `pending_owner_receipt_review` أو `pending_inventory_approval` | محاسب/مالك | كمية، وحدة، تكلفة، وحل البنود المخصصة | لا مخزون بعد |
| اعتماد مخزني | `approved` | `approved_and_supplied` | المالك | مراجعة استلام، تاريخ، ربط المنتجات | هنا فقط يزاد المخزون/تسجل مشتريات المالك |
| رفض | مسجل مع الدورة | مرفوض | المالك | سبب غير فارغ | لا مخزون، ويجب حفظ الأثر |
| إلغاء | `cancelled` | ملغى | المالك | حالة مسموحة | لا مخزون |

### شروط قبول الحالات

- تُنشأ مصفوفة انتقالات مركزية تمنع كل انتقال غير مذكور.
- يسجل كل انتقال: السابق، اللاحق، المنفذ، الوقت، الملاحظة، والبند عند انطباقه.
- يمنع أي انتقال متزامن بقفل صف وإعادة الفحص داخل transaction.
- لا ينفذ الإشعار قبل commit، ويجب أن يكون قابلًا للإعادة دون تكرار.

## 4. هل ملفات PDF تخدم الصفحات؟

| PDF | موضعه | متى يكون صحيحًا | التقييم |
| --- | --- | --- | --- |
| طلبية التوريد | صفحة العرض للمالك | المسودة/قبل الاستلام | **مفيد** كمستند طلب للمورد، مع خيار إخفاء الأسعار |
| ورقة الاستلام | صفحة الطلبية/المحاسب | `sent` | **مفيدة** كورقة عمل؛ يجب ألا تُسمى سجل استلام قبل التأكيد |
| سجل الاستلام | صفحة العرض | `received` أو `approved` | **مفيد** للمطابقة والأرشفة |
| سجل الاعتماد المخزني | صفحة الطلبية للمالك | `approved` فقط | **مفيد وضروري** كأثر نهائي |
| مستند الجرد | صفحة الجرد | `returned_to_accountant` أو `count_draft` | **مفيد** للعد الميداني، وهو لا يكشف كمية النظام أو الفرق |

### ملاحظات PDF الواجب إصلاحها

1. `pdf.blade.php` يحتوي عدة خصائص `style="..."`. استثناء PDF يسمح بـ`<style>` في الرأس، لكن الهوية تطلب تجميع القواعد واستعمال classes متى أمكن.
2. يجب اختبار خط Cairo المضمن، RTL، الهوامش، وتكرار رأس الجدول مع 1، 20، و100 بند.
3. يجب إضافة اختبارات HTML تثبت أن PDF المحاسب لا يحتوي أسماء حقول أو قيم `system_quantity_snapshot`، الفرق، أو تكلفة لا يحق له رؤيتها.
4. يجب ربط كل زر PDF بالحالة نفسها في الخادم، لا الإخفاء البصري فقط. التحقق الحالي موجود في controller ويحتاج تثبيته باختبارات انحدار.

## 5. الهوية البصرية وتجربة الاستخدام

### ما تم التحقق منه

- لا يوجد `<style>` أو `style="..."` في واجهات Blade التفاعلية للنظام؛ الحالات الموجودة محصورة في قوالب PDF.
- سكربتات الواجهة منقولة إلى `resources/js/features/purchase-orders` وليست كتلاً مضمنة في Blade.
- فحص الهوية كان يتوقف على مصطلح قديم في مستند تاريخي؛ تم توحيده إلى «التاريخ» وفق مرجع الهوية.

### إصلاحات بصرية مقترحة

1. تقسيم صفحة العرض إلى partials بحسب المرحلة: الملخص، البنود، الجرد، الاستلام، الاعتماد، وسجل الأحداث، مع إبقاء الشكل والمنطق دون تغيير.
2. عرض «الإجراء المطلوب الآن» في أعلى الصفحة كنص وشارة، لا باللون وحده.
3. إبقاء إجراء رئيسي واحد واضح، ونقل الإجراءات النادرة/الخطرة إلى قسم منفصل في نهاية الصفحة.
4. اختبار الوضعين المظلم والفاتح على عروض 360، 768، و1366 بكل حالة دورة، لا بصفحة مسودة فقط.
5. تحويل جداول البنود في الجوال إلى بطاقات أو حاوية تمرير مع بقاء اسم المنتج والإجراء واضحين.

## 6. الملفات والدوال القديمة

### نتيجة التتبع

- **لا يوجد ملف برمجي يمكن حذفه بأمان بناءً على التتبع الساكن وحده.** الموديلات والخدمة ومنشئ PDF ومساعدا التكلفة والترتيب كلها مرتبطة.
- `StorePurchaseOrderCountAttempt` و`StorePurchaseOrderEvent` ليسا مخلفات؛ هما جزء من التتبع ومحاولات الجرد.
- `App\Models\Purchase` ليس نظام طلبيات مكررًا؛ يستعمل لتسجيل بنود مشتريات المالك عند الاعتماد.
- `routes/purchase-orders.php` مدخل مسارات المالك ويُضمن من `routes/user.php`؛ لا يحذف.

### مرشحات التنظيف بعد الموافقة

1. المستندات `docs/تطوير-طلبيات-التوريد.md`، `docs/تطوير-نظام-الطلبيات.md`، و`docs/المتبقي-لإكمال-نظام-طلبيات-التوريد.md` تحتوي مراحل تاريخية متداخلة. الأفضل إبقاؤها مؤقتًا مع شارة «تاريخي»، ثم أرشفتها في commit منفصل بعد تأكيد أن المواصفات المعتمدة تغطي كل القرارات.
2. لا تحذف أي migration مطبقة؛ إزالتها تكسر إنشاء قاعدة جديدة وتاريخ الترقية.
3. لا تحذف partial أو JavaScript بناءً على عدم وجود مرجع PHP مباشر؛ يجب فحص مدخلات Vite و`data-*` والتحميل الديناميكي أولًا.

## 7. موافقات مطلوبة قبل الإصلاح

يلزم رد صاحب المشروع على هذه النقاط قبل التنفيذ، لأنها تمس الحالات أو المخزون أو الحذف:

1. هل توافق على تحويل كل انتقالات الحالة إلى transactions بقفل صف وإشعار after-commit؟
2. هل عند وجود فرق جرد يكفي التنبيه ويجوز الاستمرار، أم يمنع الإرسال حتى التسوية؟ المواصفة الحالية تقول: تنبيه مع جواز الاستمرار.
3. هل تريد الحذف النهائي بعد الإلغاء، أم soft delete والأرشفة فقط؟ التوصية: الأرشفة فقط لحماية الأثر.
4. هل توافق على أرشفة المستندات التاريخية الثلاثة المذكورة في القسم 6 بعد دمج القرارات الفريدة؟
5. هل توافق على تقسيم controller/service/Blade/JavaScript مع منع أي تغيير وظيفي؟

## 8. خطة الإصلاح المقترحة

1. **منفذ:** توحيد الحالات والفلاتر وبوابة PDF.
2. **منفذ:** قفل انتقالات الحالة وجدولة التنبيهات بعد commit.
3. **منفذ:** توسيع اختبارات الصلاحيات وPDF والدورة، مع اختبار 1 و20 و100 بند.
4. **منفذ جزئيًا:** فصل خدمة PDF وخدمة التنبيهات وأدوات الدعم عن الملفات الكبيرة.
5. **ينفذه صاحب المشروع:** تثبيت dependencies وتشغيل بوابة القبول والقبول البصري الموثق في الوضعين والجوال.
6. **مؤجل لموافقة منفصلة:** أرشفة المستندات التاريخية، من دون حذف migrations أو سجلات التتبع.

## 9. بوابة القبول

لا يعتمد النظام قبل نجاح:

```bash
php artisan test --testsuite=Unit --filter='PurchaseOrder|StorePurchaseOrder'
php artisan test --testsuite=Feature --filter=PurchaseOrder
npm run test:visual
npm run build
npm run test:contrast
find app/Modules/PurchaseOrders routes -type f -name '*.php' -print0 | xargs -0 -n1 php -l
```

ويلزم إضافة قبول يدوي موثق للوضعين، الجوال، الأدوار، وكل PDF بطلبية قصيرة وطلبية طويلة.

## 10. التصحيح المعتمد لمرحلة تأكيد الاستلام

1. يؤكد المحاسب ما وصل من المورد: الكمية، الوحدة، وسعر الكمية المستلمة. تظهر وحدة البيع الافتراضية وتفاصيل الطقم/الحبة أو الرول/المتر، ويعاد حساب السعر عند تغيير الكمية أو الوحدة.
2. لا يحق للمحاسب اعتماد تحديث تكلفة المنتج. هو يسجل سعر المورد فقط، ويظهر الفرق للمالك.
3. يصل تنبيه «تم تأكيد الاستلام من المحاسب» إلى المالك، ويفتح صفحة مستقلة بعنوان «مراجعة تأكيد الاستلام». لا تعرض هذه المرحلة إجراءات الاعتماد المخزني.
4. تظهر علامة «عدّله المحاسب» على كل بطاقة غُيرت كميتها أو وحدتها أو سعرها أو ملاحظتها.
5. يملك المالك نافذة واحدة لكل بند غير مربوط. تسمح النافذة بالبحث والربط بمنتج موجود، أو إنشاء منتج بيع، أو إنشاء منتج مشتريات مالك، وتربط النتيجة بالبند فور الحفظ.
6. ينقل زر «تأكيد الاستلام» الطلبية إلى مرحلة «الاعتماد المخزني». في صفحة الاعتماد تستعمل التسميات «الكمية الآن» و«الكمية المستلمة»، ولا تعرض «المخزون وقت تأكيد الجرد».
7. تظهر تنبيهات الحالا المختصرة فقط؛ لا يظهر شرح آلية لقطة المخزون للمحاسب، وتبقى تعليمات PDF في أسفل الوثيقة.
