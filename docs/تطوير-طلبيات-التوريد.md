# تطوير نظام طلبيات التوريد وربطه بالجرد

> **مستند تاريخي:** حلت مواصفات `docs/المواصفات-المعتمدة-لنظام-طلبيات-التوريد.md` محل هذه الخطة، ولا يستخدم هذا المستند لتنفيذ الدورة الجديدة.

## 1. الهدف

هذا المستند هو مرجع تنفيذ دورة مراجعة الجرد داخل نظام طلبيات التوريد، بحيث يستطيع المحاسب تجهيز طلبية توريد دون كشف كميات المخزون له، ثم يستطيع المالك مراجعتها، وإرجاعها للمحاسب لإدخال جرد فعلي، ثم مقارنة جرد المحاسب مع لقطة مخزون النظام عند الإرسال.

الدورة المقصودة هنا هي **مراجعة ومقارنة فقط**، وليست تسوية مخزون. لا يتم تعديل رصيد المنتجات بسبب إدخال الجرد، ولا يتم اعتماد أي فرق مخزني ضمن هذه الدورة إلا من خلال إجراء مستقل وصريح خارج الطلبية.

## 2. القواعد الملزمة

1. لا يكشف النظام كمية المخزون الحالية للمحاسب داخل طلبية التوريد أو PDF الجرد الورقي.
2. لا يكشف النظام الفرق بين جرد المحاسب ورصيد النظام للمحاسب.
3. يحفظ النظام لقطة رصيد النظام لكل منتج عند إرسال الجرد للمالك، وليس عند فتح الصفحة فقط.
4. أي حركة مخزنية بعد إرسال الجرد لا تغيّر اللقطة المحفوظة.
5. يرى المالك وحده كمية المحاسب، ولقطة النظام، والفرق، ونوع الفرق.
6. الجرد داخل الطلبية لا يعدل المخزون تلقائيًا.
7. الاعتماد المخزني النهائي يبقى مرتبطًا بدورة الاستلام والاعتماد الحالية، ولا يتحول إلى تسوية فروقات جرد.
8. إذا كانت مراجعة الجرد قيد التنفيذ، يمنع الاعتماد المخزني النهائي حتى تكتمل أو تعتمد من المالك.
9. الإلغاء أفضل من الحذف الفعلي للحفاظ على سجل المراجعة والحالات.
10. جميع واجهات الويب تلتزم بالهوية البصرية المركزية، ولا يضاف CSS داخل Blade.
11. قوالب PDF مسموح لها بتنسيق طباعة داخلي محدود حسب قواعد الهوية البصرية الخاصة بالطباعة.

## 3. الأدوار والصلاحيات

### 3.1 المحاسب

يسمح للمحاسب بما يلي:

- إنشاء طلبية توريد حسب الصلاحية المعتمدة في المشروع.
- إضافة منتجات أو أسطر مخصصة حسب القواعد الحالية.
- إرسال الطلبية للمالك أو إدخال الجرد عندما يعيدها المالك للجرد.
- حفظ جرد فعلي مؤقت لكل منتج مطلوب.
- إرسال الجرد للمالك عند اكتمال الكميات.
- تصدير PDF جرد ورقي لا يحتوي على رصيد النظام أو الفروقات.

يمنع على المحاسب ما يلي:

- رؤية كمية النظام الحالية.
- رؤية لقطة كمية النظام وقت إرسال الجرد.
- رؤية الفرق بين الجرد والنظام.
- اعتماد الطلبية بدل المالك.
- إجراء تسوية مخزنية من داخل جرد الطلبية.

### 3.2 المالك

يسمح للمالك بما يلي:

- مراجعة الطلبية بعد إرسالها.
- اعتماد الطلبية وفق دورة التوريد الحالية.
- رفض أو إلغاء الطلبية مع ملاحظة عند الحاجة.
- تعديل الطلبية عندما تكون حالتها تسمح بذلك.
- إرجاع الطلبية للمحاسب لإدخال الجرد مع ملاحظة اختيارية.
- مراجعة كمية المحاسب ولقطة النظام والفرق بعد إرسال الجرد.
- اعتماد مراجعة الجرد فقط، دون تعديل المخزون.
- إرجاع الجرد للمحاسب مرة أخرى عند الحاجة.

## 4. حالات الطلبية وحالات الجرد

### 4.1 حالات الطلبية الأساسية

الحالات الأساسية الحالية للطلبية تبقى كما هي:

| الحالة | المعنى |
| --- | --- |
| `draft` | مسودة قابلة للتعديل قبل الإرسال. |
| `sent` | تم إرسال الطلبية/اعتماد إرسالها ضمن دورة التوريد. |
| `received` | تم تسجيل بيانات الاستلام بانتظار الاعتماد المخزني. |
| `approved` | تم الاعتماد المخزني النهائي وإغلاق الطلبية. |
| `cancelled` | تم إلغاء الطلبية مع الحفاظ على السجل. |

### 4.2 حالات مراجعة الجرد داخل الطلبية

تم فصل حالة مراجعة الجرد عن حالة الطلبية الأصلية حتى لا نكسر دورة التوريد الحالية:

| الحالة | المعنى |
| --- | --- |
| `null` | لا توجد مراجعة جرد مطلوبة لهذه الطلبية. |
| `returned_to_accountant` | أعاد المالك الطلبية للمحاسب لإدخال الجرد. |
| `count_draft` | بدأ المحاسب إدخال الجرد وحفظه مؤقتًا. |
| `pending_owner_after_count` | أرسل المحاسب الجرد للمالك مع حفظ لقطة النظام. |
| `approved` | اعتمد المالك مراجعة الجرد فقط. |

## 5. تدفق العمل التفصيلي

### 5.1 إنشاء الطلبية

1. ينشئ المحاسب أو المالك الطلبية حسب الصلاحية الحالية.
2. تضاف المنتجات النظامية أو المنتجات المخصصة.
3. لا تظهر للمحاسب كميات المخزون الحالية.
4. تبقى الطلبية مسودة حتى إرسالها.

### 5.2 مراجعة المالك الأولى

بعد إرسال الطلبية، يستطيع المالك:

- متابعة دورة الاستلام والاعتماد الحالية.
- إرجاع الطلبية للجرد إذا احتاج مراجعة مخزون فعلية قبل القرار.
- إلغاء الطلبية عند الحاجة بدل حذفها نهائيًا.

### 5.3 إرجاع الطلبية للجرد

عند ضغط المالك على إرجاع للجرد:

1. تتحول حالة مراجعة الجرد إلى `returned_to_accountant`.
2. تحفظ ملاحظة المالك إن وجدت.
3. تحدد الأسطر المخزنية التي تحتاج جردًا.
4. لا يضاف أو يخصم أي رصيد مخزني.

لا تدخل أسطر مشتريات المالك أو الأسطر غير المخزنية في مقارنة الجرد، لأنها لا تمثل رصيدًا مخزنيًا مباشرًا.

### 5.4 إدخال جرد المحاسب

صفحة جرد المحاسب تعرض:

- اسم المنتج.
- كود المنتج أو التعريف المتاح عند توفره.
- الكمية المطلوبة في الطلبية.
- حقل كمية الجرد الفعلية.
- حقل ملاحظة اختيارية.

ولا تعرض:

- كمية النظام.
- الفرق.
- حالة نقص أو زيادة.
- أي مؤشر يكشف مخزون النظام مباشرة أو بشكل غير مباشر.

### 5.5 حفظ الجرد مؤقتًا

عند الحفظ المؤقت:

1. تحفظ كميات المحاسب وملاحظاته.
2. تصبح حالة المراجعة `count_draft`.
3. لا تحفظ لقطة النظام النهائية بعد.
4. لا يظهر الفرق لأي محاسب.

### 5.6 إرسال الجرد للمالك

عند إرسال الجرد للمالك:

1. يجب إدخال كمية الجرد لكل منتج مطلوب.
2. تحفظ كمية المحاسب.
3. تحفظ ملاحظة المحاسب.
4. تحفظ لقطة كمية النظام لكل منتج في نفس لحظة الإرسال.
5. يحفظ وقت اللقطة ووقت الإرسال.
6. يحفظ المستخدم الذي أرسل الجرد.
7. تتحول حالة المراجعة إلى `pending_owner_after_count`.

اللقطة المحفوظة هي المرجع الافتراضي للمقارنة، حتى لو حدثت مبيعات أو توريدات أو نقل مخزني بعد ذلك.

### 5.7 مراجعة المالك بعد الجرد

يرى المالك جدول مقارنة يحتوي على:

- اسم المنتج.
- الكمية المطلوبة في الطلبية.
- كمية جرد المحاسب.
- لقطة كمية النظام وقت إرسال الجرد.
- الفرق.
- نوع الفرق: مطابق، نقص، زيادة.
- ملاحظة المحاسب.
- وقت إرسال الجرد.

خيارات المالك بعد الجرد:

- اعتماد مراجعة الجرد فقط.
- إرجاعها للمحاسب مرة أخرى مع ملاحظة.
- متابعة دورة التوريد الحالية حسب حالة الطلبية.
- رفض أو إلغاء الطلبية حسب القواعد التشغيلية.

## 6. قواعد الاعتماد والرفض والإلغاء

لا تعتمد مراجعة الجرد إذا:

- لم يرسل المحاسب الجرد للمالك.
- توجد أسطر مطلوبة للجرد بلا لقطة مخزون محفوظة.
- توجد أسطر مطلوبة بلا كمية جرد عند الإرسال.

لا يعتمد المخزون النهائي إذا:

- الطلبية لم تصل إلى حالة `received`.
- مراجعة الجرد في حالة `returned_to_accountant` أو `count_draft` أو `pending_owner_after_count`.
- توجد بيانات استلام ناقصة تمنع الاعتماد الحالي.
- المستخدم لا يملك صلاحية الاعتماد.

اعتماد مراجعة الجرد لا يعني:

- تعديل كمية المنتج.
- تسوية الفرق.
- اعتماد توريد المورد.
- إغلاق الطلبية مخزنيًا.

## 7. PDF الجرد الورقي

PDF الجرد الورقي مخصص للمحاسب أو للجرد الميداني.

يحتوي على:

- رقم الطلبية.
- اسم المتجر.
- اسم المورد عند توفره.
- تاريخ إنشاء النموذج.
- قائمة المنتجات المطلوب جردها.
- الكمية المطلوبة.
- خانة كمية الجرد.
- خانة الملاحظات.

ويمنع أن يحتوي على:

- رصيد النظام.
- لقطة النظام.
- الفرق.
- حالة نقص أو زيادة.
- أي تكلفة أو قيمة تكشف المخزون الداخلي إذا لم تكن مطلوبة للجرد الورقي.

## 8. سجل العمليات والأرشفة

كل انتقال حالة مهم يجب أن يكون قابلًا للتتبع:

- من نفذ الإجراء.
- وقت الإجراء.
- الحالة السابقة.
- الحالة الجديدة.
- الملاحظة إن وجدت.
- هل تم حفظ لقطة مخزون.

في المرحلة الحالية تحفظ الحقول الأساسية داخل الطلبية والبنود، ويجب عند استكمال سجل الأحداث التفصيلي إضافة جدول أو خدمة سجل مخصصة لانتقالات حالات الطلبية والجرد دون حذف السجل عند الرفض أو الإلغاء.

## 9. الإشعارات المطلوبة

الإشعارات المطلوبة عند استكمال دورة الإشعارات:

| الحدث | المستقبل | النص المقترح |
| --- | --- | --- |
| إرسال طلبية جديدة | المالك | توجد طلبية توريد بانتظار مراجعتك. |
| إرجاع الطلبية للجرد | المحاسب | أعاد المالك طلبية توريد لإدخال الجرد. |
| إرسال الجرد للمالك | المالك | تم إرسال جرد طلبية توريد للمراجعة. |
| رفض الطلبية | المحاسب | تم رفض طلبية توريد، راجع الملاحظة. |
| إرجاع الجرد مرة أخرى | المحاسب | أعيد جرد الطلبية للمراجعة مرة أخرى. |

لا تحتوي الإشعارات على:

- كميات مخزون.
- فروقات.
- أسماء منتجات تكشف نقصًا حساسًا إذا كانت قواعد المشروع تمنع ذلك.

## 10. التعامل مع التاريخ والوقت

يعتمد النظام على التاريخ والوقت الكاملين للأحداث المهمة:

- وقت إرسال الطلبية.
- وقت إرجاعها للجرد.
- وقت حفظ الجرد مؤقتًا.
- وقت إرسال الجرد للمالك.
- وقت حفظ لقطة المخزون.
- وقت الاعتماد أو الإلغاء.

أما المقارنة نفسها فتستخدم لقطة النظام المحفوظة عند إرسال الجرد، وليس الرصيد الحالي.

## 11. التعديل بعد الجرد

إذا عدّل المالك سطرًا بعد إرسال الجرد:

1. يجب تعليم السطر بأنه تغيّر بعد الجرد.
2. يجب أن تظهر ملاحظة للمالك أن المقارنة السابقة قد لا تمثل السطر بعد تعديله.
3. إذا أضيف منتج مخزني جديد بعد الجرد، يجب أن يحتاج إلى مراجعة أو جرد جديد قبل الاعتماد حسب قرار المشروع.
4. حذف سطر له جرد محفوظ لا يجب أن يحذف أثره من سجل العمليات عند استكمال سجل الأحداث التفصيلي.

## 12. الاختبارات المطلوبة

### 12.1 اختبارات الصلاحيات

- المحاسب يستطيع إنشاء طلبية حسب صلاحياته.
- المحاسب لا يستطيع رؤية رصيد النظام.
- المحاسب لا يستطيع رؤية الفروقات.
- المحاسب لا يستطيع اعتماد الطلبية بدل المالك.
- المالك يستطيع إرجاع الطلبية للجرد.
- المالك وحده يرى مقارنة الجرد مع لقطة النظام.

### 12.2 اختبارات الحالات

- انتقال الطلبية من مسودة إلى مرسلة.
- انتقال مراجعة الجرد إلى `returned_to_accountant`.
- انتقال مراجعة الجرد إلى `count_draft` عند الحفظ المؤقت.
- انتقال مراجعة الجرد إلى `pending_owner_after_count` عند الإرسال.
- اعتماد مراجعة الجرد إلى `approved`.
- منع الاعتماد المخزني النهائي أثناء وجود مراجعة جرد غير مكتملة.

### 12.3 اختبارات اللقطة والفروقات

- تحفظ كمية المحاسب لكل سطر عند الإرسال.
- تحفظ لقطة النظام لكل سطر عند الإرسال.
- أي حركة مخزنية بعد الإرسال لا تغير اللقطة.
- الفرق المعروض للمالك يحسب من اللقطة المحفوظة.
- المحاسب لا يستطيع الوصول إلى اللقطة من الواجهة أو PDF.

### 12.4 اختبارات PDF

- PDF الجرد يعرض المنتجات وحقول الجرد.
- PDF لا يحتوي رصيد النظام.
- PDF لا يحتوي الفروقات.
- PDF لا يحتوي مؤشرات نقص أو زيادة.
- PDF واضح وقابل للطباعة بالعربية.

### 12.5 اختبارات الهوية البصرية

- لا يوجد CSS داخل Blade في واجهات الويب.
- تستخدم الواجهات كلاسات ومكونات المشروع المركزية.
- تعمل الصفحة في الوضع المظلم والفاتح.
- الجداول قابلة للاستخدام على الشاشات الصغيرة.
- الأزرار المهمة واضحة ولا تعتمد على hover فقط.

### 12.6 اختبارات الانحدار

- دورة التوريد الحالية تعمل كما هي عند عدم استخدام الجرد.
- الاعتماد المخزني المرتبط بتاريخ العملية المالية لا يتغير.
- التقارير الحالية لا تتغير بسبب إدخال جرد داخل الطلبية.
- اعتماد مراجعة الجرد لا يضيف ولا يخصم من المخزون.

## 13. حالة التنفيذ الحالية

تم تنفيذ الأساس التالي في الكود:

- حقول قاعدة البيانات لحالة مراجعة الجرد ولقطات البنود.
- خصائص وح casts في موديلات الطلبية والبنود.
- مسارات إرجاع الطلبية للجرد، إدخال الجرد، حفظه، إرساله، واعتماد مراجعته.
- صفحة إدخال جرد لا تعرض رصيد النظام أو الفروقات.
- PDF جرد ورقي لا يعرض رصيد النظام أو الفروقات.
- جدول مقارنة للمالك عند وصول الجرد.
- منع الاعتماد المخزني النهائي أثناء وجود مراجعة جرد غير مكتملة.

ما يجب استكماله لاحقًا:

- مدخل محاسب كامل لإنشاء الطلبيات ضمن صلاحيات المحاسب بدل المسار المؤقت.
- سجل انتقالات حالات تفصيلي منفصل إن لم يكن سجل العمليات المركزي يغطي كل الأحداث.
- إشعارات فعلية لكل انتقال حالة.
- تعليم السطر تلقائيًا عند تعديله بعد الجرد.
- اختبارات Feature/Unit شاملة لدورة الجرد والصلاحيات والـ PDF.

## 14. معيار القبول النهائي

تقبل المهمة عند تحقق التالي:

1. يستطيع المحاسب إنشاء طلبية وإرسالها دون رؤية كميات المخزون.
2. يستطيع المالك إرجاع الطلبية للجرد.
3. يستطيع المحاسب إدخال الجرد وحفظه أو إرساله.
4. تحفظ لقطة النظام وقت إرسال الجرد.
5. يرى المالك الفروقات بوضوح.
6. لا يعدل الجرد المخزون تلقائيًا.
7. يستطيع المالك اعتماد مراجعة الجرد أو إرجاعها.
8. يحفظ سجل كامل للحالات والملاحظات.
9. يعمل PDF الجرد دون كشف المخزون.
10. تنجح اختبارات الصلاحيات والحالات والجرد وPDF والهوية والانحدار.

## 14.1 قاعدة واجهات طلبيات التوريد المشتركة

- صفحة الطلبيات الرئيسية، وصفحة إنشاء الطلبية، وصفحة معاينة الطلبية السابقة أو المعتمدة تستخدم قالبًا مشتركًا للمالك والمحاسب قدر الإمكان.
- الحكم بما يظهر داخل القالب يكون من خلال سياق الدور والصلاحيات، وليس عبر نسخ صفحات متشابهة لكل دور.
- سياق المحاسب داخل القالب المشترك يمنع عرض رصيد النظام، تكلفة النظام، فروقات الجرد، أو أي مؤشر يكشف حالة المخزون بشكل مباشر أو غير مباشر.
- سياق المالك داخل القالب نفسه يسمح بعرض المقارنة ولقطة النظام وأزرار الاعتماد أو الإرجاع بحسب الحالة والصلاحية.
- إذا احتاج دور معيّن إجراءً مختلفًا، يضاف شرط عرض واضح داخل القالب المشترك أو مكوّن مشترك، ولا تنشأ صفحة منفصلة إلا لمرحلة متخصصة مثل إدخال الجرد أو PDF الطباعة.
- تظهر في بحث المحاسب منتجات المخزون ومنتجات مشتريات المالك نفسها المتاحة للمالك، مع حجب أرصدة النظام والتكاليف وفروقات الجرد فقط.
- تحفظ مسودة المتصفح بمفتاح مستقل يجمع نوع المستخدم ومعرّفه والمتجر، فلا تختلط مسودة المالك بمسودة المحاسب أو بمستخدم آخر.
- تتم مراجعة جرد الطلبية، عند طلبها، قبل إرسال الطلبية للمورد. ولا يسمح بالإرسال حتى يعتمد المالك مراجعة الجرد، بينما تبقى الطلبية التي لم يطلب لها جرد قابلة للإرسال وفق المسار المعتاد.
- اسم المورد والملاحظة العامة من بيانات المالك؛ ينشئ المحاسب البنود والكميات المطلوبة ثم يكمل المالك هذه البيانات عند المراجعة.
- يعرض اسم الطلبية بصيغة تشغيلية واضحة: «طلبية + اسم المورد + يوم-شهر»، بدل الاعتماد على رقم السجل وحده.

## 14.2 توافق قواعد البيانات السابقة

- الهجرة `2026_08_05_000001` لا تنشئ أعمدة؛ وجودها يحفظ ترتيب سجل الهجرات للقواعد التي طبقت أعمدة دورة الجرد يدويًا من قبل.
- الهجرة `2026_08_05_000002` هي المسؤولة عن مطابقة المخطط، وتضيف فقط الأعمدة غير الموجودة دون إعادة إنشاء `inventory_review_status` أو `inventory_submitted_at` أو حذف بيانات سابقة.
- عند فشل محاولة سابقة بسبب عمود مكرر، يكفي استبدال ملفات الهجرة بالإصدار الحالي ثم تشغيل `php artisan migrate` مجددًا؛ لا يلزم حذف العمود أو بيانات الطلبيات.
