# المستند الموحد لتدقيق وإغلاق إصلاحات الواجهات

> حالة التنفيذ: اكتمل استخراج ربط الأحداث من الواجهات الحساسة، وأزيلت الاستثناءات المؤقتة، وأصبحت بوابة الواجهة تمر على كل ملفات Blade بلا استثناءات تشغيلية.
> تاريخ آخر تدقيق للحصر: 2026-07-29.

## النطاق الشامل

- تفحص البوابة جميع ملفات `resources/views/**/*.blade.php` تلقائيًا، لذلك لا تحتاج إضافة كل نظام يدويًا إلى قائمة ثابتة.
- تشمل صفحات المالك والمحاسب والمدير والمتاجر والموظفين والفواتير والمنتجات والمخزون والنقل والأقسام والتقارير والاشتراكات والمصادقة والأخطاء والمكونات المشتركة.
- تمنع خصائص أحداث DOM المضمّنة، بما فيها أحداث النقر والتغيير والإدخال والإرسال والتركيز، داخل جميع ملفات Blade بلا قائمة استثناءات.
- تمنع `<style>` و`style="..."` وأقسام الأنماط المحلية في واجهات الويب.

## الواجهات الحساسة المستخرجة

- تحصيل الآجل: استخرجت دوال الفتح والإغلاق والمعاينة والتحصيل الكامل والجزئي إلى `resources/js/features/accountant/credit-collection.js`، وأصبح Blade يمرر بيانات الصفحة والمسار وCSRF عبر عقد إعداد آمن فقط.
- المديونيات: استخرجت دوال إدارة الموظف وفتح التحصيل والتحصيل الكامل والجزئي إلى `resources/js/features/accountant/debt-operations.js`، وأصبح Blade يمرر قوالب المسارات عبر عقد إعداد آمن فقط.
- موازنة المحاسب وقرار الشفت: نقل اعتراض إرسال النموذج ورسالة قرار تاريخ العمل إلى وحدة JavaScript مستقلة، مع بقاء أسماء الحقول والقيم ومسار النموذج كما هي.
- المبيعات اليومية: استخرجت أحداث عرض التفاصيل ونوافذ التعديل واختيار الوحدة والبحث والكميات والدفع والإجمالي إلى `resources/js/features/stores/daily-sales.js`، وأصبح Blade يمرر بيانات العمليات والمنتجات والمسارات والقيم المعادة من التحقق عبر عقد إعداد آمن.
- ربطت الوحدات الجديدة من مدخل Vite المركزي، ولذلك لا تحتاج الواجهات إلى تحميل سكربتات مستقلة أو تعريف event handlers داخل العناصر.

## تصنيف السكربتات المتبقية داخل Blade

- استخرجت الواجهات الحساسة الأربع المستهدفة: تحصيل الآجل، والمديونيات، وقرار الموازنة، والمبيعات اليومية؛ وبقيت بيانات كل صفحة المولدة من الخادم داخل Blade في عقود إعداد آمنة دون نقل الحسابات إلى الخادم أو تغيير آلية القراءة والكتابة.
- هذا المتبقي مصنف على أنه منطق مالي/مخزني محمي، وليس ربط واجهة عام؛ لم يُعاد تصميم معادلاته أو payload الخاص به في هذه الدفعة.
- أي نقل إضافي لهذه المعادلات إلى ملفات خارجية يتطلب اختبارات تدفق متصفح للبيانات الحقيقية وموافقة مستقلة إذا استلزم تغيير آلية القراءة أو الكتابة.
- قوالب PDF والطباعة والبريد تبقى مستثناة من منع CSS المضمّن فقط، لأن محركات PDF وعملاء البريد قد لا تحمل CSS التطبيق؛ ولا يشمل الاستثناء خصائص أحداث JavaScript.

## تدقيق السكربتات المتبقية

- اكتمل حصر ملفات Blade المتبقية وتصنيفها إلى عرض عام، وعرض يحتاج إعدادًا آمنًا، ومنطق مالي/موظفين، ومنطق بيع/مخزون/طلبات شراء.
- لا يعد وسم `application/json` في فهرس المنتجات JavaScript تنفيذيًا، وقد وثق منفصلًا ضمن الحصر.
- استخرجت دفعة العرض العام الأولى: بحث منتجات المحاسب، تفاصيل تقرير الاستهلاك، تحديد الإشعارات، اختيار مستلميها، وحالة فلترة طلبات الشراء؛ وراجع محملا الثيم وSweetAlert وأبقيا كتحميلين تقنيين مشتركين.
- استخرج رسم مبيعات تفاصيل المتجر إلى وحدة مستقلة، وأصبح Blade يمرر محاور الرسم وقيمه عبر عقد إعداد آمن فقط.
- استخرجت سلوكيات عرض لوحة المالك، بما فيها المخطط وتفاصيل البطاقات والرواتب واللقطة اليومية، مع إبقاء جميع الأرقام محسوبة من الخادم وتمريرها عبر عقد إعداد آمن.
- استخرجت تفاعلات إنشاء الفاتورة وتعديلها إلى وحدتين مستقلتين، مع إبقاء أسماء الحقول وحساب الإجمالي والضريبة وأسطر الخدمات كما كانت دون تعديل مسارات الحفظ.
- استخرجت رسائل واجهة المصروف، وتأكيدات الموظفين وفحص البريد، واختيار عرض الاشتراك، وتأكيدات فجوات الشفت إلى وحدات مستقلة دون تغيير النماذج أو القرارات المرسلة.
- استخرجت واجهة تحصيل مديونية الموظف وطرق الدفع إلى وحدة مستقلة، واستبدلت أوامر Alpine التنفيذية بعقود بيانات تحمل المسار والمبلغ ونص التأكيد فقط.
- استخرجت واجهتا إنشاء المنتج وتعديله إلى وحدتين مستقلتين، مع إبقاء تحويلات الوحدات والحد الأدنى والتجزئة حرفيًا، وتحويل أخطاء التحقق إلى عقد بيانات آمن غير تنفيذي.
- استخرجت واجهتا الاستهلاك الداخلي وبيع التضليل إلى وحدتين مستقلتين، وأصبحت قوائم المنتجات تمر عبر عقود بيانات آمنة مع إبقاء حقول الكميات وحدود المخزون كما كانت.
- استخرجت واجهتا إنشاء طلب الشراء وعرضه إلى وحدتين مستقلتين، مع تمرير المنتجات والمسودة وحالة الطلب وتغييرات التكلفة عبر عقود إعداد آمنة دون تغيير حقول البنود أو مسارات الاستلام والاعتماد.
- استخرجت واجهة البيع السريع إلى وحدة مستقلة، مع إبقاء حساب الإجماليات والضريبة والدفع والآجل وفحوص المخزون حرفيًا، وتمرير المسارات وحالات المتجر فقط عبر عقد إعداد آمن.

## ما لم يُغيّر

- لم يُعدل Controller أو Route أو Model أو Migration أو Service أو استعلام.
- لم تتغير أسماء حقول الدفع أو قيم قرار الشفت أو عناوين النماذج أو طرق HTTP.
- لم تتغير قاعدة البيانات أو آلية القراءة والكتابة أو الحسابات أو المخزون أو الصلاحيات.
- لم تُضف ألوان أو أنماط محلية، ولم تتغير الهوية البصرية المعتمدة.

## نتيجة المراجعة النهائية

- لا توجد خصائص أحداث DOM مضمّنة في أي ملف Blade.
- أزيلت قائمة `protectedLegacyInlineEventFiles` بالكامل، وأصبح فشل العقد عامًا لأي واجهة حالية أو مستقبلية.
- يغطي الفحص كذلك `ondblclick` و`onkeypress` و`onfocus` و`onblur` حتى لا تعود الأحداث من أبواب لم تكن ضمن القائمة القديمة.
- بوابة القبول الأمامية الموحدة هي `npm test`؛ فهي تشغّل عقد الهوية والواجهات ثم بناء Vite بالتتابع، ويظل `git diff --check` فحص مستودع مستقلًا.
- اختبار التدفقات الفعلية ببيانات تشغيلية حقيقية لم يُنفذ في هذه البيئة، التزامًا بعدم قراءة بيانات الإنتاج أو تغييرها ضمن المراجعة البصرية.


## بوابة القبول الموحدة

1. يشغّل `npm test` فحص عقود الهوية والواجهات ثم بناء Vite في أمر واحد.
2. لا تتغير أسماء الحقول أو المسارات أو طرق HTTP أو نصوص التأكيد.
3. يمنع العقد الساكن عودة السكربت التنفيذي إلى أي واجهة مستخرجة.
4. لا يبدأ اختبار موظف أو عملية مالية فعلية قبل تزويد حسابات وبيانات متجر تجريبية صريحة وتحديد السجلات المسموح إنشاؤها وحذفها.

## خارطة طريق إكمال المهمة الحالية

> هذه الخارطة هي نقطة التسليم عند الانتقال إلى مهمة أخرى. الاستخراج البرمجي مكتمل، والمتبقي هو إثبات القبول التشغيلي في بيئة تجريبية قابلة للرجوع، لا إعادة فتح منطق الواجهات أو الحسابات.

### المرحلة 1: تثبيت نقطة التسليم

- [ ] الاحتفاظ برقم آخر commit مقبول وطلب السحب المرتبط به.
- [ ] التأكد من أن `git status --short` نظيف قبل بدء أي اختبار تشغيلي.
- [ ] تشغيل `npm test` وتسجيل نتيجته؛ هذا الأمر يفحص العقود ثم يبني أصول Vite.
- [ ] عدم إضافة ملفات `vendor` أو `.env` أو بيانات الاختبار إلى Git.

**شرط الانتقال:** نجاح البوابة الأمامية وعدم وجود تغييرات محلية غير موثقة.

### المرحلة 2: تجهيز بيئة Laravel التجريبية

- [ ] توفير `vendor/autoload.php` محليًا بواسطة Composer في بيئة التشغيل، دون رفع مجلد `vendor` إلى المستودع.
- [ ] استخدام ملف بيئة وقاعدة بيانات تجريبيين منفصلين عن الإنتاج.
- [ ] أخذ نسخة احتياطية أو snapshot قابلة للاستعادة قبل إنشاء أي سجل اختباري.
- [ ] تحديد حسابات تجريبية صريحة للمالك والمحاسب والموظف، وتحديد المتجر والمنتجات المسموح استخدامها.
- [ ] كتابة قائمة بالسجلات المسموح إنشاؤها وتعديلها وحذفها أثناء الاختبار.

**نقطة توقف إلزامية:** إذا كانت قاعدة البيانات المتاحة إنتاجية أو لم تحدد السجلات المسموحة، لا يبدأ أي اختبار كتابة.

### المرحلة 3: الاختبارات الآلية

- [ ] تشغيل `npm test` مرة أخرى داخل البيئة المكتملة.
- [ ] تشغيل `php artisan test` بعد توفر `vendor` وقاعدة الاختبار المنفصلة.
- [ ] تشغيل اختبارات Feature وUnit المرتبطة بالبيع السريع، الآجل، المديونية، المخزون، المبيعات اليومية، والفواتير.
- [ ] تسجيل أي اختبار فاشل مع اسمه ورسالة الخطأ وتحديد هل سببه التعديل الحالي أم إعداد البيئة.

**شرط الانتقال:** لا يوجد فشل مرتبط بالتغييرات الحالية، ولا يُتجاوز فشل بوصفه قديمًا دون دليل موثق.

### المرحلة 4: مصفوفة القبول البصري

تراجع الصفحات في الوضعين المظلم والفاتح، وعلى أربع فئات: شاشة كبيرة، متوسطة، صغيرة، ولمس.

- [ ] صفحات تسجيل الدخول، الاستعادة، إعادة التعيين، الترحيب، والإيقاف تظهر في منتصف الشاشة.
- [ ] النوافذ والتنبيهات والتولتيب تظهر في منتصف مساحة العرض، ويبقى المحتوى الطويل قابلًا للتمرير.
- [ ] يظهر في زر الوضع رمز واحد فقط: القمر في الوضع الفاتح والشمس في الوضع المظلم.
- [ ] قائمة «متاجري» تعرض جميع الأسماء، ولا تفتح روابط أكثر من بطاقة متجر واحدة في الوقت نفسه.
- [ ] لا توجد أخطاء Console أو طلبات Network مكررة عند فتح النوافذ أو تبديل الوضع أو التنقل بين المتاجر.

**دليل القبول:** تحفظ لقطة شاشة لكل فئة شاشة في الوضعين، مع تسجيل المسار والحساب المستخدمين.

### المرحلة 5: تدفقات القراءة الآمنة

- [ ] فتح لوحات المالك والمحاسب والمتجر ومقارنة الأرقام المعروضة قبل التعديل وبعده.
- [ ] اختبار البحث والفلاتر وفتح تفاصيل المتجر والموظف والمنتج دون حفظ تغييرات.
- [ ] التأكد من أن عقود `data-*` لا تكشف إلا البيانات اللازمة للواجهة الحالية.
- [ ] التأكد من أن الرجوع وإغلاق النوافذ وEscape واللمس لا يرسلون طلبات كتابة.

**شرط الانتقال:** لا اختلاف في الأرقام أو الصلاحيات أو الاستعلامات الناتجة عن الاستخراج.

### المرحلة 6: تدفقات الكتابة الحساسة

تنفذ فقط على السجلات التجريبية المعتمدة، مع تسجيل القيم قبل العملية وبعدها.

- [ ] بيع سريع: كاش، شبكة، ميكس، آجل كامل، وآجل جزئي.
- [ ] منتج عادي، منتج قابل للتجزئة، رول، وتضليل، مع مقارنة خصم المخزون المتوقع والفعلي.
- [ ] تحصيل آجل ومديونية كامل وجزئي، والتحقق من وسيلة الدفع والرصيد الناتج.
- [ ] تعديل عملية مبيعات يومية، ثم التحقق من الإجمالي والدفع والمخزون.
- [ ] إنشاء طلب شراء ومسودة واستعادتها، ثم الاستلام والاعتماد وتغير التكلفة.
- [ ] إنشاء فاتورة وتعديلها والتأكد من الإجمالي والضريبة وأسطر الخدمات.
- [ ] اختبار العملية المعلقة وانقطاع الاتصال في البيع السريع لمنع التكرار.

**نقطة توقف إلزامية:** أي اختلاف مالي أو مخزني يوقف بقية الاختبارات؛ تحفظ القيم والأدلة ولا ينفذ إصلاح منطقي قبل موافقة صاحب المشروع.

### المرحلة 7: التنظيف والرجوع

- [ ] حذف السجلات التجريبية المحددة فقط، أو استعادة snapshot البيئة التجريبية.
- [ ] التأكد من عودة أرصدة الموظف وكميات المنتجات وحالة الشفت إلى نقطة البداية.
- [ ] عدم تشغيل أوامر تنظيف عامة أو حذف جماعي على بيانات حقيقية.
- [ ] إرفاق سجل العمليات التي أُنشئت وأرقامها وكيف أزيلت.

### المرحلة 8: قرار الإغلاق والنشر

- [ ] نجاح `npm test` و`php artisan test` في البيئة المكتملة.
- [ ] اكتمال مصفوفة الشاشات والوضعين دون خلل بصري.
- [ ] نجاح تدفقات القراءة والكتابة وعدم وجود اختلاف مالي أو مخزني.
- [ ] مراجعة Console وNetwork والسجلات الخلفية دون أخطاء جديدة.
- [ ] اعتماد خطة الرجوع ونسخة ما قبل النشر.
- [ ] نشر commit المقبول فقط، ثم تشغيل smoke test للقراءة دون إنشاء بيانات إنتاجية.

### تعريف الاكتمال

تعد المهمة مكتملة نهائيًا عندما تنجح المراحل السابقة بأدلتها، ولا يبقى فشل غير مصنف، وتكون بيانات الاختبار قد نُظفت أو استعيدت، ويصدر صاحب المشروع قرار النشر. إلى ذلك الحين توصف الحالة بأنها: **الإصلاح البرمجي مكتمل، والقبول التشغيلي بانتظار البيئة التجريبية**.
