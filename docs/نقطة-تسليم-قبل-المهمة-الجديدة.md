# نقطة تسليم مميزة قبل المهمة الجديدة

> **علامة التسليم:** `AMON-HANDOFF-NOTIFICATIONS-2026-09-25`
>
> هذه العلامة هي المرجع الذي يجب ذكره عند فتح المهمة التالية، حتى يبدأ العمل من
> الحالة الصحيحة ولا يعاد تنفيذ PWA المتراجع عنها ضمن هذا الطلب.

## قرار الدمج الحالي

سيُدمج الطلب الحالي بما يحتويه من تحسينات نظام الإشعارات والحماية والنقل المخزني
والجرد والتقارير. لا توجد في الحالة النهائية لهذا الطلب بنية PWA قابلة للتثبيت؛
فقد تم التراجع الكامل عن التجربة في الالتزام `1602989`.

الملف `docs/ملاحظة-تحديث-الفرع.md` مجرد علامة نصية لا تضيف سلوكًا إلى التطبيق.

## ما وصلنا إليه

### منفذ ويبقى بعد الدمج

- عزل الإشعارات بحسب نوع المستلم ومنع تصادم معرفات المالك والمحاسب.
- توحيد قراءة الإشعارات وإخفائها ضمن نطاق المستلم الحالي.
- نقل إرسال OneSignal إلى Queue مع Retry وTimeout وBackoff.
- إضافة تنظيف آمن للإشعارات القديمة مع وضع المعاينة ومركز عمليات للإدارة.
- API إشعارات أولي محمي بجلسة الويب؛ ليس API Token لتطبيق Flutter بعد.
- تشديد حراس المالك والمحاسب والمتجر ومسارات المصادقة الحساسة.
- اعتماد يوم العمل في النقل المخزني وإضافة تقرير النقل ونسخة PDF.
- الحفظ الجماعي لجرد المحاسب والمسودة المحلية الخاصة بصفحة الجرد.

### تم التراجع عنه ولا يعد جزءًا من الحالة النهائية

- Manifest الخاص بـPWA.
- Service Worker وOffline shell.
- أيقونة تثبيت PWA.
- تسجيل Service Worker في JavaScript.
- App Context API التجريبي وRequest ID اللذان أضيفا ضمن حزمة PWA.
- اختبارات وعقد PWA التجريبيان.

## بداية المهمة الجديدة

1. ادمج الطلب الحالي أولًا.
2. أنشئ فرعًا جديدًا من أحدث نسخة للفرع الأساسي بعد الدمج، ولا تواصل على فرع
   هذا الطلب.
3. اذكر علامة التسليم `AMON-HANDOFF-NOTIFICATIONS-2026-09-25` في وصف المهمة.
4. راجع `docs/خارطة-طريق-PWA-Flutter.md`، لكن تعامل مع حالة PWA التنفيذية على
   أنها **غير منفذة** بعد التراجع.
5. قبل أي واجهة اقرأ `docs/الهوية-البصرية-للمشروع.md`.
6. لا تنشئ Migration ولا تعدل البيانات الحقيقية في أول دفعة.
7. ابدأ بتدقيق واختبارات تشغيل ما تم تنفيذه في الإشعارات، ثم اختر نظامًا واحدًا
   فقط للحزمة التالية.

## الحزمة التالية المقترحة

الحزمة الآمنة التالية هي **تثبيت نظام الإشعارات الحالي على Staging** قبل إعادة
فتح PWA:

**تحديث التنفيذ:** أضيف الفحص الثابت القابل للتكرار بالأمر
`npm run test:notifications`، وأضيفت بوابة التشغيل في
`docs/بوابة-Staging-لنظام-الإشعارات.md`. لا تزال التجارب الفعلية على Staging
وقياسات قاعدة البيانات وQueue مطلوبة، ولا يدعي الفحص الثابت أنها نُفذت.

- Feature Tests لعزل المالك والمحاسب وصلاحيات القراءة والإخفاء.
- تشغيل Queue worker وScheduler ومراقبة failed jobs وqueue lag.
- تجربة OneSignal بمستلمين اختباريين فقط.
- قياس استعلامات قائمة الإشعارات والعداد.
- اختبار مركز عمليات الإدارة والحذف التجريبي `--dry-run`.
- تسجيل النتائج والمشكلات دون تغيير Schema الإنتاج.

بعد اجتياز هذه البوابة يمكن فتح طلب مستقل جديد لتأسيس PWA من الصفر، بأصول نصية
فقط في أول دفعة، ومن دون Offline للعمليات المالية أو المخزنية الحساسة.

## حدود واضحة للمهمة التالية

- لا تخلط إعادة PWA مع إصلاحات الإشعارات في طلب واحد.
- لا تستخدم Livewire في منطق الإشعارات أو API.
- لا تعتبر API الجلسة الحالي صالحًا لـFlutter؛ يلزم قرار مستقل للمصادقة بالرموز.
- لا تعتمد أي عملية بيع أو جرد أو نقل أثناء انقطاع الإنترنت تلقائيًا.
- لا تحذف Queue قبل قياسها؛ مركز الإدارة يدير السجلات ولا يستبدل عامل الإرسال.
