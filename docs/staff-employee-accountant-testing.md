# مستند اختبارات نظام الموظفين والمحاسبين

> الغرض: هذا المستند يشرح ما نحتاجه لاختبار نظام الموظفين والمحاسبين والعمليات المرتبطة بهم، وكيفية تطبيق الاختبارات بدون أن يقوم المطور بإنشاء بيانات قاعدة البيانات الأساسية. المالك/المتجر/الموظف/المحاسب سيتم تجهيزهم يدويًا قبل تشغيل الاختبارات حسب قرار مالك المشروع.

## 1. نطاق النظام المطلوب اختباره

يشمل النظام:

1. صفحات الموظفين:
   - صفحة كل موظفي المالك: `user.employees.index`.
   - صفحة موظفي متجر محدد: `user.stores.employees.index`.
2. صفحات المحاسبين:
   - صفحة كل محاسبي المالك: `user.accountants.index`.
   - صفحة محاسبي متجر محدد: `user.stores.accountants.index`.
3. عمليات الموظف أو المحاسب المرتبط بموظف:
   - السحب.
   - الغياب.
   - المديونية.
   - البيع الآجل.
   - تحصيل الآجل.
   - تحصيل المديونية.
4. إجراءات الحالة:
   - إضافة موظف/محاسب.
   - تعديل بيانات موظف/محاسب.
   - إيقاف/تفعيل موظف.
   - إيقاف/تفعيل محاسب.
   - حذف/استرجاع موظف.
   - حذف/استرجاع محاسب.
5. التقارير:
   - راتب الشهر.
   - خصم الغياب.
   - السحوبات.
   - المديونيات.
   - البيع الآجل والتحصيلات.
   - تقرير PDF للموظف.
6. تاريخ الموظف:
   - النقل بين المتاجر.
   - تغيير الراتب داخل الشهر.
   - الإيقاف داخل الشهر.
   - حذف أو إيقاف الموظف في شهر لاحق دون التأثير على تقارير الشهور السابقة.

## 2. بيانات الاختبار التي سيجهزها مالك المشروع

حسب التعليمات، لن يقوم الاختبار بإنشاء البيانات الأساسية التالية تلقائيًا، بل يتم الاعتماد على بيانات جاهزة في قاعدة البيانات:

| الكيان | المطلوب |
|---|---|
| المالك | مستخدم مالك له صلاحية دخول إلى لوحة المالك. |
| المتجر | متجر واحد على الأقل تابع للمالك. ويفضل متجران لاختبارات النقل. |
| الموظف | موظف تابع للمتجر الأول. |
| المحاسب | حساب محاسب مرتبط بموظف أو موظف مستقل حسب السيناريو. |

### متغيرات بيئة مقترحة للاختبارات اليدوية/شبه الآلية

حتى لا نثبت أرقامًا داخل ملفات الاختبار، يمكن تشغيل الاختبارات بقيم من `.env.testing` أو من متغيرات بيئة:

```env
TEST_OWNER_ID=1
TEST_STORE_ID=1
TEST_SECOND_STORE_ID=2
TEST_EMPLOYEE_ID=1
TEST_ACCOUNTANT_ID=1
```

إذا لم تكن هذه القيم موجودة، يجب أن يفشل الاختبار برسالة واضحة مثل:

```text
Missing TEST_OWNER_ID / TEST_STORE_ID / TEST_EMPLOYEE_ID / TEST_ACCOUNTANT_ID
```

## 3. قواعد عامة قبل كتابة الاختبارات

1. لا نختبر على بيانات عشوائية في قاعدة الإنتاج.
2. يجب تشغيل الاختبارات على قاعدة اختبار أو نسخة تجريبية.
3. لا نستخدم `RefreshDatabase` إذا كنا سنعتمد على بيانات يجهزها مالك المشروع يدويًا.
4. يمكن استخدام `DatabaseTransactions` عند الحاجة، حتى يتم التراجع عن العمليات التي ينفذها الاختبار.
5. أي اختبار يغير حالة موظف أو محاسب يجب أن يعيد الحالة كما كانت أو يعمل داخل Transaction.
6. يجب فصل اختبارات القراءة عن اختبارات الكتابة.
7. اختبارات الرواتب يجب أن تحدد شهرًا واضحًا مثل `2026-06` أو `2026-07` ولا تعتمد على `now()` إلا عند اختبار الشهر الحالي.
8. أي اختبار يتعلق بالنقل أو الرواتب يجب أن يستخدم تواريخ ثابتة.
9. أي اختبار يتعلق بالصفحات يجب أن يتحقق من `return_to` والرجوع إلى الصفحة الأصلية.

## 4. خطة اختبارات الصفحات الأربع بعد دمجها في صفحتين

رغم أن الواجهات أصبحت موحدة، يجب اختبار الروابط الأربعة لأنها ما زالت مهمة للمستخدم:

| الرابط | المطلوب |
|---|---|
| `/user/employees` | يعرض كل موظفي المالك في كل المتاجر. |
| `/user/stores/{store}/employees` | يعرض موظفي المتجر المحدد فقط. |
| `/user/accountants` | يعرض كل محاسبي المالك في كل المتاجر. |
| `/user/stores/{store}/accountants` | يعرض محاسبي المتجر المحدد فقط. |

### 4.1 اختبارات صفحة كل موظفي المالك

#### يجب اختبار التالي:

1. الصفحة تفتح بنجاح للمالك.
2. تعرض موظفي كل متاجر المالك.
3. لا تعرض موظفي مالك آخر.
4. زر إضافة موظف يحمل `return_to` إلى `/user/employees`.
5. زر عرض الموظف يحمل `return_to` إلى `/user/employees`.
6. زر تعديل الموظف يحمل `return_to` إلى `/user/employees`.
7. إيقاف الموظف يرجع إلى `/user/employees`.
8. تفعيل الموظف يرجع إلى `/user/employees`.
9. حذف الموظف يرجع إلى `/user/employees`.
10. دخول سلة الموظفين من صفحة كل الموظفين يرجع إلى `/user/employees`.

#### حالة الرجوع المتوقعة

| العملية | الرجوع المتوقع |
|---|---|
| إضافة موظف | صفحة كل موظفي المالك. |
| تعديل موظف | صفحة كل موظفي المالك. |
| إيقاف/تفعيل موظف | صفحة كل موظفي المالك. |
| حذف موظف | صفحة كل موظفي المالك. |
| استرجاع موظف من السلة | يبقى في السلة بعد التنفيذ، وزر الرجوع يرجع إلى صفحة كل موظفي المالك. |

> ملاحظة مهمة: الاسترجاع يتم داخل صفحة السلة. لذلك السلوك الحالي المتوقع هو البقاء في السلة بعد الاسترجاع، ثم الرجوع بزر الرجوع إلى صفحة القائمة الأصلية. إذا أردنا أن ينتقل مباشرة إلى صفحة الموظفين بعد الاسترجاع، فهذا تغيير سلوك منفصل يجب اعتماده.

### 4.2 اختبارات صفحة موظفي متجر محدد

#### يجب اختبار التالي:

1. الصفحة تفتح بنجاح للمالك إذا كان المتجر تابعًا له.
2. الصفحة تمنع الوصول إذا كان المتجر ليس تابعًا للمالك.
3. تعرض موظفي هذا المتجر فقط.
4. لا تعرض موظفي المتاجر الأخرى.
5. زر إضافة موظف يحمل `store_id` و `return_to` إلى صفحة موظفي هذا المتجر.
6. زر عرض الموظف يحمل `return_to` إلى صفحة موظفي هذا المتجر.
7. زر تعديل الموظف يحمل `return_to` إلى صفحة موظفي هذا المتجر.
8. إيقاف/تفعيل الموظف يرجع إلى صفحة موظفي هذا المتجر.
9. حذف الموظف يرجع إلى صفحة موظفي هذا المتجر.
10. سلة الموظفين من صفحة المتجر تعرض محذوفي هذا المتجر فقط، وزر الرجوع يرجع لصفحة موظفي هذا المتجر.

#### حالة الرجوع المتوقعة

|---|---|
| إضافة موظف | صفحة موظفي المتجر. |

| إيقاف/تفعيل موظف | صفحة موظفي المتجر. |
| حذف موظف | صفحة موظفي المتجر. |
| استرجاع موظف من السلة | يبقى في سلة موظفي المتجر، وزر الرجوع يرجع إلى صفحة موظفي المتجر. |

## 5. اختبارات العمليات المالية للموظف/المحاسب

يجب أن نختبر العمليات على `Employee` سواء كان موظفًا عاديًا أو موظفًا مرتبطًا بحساب محاسب.

### 5.1 السحب

سيناريوهات الاختبار:

1. تسجيل سحب لموظف.
2. تسجيل سحب لموظف مرتبط بمحاسب.
3. منع تكرار نفس السحب بنفس التاريخ والقيمة والوصف.
4. حفظ `store_id` الحالي للعملية.
5. حفظ `person_id` و `person_type`.
6. حفظ `added_by` حسب منفذ العملية.
7. ظهور السحب في تقرير الشهر الصحيح.
8. إذا نُقل الموظف لاحقًا، يبقى السحب على متجره الأصلي.

### 5.2 الغياب

سيناريوهات الاختبار:

1. تسجيل غياب بتاريخ محدد.
2. منع تسجيل غياب مكرر لنفس اليوم.
3. احتساب خصم الغياب من الراتب.
4. بقاء الغياب على المتجر الأصلي بعد نقل الموظف.
5. ظهور الغياب في PDF ضمن أيام التقرير.

### 5.3 المديونية

سيناريوهات الاختبار:

1. إضافة مديونية.
2. تحصيل جزئي.
3. تحصيل كامل.
4. عند نقل الموظف، تنتقل المديونيات حسب القاعدة الحالية.
5. لا تختلط المديونيات بين ملاك مختلفين.

### 5.4 البيع الآجل

سيناريوهات الاختبار:

1. إضافة بيع آجل.
2. تحصيل جزئي.
3. تحصيل كامل.
4. ظهور المتبقي بشكل صحيح.
5. ظهور التحصيلات في تقرير الموظف.

## 6. اختبارات الرواتب والتقارير

### 6.1 راتب موظف بدون تغييرات

المتوقع:

1. راتب كامل إذا عمل كامل الشهر.
2. لا توجد أيام إيقاف.
3. لا يوجد خصم غياب.

### 6.2 إيقاف موظف داخل الشهر

مثال:

- الراتب: 3000.
- الإيقاف: يوم 17.

المتوقع:

1. يحسب له راتب أيام العمل فقط.
2. الأيام بعد الإيقاف لا تحتسب.
3. تقارير الشهور السابقة لا تتغير.

### 6.3 زيادة راتب داخل الشهر

مثال:

- من يوم 1 إلى 9: الراتب القديم.
- من يوم 10 إلى نهاية الشهر: الراتب الجديد.

المتوقع:

1. لا يتم تعديل أي بيانات قديمة.
2. الراتب المستحق يحسب يوميًا حسب راتب كل يوم.
3. تقرير الشهر السابق لا يتأثر.

### 6.4 نقل موظف داخل الشهر

مثال:

- من يوم 1 إلى 7 في متجر 1.
- من يوم 8 إلى نهاية الشهر في متجر 2.

المتوقع:

1. تقرير متجر 1 يحتسب أيام متجر 1 فقط.
2. تقرير متجر 2 يحتسب أيام متجر 2 فقط.
3. السحب والغياب يبقيان في المتجر الذي حدثا فيه.
4. المديونية تنتقل حسب القاعدة الحالية.

## 7. اختبارات PDF للموظف

يجب اختبار:

1. التقرير يفتح بدون أخطاء.
2. يظهر راتب التقرير.
3. يظهر عدد أيام العمل.
4. يظهر عدد أيام الإيقاف.
5. يظهر خصم الغياب.
6. يظهر السحب.
7. يظهر الغياب وتأثيره.
8. يظهر اسم منفذ العملية إذا كان مطلوبًا.
9. إذا كان هناك محاسب واحد فقط في المتجر، يظهر اسمه في بيانات المتجر ويختفي عمود `سجّل بواسطة`.
10. إذا كان هناك أكثر من محاسب أو تغير منفذ العملية، يظهر عمود `سجّل بواسطة`.
11. إذا لا توجد عمليات من متجر آخر، لا يظهر عمود `متجر آخر`.
12. إذا توجد عملية من متجر آخر، يظهر عمود `متجر آخر`.

## 8. طريقة تطبيق الاختبارات

### 8.1 اختبارات قراءة لا تغير البيانات

هذه يمكن تشغيلها بأمان نسبيًا:

```bash
php artisan test --filter=EmployeeIndexTest
php artisan test --filter=AccountantIndexTest
```

أمثلة:

- فتح صفحة كل الموظفين.
- فتح صفحة موظفي متجر.
- فتح صفحة كل المحاسبين.
- فتح صفحة محاسبي متجر.
- التأكد من ظهور أسماء محددة.
- التأكد من عدم ظهور أسماء خارج المتجر.

### 8.2 اختبارات كتابة داخل Transaction

هذه تنفذ عمليات ثم تتراجع عنها:

```php
use Illuminate\Foundation\Testing\DatabaseTransactions;

class EmployeeOperationTest extends TestCase
{
    use DatabaseTransactions;
}
```

أمثلة:

- تسجيل سحب.
- تسجيل غياب.
- إيقاف موظف.
- تفعيل موظف.
- حذف موظف Soft Delete.

### 8.3 اختبارات لا ننفذها إلا على قاعدة اختبار

هذه خطرة ولا تشغل على بيانات حقيقية إلا إذا وافق مالك المشروع:

- حذف نهائي.
- نقل موظف بين متاجر.
- تعديل راتب فعلي.
- تغيير حالة محاسب فعلي.

## 12. ملاحظات مهمة قبل التنفيذ

1. إذا أردنا أن الاسترجاع بعد الضغط عليه يرجع مباشرة إلى صفحة القائمة الأصلية بدل البقاء في السلة، فهذا يحتاج تعديل سلوك بسيط في restore للموظفين والمحاسبين.
2. إذا أردنا ضمان الرجوع في إيقاف/تفعيل المحاسب دون الاعتماد على `back()`، يمكن لاحقًا تعديل الكنترولر ليقرأ `return_to` مثل الموظفين.
3. الأفضل أن نبدأ باختبارات الرجوع والفلترة لأنها أقل خطرًا من اختبارات العمليات المالية.
4. بعد ذلك ننتقل لاختبارات الرواتب والنقل لأنها الأكثر حساسية.
5. لا يتم تشغيل اختبارات الكتابة على قاعدة بيانات حقيقية إلا بعد أخذ نسخة احتياطية أو استخدام قاعدة اختبار.
